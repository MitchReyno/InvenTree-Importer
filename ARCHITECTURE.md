# Repository architecture

The repository is a root pnpm workspace containing a uv-managed Python importer in `backend/`, a React/TypeScript/Vite manual intake application in `frontend/`, and a Fastify/PostgreSQL application in `intake-server/` with runtime schemas in `contracts/`. The browser consumes same-origin capture, review and optional media APIs; Python remains disconnected. Root pnpm scripts expose separate application/check entry points; no web import or autoreload starts an inventory executor or durable worker.

## Application boundaries

`backend/` owns `pyproject.toml`, `uv.lock`, `.python-version`, `src/invimport/`, importer `config/`, Python `tests/` and operational `scripts/`. Its package name, CLI and import contracts remain `invimport`. The ordinary importer retains its legacy default; durable execution is an explicit bounded opt-in. Detailed identity, approval, ownership, effects, recovery and release limits live in the [backend architecture](backend/ARCHITECTURE.md), not in a parallel root summary.

`frontend/` owns its package dependencies/scripts, Vite configuration, TypeScript source and component tests. It consumes validated generated capture, review and media DTOs, retains batch/subject URLs and presents human notes, exact selections, distinct physical lots/shared Part proposals, defaults/overrides and explicit revision conflicts.

PostgreSQL owns retained state. The browser requests exact server-bound approval and explicit supervised apply through the same-origin API; it holds no inventory mutation credential. Optional retained uploads and deterministic crop versions are implemented. Provider inference, the Python runtime connection and final authentication/access qualification remain future work. Built assets are served same-origin by Fastify; standalone Vite has no API proxy. The [frontend architecture](frontend/ARCHITECTURE.md) links primary original layout references and separates this manual slice from later work.

`intake-server/` retains the T01 strict parser/serializer, development actor/target attribution, loopback Host/Origin/CSRF controls, reviewed SQL, Drizzle/pg access and owned PostgreSQL workflow. T02 adds explicit `capture/routes.ts` registration, scoped transactional persistence and bounded semantic existing-Part/location reads. `0002_capture.sql` is additive; immutable command/note/selection history preserves source/contribution identity.

`contracts/` owns runtime schemas and generated OpenAPI/DTO/client artifacts. T04 adds exact manual review/preparation/approval and journal-derived results through `review/routes.ts`; only a separately started owned-fake runner can dispatch supervised stock execution. Providers and final identity/permission qualification remain unimplemented.

Public-boundary PG/process tests qualify DBOS 5.4.0 for bounded scheduler delivery/recovery, not physical writer ownership. The [T01](docs/handovers/bench-intake-T01.md) and [T02](docs/handovers/bench-intake-T02.md) handovers record evidence/limits. No root `.env` is read by these packages; T02 tests use controlled fake reads and send the protected real inventory no requests.

Keep dependencies within these declared boundaries. Shared documentation/tooling and the explicit `contracts` runtime package are different responsibilities. Do not make the backend import frontend or test code, or add a second importer policy implementation to the UI. Capture is not an executable import preview or authorization boundary. Later consumers use reviewed public contracts and owning repositories rather than sibling SQL internals.

## Supervised stock execution

T03 is merged as PR #42. The [execution module](intake-server/src/execution/ARCHITECTURE.md) owns immutable approval/run/request/effect authority, original-run safe recovery, cancellation, physical host exclusion and external activation/restore witnesses. The initial stock profile is `owned-fake-stock/1`; T05 adds the bounded fake media profile described below. API530's inspected stock-create serializer lacks writable barcode attribution; no actual InvenTree mutation profile is supported or promised.

T04 connects capture and executor through public scoped materialization, source-history and exact reservation seams. Its [handover](docs/handovers/bench-intake-T04.md) records the observed two-lot browser/PG/DBOS/supervisor/fake journey, adverse cases and remaining limits. The web process never starts an apply worker. The real server named by the original root `.env` remains strictly read-only.

T05 adds retained private originals, immutable deterministic crop versions and selected attachments through the [owning media boundary](intake-server/ARCHITECTURE.md#retained-media-and-additive-attachment-execution). Explicit configuration binds the private blob root to its database; a separately started, bounded decoder handles image/PDF processing. Additive approval and execution formats seal exact evidence versions and destinations under `owned-fake-media/1`. Attachment recovery remains attached to the original run and never recreates stock. The [T05 handover](docs/handovers/bench-intake-T05.md) records its fake-target and containment evidence.

T09 extends the same authority with explicit new-Part specifications, observed existing category/parameter/company mappings, initial tag names and selected Part attachments under `owned-fake-effects/1`. Missing tag names may be created through the native initial-Part request shape; existing-Part reuse does not authorize tag collection replacement or arbitrary metadata changes. Category/template/company creation stays unsupported. The additive effects plan, journal and migration0010 preserve legacy stock/media bytes and bind dependent operations to attributable Part outputs. Selected assessment and repair retain the original run/approval; later rounds require fresh review and checked known-output reuse rather than recreating a Part or consumed stock. The [T09 handover](docs/handovers/bench-intake-T09.md) distinguishes owned-fake qualification, upstream API source research and remaining compatibility limits. No InvenTree server plugin is required or connected.

Actual InvenTree mutation and live provider inference are unqualified. Provider integration tests use deterministic stubs until Mitch explicitly authorizes model usage; existing sign-in does not authorize a test call.

## Durable Processing coordination

T06 adds provider-neutral retained jobs, exact input attempts, authenticated results, proposals and application questions through the [Processing boundary](intake-server/src/processing/ARCHITECTURE.md). New internal V2 formats bind exact media manifest text/digests and typed note/version provenance; old sealed inputs remain readable. The public media module owns scoped reads, retention handles and immutable command-pin verification. Human answers reuse capture validation and commit the edit, continuation and events together.

PostgreSQL owns logical attempts and actor-lane reservations; DBOS provides bounded delivery. Logical cancellation or stale input does not prove a child stopped. Only exact command-ending settlement or interruption after reap releases its held lane, and old output cannot regress a newer attempt. The [T06 handover](docs/handovers/bench-intake-T06.md) distinguishes actual deterministic child tests from unqualified native-provider behavior.

Processing UI exposes the approved subviews, pinned React Hook Form questions, scoped retained reads and separate global lane activity. The injected research adapter is fixture-only and has no inventory mutation capability. Native inference, entitlement, content inspection and final identity remain future qualification; application model tests use stubs until explicit authorization.

## Workspace and data ownership

Root `package.json` delegates development/build/check commands; each Node application/contracts package owns its dependencies and root `pnpm-lock.yaml` is the single pnpm lockfile. Root development dependencies supply Prettier for eligible web/code files and remark for Markdown with unwrapped prose; Python remains Ruff-managed. CLI, VS Code and changed-file hooks share owning configs and protected/generated exclusions; see the [formatting workflow](README.md#formatting-in-cli-and-vs-code). Python remains uv-managed with its own backend lock; its development group supplies pre-commit for opt-in hooks. `.node-version` pins maintained Node LTS; Python's version stays scoped to backend. CI runs on PRs and pushes to `main` / `interactive-app`; **Changed paths** always tests the selector and passes typed booleans to local reusable **Test** / **Lint** workflows. Package-scoped frontend, intake contracts/HTTP and intake PG/process jobs do not expand root aggregate commands. Intake-server-only code selects neither frontend nor Python; contracts select both server and browser consumers. Docs-only changes do not run server/backend suites. Shared workspace/toolchain inputs select their actual consumers; workflow changes or unavailable comparison history conservatively select all checks. Each selected failure remains failed, while unselected jobs skip; there is no required aggregate, `continue-on-error` or failure-masking gate. The coordinator's removal of required status checks, preserving history protection, is recorded in [T00](docs/handovers/bench-intake-T00-ci.md). Selected relevant checks and independent review still gate coordinator merges. No tests run in local pre-commit. See the [root README](README.md#commit-hooks-and-ci), [intake testing tiers](intake-server/TESTING.md) and [layout guide](docs/repository-layout.md).

Root `.env`, `.local_imports/`, `.cache/`, `.temp/` and backups retain their existing meaning; relocation does not migrate or delete them. Explicit relative arguments remain caller-cwd-relative. Omitted managed cache/scanner-export defaults from backend cwd share root local data. Platform execution/scanner state and an explicit `INVIMPORT_STATE_DIR` keep their existing namespace. Backend source location anchors default environment/config discovery; it does not search an unrelated cwd repository. Frontend Vite configuration neither loads root `.env` nor proxies to inventory. See the layout guide for exact rules and wheel limits.

## Provisional integration spikes

The [shared spike fixture and message contract](spikes/shared/README.md) provides versioned JSON Schema and original synthetic evidence for independent provider, coordinator and importer-adapter investigations. It is repository-only investigation material, checked offline by `pnpm spikes:check` and the backend's normal suite. It does not add production endpoints, a coordinator, provider authentication or inventory-write authority, and it does not change the packaged importer or frontend runtime. Domain revisions, attempt correlation and intended consumer acceptance rules are explicit; their transactional enforcement remains part of the individual spikes.

The consolidated importer-adapter spike also adds the narrow packaged `execution.adoption.inspect_binding` API and its registry-owned lookup, described in the [backend adoption boundary](backend/ARCHITECTURE.md#ownership-transport-and-recovery). This read-only inspection seam does not change the CLI default, grant a writer lease or relax execution/recovery policy. The other spike runtimes and their dependency environments remain repository-only investigations, not production application services.

The [proposed intake design](docs/intake-design.md) and [revised application delivery plan](docs/intake-plan.md) reconcile the separately reviewed spikes, distinguish actual provider observations from synthetic/fake-target evidence, and retain outstanding runtime and combined-integration gates. They recommend boundaries for later work rather than describe an implemented application. The [reconciliation handover](docs/handovers/intake-spike-decisions.md) records decisions, alternatives, validation and publication limits.

## Documentation and change ownership

Maintain this file as the cross-application map and responsibility contract. Keep application internals in their corresponding `ARCHITECTURE.md` and language/ framework rules in their `CODE_GUIDELINES.md`; root [CODE_GUIDELINES.md](CODE_GUIDELINES.md) owns shared engineering rules. When a boundary changes, update its owning document and any callers/operator guidance in the same change. Root README and AGENTS are entry points into this map.

Backend stage decisions, rejected candidates, acceptance evidence and historical release limits remain in `docs/handovers/` and the maintained execution documents. The relocation/documentation split is recorded in its [handover](docs/handovers/repository-layout.md). Historical handovers retain the filenames and commands used at the time; active links point to current documents. Future product plans must be labeled as plans and cannot imply implemented API, deployment or end-to-end UI behavior. Nothing in this map enables a new default import path, remote concurrency guarantee or live inventory authorization.
