# Repository architecture

The repository is a root pnpm workspace containing a uv-managed Python importer in `backend/`, a minimal React/TypeScript/Vite intake scaffold in `frontend/`, and an independent Fastify/PostgreSQL foundation in `intake-server/` with runtime schemas in `contracts/`. The browser and Python importer have no runtime connection to this new API. Root pnpm scripts expose separate application/check entry points; no web import or autoreload starts an inventory executor or durable worker.

## Application boundaries

`backend/` owns `pyproject.toml`, `uv.lock`, `.python-version`, `src/invimport/`, importer `config/`, Python `tests/` and operational `scripts/`. Its package name, CLI and import contracts remain `invimport`. The ordinary importer retains its legacy default; durable execution is an explicit bounded opt-in. Detailed identity, approval, ownership, effects, recovery and release limits live in the [backend architecture](backend/ARCHITECTURE.md), not in a parallel root summary.

`frontend/` owns its package dependencies/scripts, Vite configuration, TypeScript source and component tests. It currently holds selected File objects in browser memory and displays names/sizes/removal controls. It does not upload, parse, persist, approve or mutate inventory. There is no backend HTTP API, dev proxy, authentication or workflow runner connecting it to the importer. The [frontend architecture](frontend/ARCHITECTURE.md) distinguishes this implemented scaffold from future work.

`intake-server/` owns the T01 executable foundation: strict Fastify parser/serializer, development actor/target attribution, loopback Host/Origin/CSRF controls, explicit reviewed SQL migrations, Drizzle/pg access and owned PostgreSQL development-service workflow. `contracts/` owns runtime schemas and generated OpenAPI/DTO/client artifacts. Only health and development bootstrap are application routes; capture, approval, inventory execution, provider inference and final identity/permission qualification are not implemented. Public-boundary PG/process tests qualify DBOS 5.4.0 for bounded scheduler delivery/recovery, not physical writer ownership. The [T01 handover](docs/handovers/bench-intake-T01.md) records exact evidence and limitations. No root `.env` is read by the new packages and the protected real inventory remains read-only; T01 sends it no requests at all.

Keep dependencies within these declared boundaries. Shared documentation/tooling and the explicit `contracts` runtime package are different responsibilities. Do not make the backend import frontend or test code, or add a second importer policy implementation to a future UI. The file picker is not an executable import preview or an authorization boundary. Later consumers use reviewed public contracts and owning repositories rather than sibling SQL internals.

## Workspace and data ownership

Root `package.json` delegates development/build/check commands; each Node application/contracts package owns its dependencies and root `pnpm-lock.yaml` is the single pnpm lockfile. Root development dependencies supply Prettier for eligible web/code files and remark for shared Markdown formatting/linting, including GitHub-flavored Markdown and unwrapped prose; Python formatting/linting remains Ruff's responsibility. Shared CLI, VS Code defaults and changed-file pre-commit hooks use the same owning configs, with generated/evidence exclusions and explicit restaging after rewrites; see the [formatting workflow](README.md#formatting-in-cli-and-vs-code). Python remains uv-managed with its own backend lock; its development group supplies pre-commit for opt-in hooks. `.node-version` pins maintained Node LTS; Python's version stays scoped to backend. CI runs on PRs and pushes to `main` / `interactive-app`; **Changed paths** always tests the selector and passes typed booleans to local reusable **Test** / **Lint** workflows. Package-scoped frontend, intake contracts/HTTP and intake PG/process jobs do not expand root aggregate commands. Intake-only code selects neither disconnected frontend nor Python; docs-only changes do not run server/backend suites. Shared workspace/toolchain inputs select their actual consumers; workflow changes or unavailable comparison history conservatively select all checks. Each selected failure remains failed, while unselected jobs skip; there is no required aggregate, `continue-on-error` or failure-masking gate. The coordinator's removal of required status checks, preserving history protection, is recorded in [T00](docs/handovers/bench-intake-T00-ci.md). Selected relevant checks and independent review still gate coordinator merges. No tests run in local pre-commit. See the [root README](README.md#commit-hooks-and-ci), [intake testing tiers](intake-server/TESTING.md) and [layout guide](docs/repository-layout.md).

Root `.env`, `.local_imports/`, `.cache/`, `.temp/` and backups retain their existing meaning; relocation does not migrate or delete them. Explicit relative arguments remain caller-cwd-relative. Omitted managed cache/scanner-export defaults from backend cwd share root local data. Platform execution/scanner state and an explicit `INVIMPORT_STATE_DIR` keep their existing namespace. Backend source location anchors default environment/config discovery; it does not search an unrelated cwd repository. Frontend Vite configuration neither loads root `.env` nor proxies to inventory. See the layout guide for exact rules and wheel limits.

## Provisional integration spikes

The [shared spike fixture and message contract](spikes/shared/README.md) provides versioned JSON Schema and original synthetic evidence for independent provider, coordinator and importer-adapter investigations. It is repository-only investigation material, checked offline by `pnpm spikes:check` and the backend's normal suite. It does not add production endpoints, a coordinator, provider authentication or inventory-write authority, and it does not change the packaged importer or frontend runtime. Domain revisions, attempt correlation and intended consumer acceptance rules are explicit; their transactional enforcement remains part of the individual spikes.

The consolidated importer-adapter spike also adds the narrow packaged `execution.adoption.inspect_binding` API and its registry-owned lookup, described in the [backend adoption boundary](backend/ARCHITECTURE.md#ownership-transport-and-recovery). This read-only inspection seam does not change the CLI default, grant a writer lease or relax execution/recovery policy. The other spike runtimes and their dependency environments remain repository-only investigations, not production application services.

The [proposed intake design](docs/intake-design.md) and [revised application delivery plan](docs/intake-plan.md) reconcile the separately reviewed spikes, distinguish actual provider observations from synthetic/fake-target evidence, and retain outstanding runtime and combined-integration gates. They recommend boundaries for later work rather than describe an implemented application. The [reconciliation handover](docs/handovers/intake-spike-decisions.md) records decisions, alternatives, validation and publication limits.

## Documentation and change ownership

Maintain this file as the cross-application map and responsibility contract. Keep application internals in their corresponding `ARCHITECTURE.md` and language/ framework rules in their `CODE_GUIDELINES.md`; root [CODE_GUIDELINES.md](CODE_GUIDELINES.md) owns shared engineering rules. When a boundary changes, update its owning document and any callers/operator guidance in the same change. Root README and AGENTS are entry points into this map.

Backend stage decisions, rejected candidates, acceptance evidence and historical release limits remain in `docs/handovers/` and the maintained execution documents. The relocation/documentation split is recorded in its [handover](docs/handovers/repository-layout.md). Historical handovers retain the filenames and commands used at the time; active links point to current documents. Future product plans must be labeled as plans and cannot imply implemented API, deployment or end-to-end UI behavior. Nothing in this map enables a new default import path, remote concurrency guarantee or live inventory authorization.
