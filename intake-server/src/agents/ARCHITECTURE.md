# Native agent integration

Native agent sessions reuse Processing attempts, currentness, actor lanes, human questions and retained proposals. This first profile is `native-agent/1` with immutable input/command/envelope version 4 and handler `processing/4`. Earlier fixture formats and instruction bytes remain unchanged. Native support is labelled `native_unverified`: deterministic protocol tests do not establish actual inference, account access or host containment.

## Defaults and session history

One settings row, with one provider row each for Claude and Codex, belongs to the configured operator, target and target context, and applies across batches. No billable model is selected implicitly. Expected-revision writes preserve concurrent edits. Each new native attempt seals the provider, authentication mode, requested model and settings revision resolved for its stage (`resolve-selection.ts`) in its immutable input. An operator-started attempt reads the settings under a shared lock; the Examine trigger and a stable identity's successors, which run as the agent writer, read them once without a lock and seal that same read into every attempt they queue. Default changes neither rewrite nor invalidate an existing attempt.

The separate session table stores timestamps, the native session identifier, resolved model and one bounded progress phase. Processing owns lifecycle, cancellation and physical lane occupancy. Session reads join scoped command authority and retained attempt state in one bounded query. The `latest_on_job` field describes selected attempt identity, not evidence freshness. Opening the batch uses the owning Processing currentness/provenance checks before exposing actionable results; history grants no suggestion authority. History is paginated by queue time and attempt ID. The browser displays lifecycle and metadata; accepted suggestions and questions remain in the owning batch view. Raw provider streams, stderr, credentials and private reasoning are not retained or published. A failed turn's diagnostic keeps only the provider's structured error: its kind (Claude's assistant `error`, or Codex's `codexErrorInfo` kind) and Claude's result `subtype`, each checked against a fixed list in `failure-model.ts`, and an HTTP status (Claude's result `api_error_status`, or the status inside Codex's `codexErrorInfo`), checked against the 100–599 range. A VM tool worker passes it to its supervisor and the guest sends it with its failure frame; each receiver checks it again.

## Provider boundary

`codex.ts` uses the installed Codex app-server over stdio JSON-RPC. API-key mode uses a fixed OpenAI Responses endpoint and an environment-key provider, without persisting the key through a login RPC. Its separate `codex-api` home never opens the subscription login store. Subscription mode reads the CLI's existing native account using a dedicated application Codex home. The operator signs in directly; the application never copies an authentication store. Effective sandbox, approval policy and provider must match the requested route before a turn starts.

`claude.ts` invokes the unmodified Claude Code CLI in headless stream-JSON mode. Subscription mode requires a pre-existing first-party host CLI login. API-key mode uses bare mode to avoid keychain authentication; subscription mode cannot use bare mode. Both use safe mode, an empty built-in tool set, strict empty MCP configuration and explicit settings-source exclusion. The only permitted CLI structured-output tool is `StructuredOutput`. There is no model or authentication fallback.

Children receive an allowlisted host environment, one selected provider's key when requested, and explicit staged context. They never inherit application database credentials, private runner channels, inventory credentials, alternate API endpoints, provider OAuth environment tokens or proxy settings. Native host administration and provider-managed policy remain trusted deployment boundaries; they have not been qualified through live inference here.

## Evidence and outcomes

The coordinator verifies retained input/command authority and command media pins before materializing evidence. Native requests contain retained notes and up to eight exact authorized JPEG/PNG/WebP image versions with a combined eight MiB limit. Hashes and byte sizes are verified after owning media reads. PDF originals and unsupported or over-budget versions are explicitly listed as unavailable. The agent must ask the operator when available evidence is insufficient; it cannot cite unavailable content. PDF page rendering into native requests and external semantic broker tools are follow-up work. Input/4 retains the earlier captured subject vocabulary: explicit new-Part create choices are refused, and versioned Review instructions are not yet consumed. Retained human notes and application question answers supply operator context in this profile.

Structured results contain exactly one proposal or one human question. Shared contracts validate shapes; the adapter additionally restricts citations to evidence actually delivered, and Processing validates subject/provenance/currentness before accepting an envelope. Suggestions never select human values or grant apply authority. Stage names grant no additional tools. This profile has no shell, filesystem, web, arbitrary MCP, inventory-write or approval tools.

## Supervision and recovery

The web process only registers settings/history routes and queues Processing commands. It never launches a CLI or starts inference on page load or settings save. A separately started worker delivers the existing durable outbox to the pinned DBOS queue, with bounded concurrency and no inference retry. A per-actor PostgreSQL advisory lock prevents duplicate native supervisors.

Streams have bounded frames, total output, stderr, runtime and process-group reap deadlines. Cancellation, supersession and shutdown abort the active adapter. The child group is terminated, escalated when needed and confirmed absent before a terminal envelope can release the lane. An unconfirmed reap keeps the lane occupied.

A worker restart refuses an occupied lane and never revives a native session or permission callback. The lane's holders record no child, so its startup check (see [held capacity](#held-capacity-at-startup)) always keeps it. After an abrupt supervisor/host failure, inspect the retained session and confirm termination of its original process tree before using the existing explicit Processing interruption maintenance seam. This first version deliberately provides no browser button that asserts physical termination. A server restart alone cannot prove a billable call stopped.

## Configuration

Provision a separate runner role with `grantProcessing(..., 'runner')`, and a scheduler role on the owned local PostgreSQL database. Apply reviewed migrations explicitly. The API role receives settings write/session insert access; the runner can read settings and update only session progress metadata. Neither role can rewrite a sealed native selection.

Set the following on the separate worker; do not load the original inventory environment file:

- `INTAKE_PROCESSING_PROFILE=native-agent/1` on both web and worker.
- Matching actor, target, target-context and Processing channel-secret configuration.
- `INTAKE_AGENT_DATABASE_URL` and `INTAKE_AGENT_SCHEDULER_DATABASE_URL`, both explicit local databases.
- `INTAKE_AGENT_WRITER_DATABASE_URL` (session worker, optional): an `agent_writer` login for the Examine lead session's lot-forming tools. Without it those tools refuse with `tool_not_allowed`.
- `INTAKE_AGENT_STATE_ROOT`, an absolute, private directory owned by the worker user. Session directories are retained.
- Optional `INTAKE_CODEX_EXECUTABLE` and `INTAKE_CLAUDE_EXECUTABLE`; defaults are `codex` and `claude` on the worker PATH.
- Optional `INTAKE_BLOB_ROOT` for authorized image content; absent storage is explicitly unavailable evidence.
- `OPENAI_API_KEY` or `ANTHROPIC_API_KEY` only for the selected API-key route. API-key variables are omitted from subscription child environments.

For Codex subscription, create the private `codex` directory beneath the state root and run `CODEX_HOME="$INTAKE_AGENT_STATE_ROOT/codex" codex login` as the worker user. Keep that dedicated home free of configuration, hooks, plugins and skills; preflight refuses them. For Claude subscription, use `claude auth login` as the host worker user. Never export or copy subscription tokens.

Start the worker with `pnpm --filter @invimport/intake-server agents:run`, then save a provider/authentication/model default in Agent settings. Start work explicitly from a batch's Processing controls. Keep worker and web supervision separate. Stopping either process is not an inventory rollback.

## Qualification

Official protocol documentation and offline CLI help/schema were inspected for Codex 0.166.0 and Claude Code 2.1.316. Controlled executable tests cover API-key/subscription branches, malformed and oversized frames, tool refusal and a child that ignores SIGTERM. Real PostgreSQL/process checks cover queue-time selection, grants, history, duplicate supervisor fencing and end-to-end DBOS delivery to a deterministic CLI. These are implementation checks only. Actual provider calls remain prohibited in this development session, so live login, entitlement, structured-output compatibility and host containment remain unverified.

## Resumable sessions (`native-agent/2`, `synthetic-session/1`)

The session profiles run long-lived, resumable sessions instead of one structured turn. They share handler `processing/5`, input `bench-intake-input/6` and command `/5`. Each seals its own tool profile: `shared-vm-agent/3` has `native-session-web-tools/1`, the rest `native-session-tools/1`. `synthetic-session/1` is the deterministic fixture twin and calls the same tools. Both stay `native_unverified` or `fixture_only`; nothing here qualifies real provider behaviour.

- **Tool server** (`tools/server.ts`): one MCP endpoint per worker on `127.0.0.1` with an ephemeral port and the SDK's localhost `Host` guard. Each provider run gets a fresh 256-bit capability; only its SHA-256 is stored, and it resolves only for a running session. Tools are `status`, `propose`, `ask`, `reply`, `fetch_evidence` and `read_inbox`; admission compares these names only, never their schemas, so `ask`'s figures needed no new tool profile; every response carries `pending_inbox`. The web process never hosts it.
- **Outbox and inbox** (`tools/outbox.ts`, `tools/inbox.ts`): outbox items are append-only with gap-free sequences per session. A `photo_view` item (migration `0036`) records each image `fetch_evidence` prepared for its response: evidence, version, page, any region, and the delivered size, media type and SHA-256, never the bytes. Inbox items (answers, chat, new evidence, revisions) belong to the session lineage, which is the Processing job. Delivery is at least once: `read_inbox` acknowledges up to its cursor and returns the next unacknowledged items with stable IDs.
- **History read** (`tools/history.ts`, `tools/history-entries.ts`): `GET /api/v1/batches/:id/processing/:jobId/history` returns a job's inbox and outbox rows as resolved entries, newest first, in pages of 200 with one opaque `before` cursor and no forward read. Rows have one total order (creation time, then stream, attempt and sequence), so equal times and the sequences each attempt restarts page without gaps or duplicates. The page, its cursor and the session metadata come from one repeatable-read transaction. The read is scoped by any session attempt of the job in the caller's account. The metadata lists every attempt, however many, with its number, state, queue time, its end from its latest transition by retained order while that is into its current terminal state, why it started where that is known (the first attempt, or a retry after a failed or interrupted one), where it ran, its sealed selection and web setting, and its failure, plus the inbox acknowledgement cursor. Each entry has a one-line summary, typed details and links, and `who`: the agent for outbox items, the operator for answers, chat and relayed instructions, and the app for evidence and revision notices; inbox entries say whether the session has read them. Resolution reads each kind once per page from the same snapshot, never once per entry: observations and lots show their current values, a proposal its retained value and one link to each source it cites at the top or on a catalogue value (notes included), currentness and the open questions making it provisional (`proposalCurrentnessFacts` in `processing/read.ts`, the predicate the Processing read uses), and each web page cited by a `/6` proposal becomes a `web_read` entry beside the first proposal of its attempt that cites it. A retired lot or removed photo becomes a `gone` link and the entry keeps its details. A lot entry shows the reason for keeping the lot separate that its `propose_lot` call gave, and says it is not retained when the call gave none. A photo view reads as an image prepared for the agent, not one it saw. It is the only session history read: the earlier `/session` timeline response is removed, and the drawer and the session page read this.
- **Batch activity read** (`tools/activity.ts`): `GET /api/v1/batches/:id/processing/activity` returns the newest recorded actions across every job of the batch whose history the history route would serve (observations, lots, regroups, proposals and questions from the outbox, and answers from the inbox), newest first in the history's total order with the job between stream and attempt, at most 20 (`limit`, default 6). It doesn't read the Agents list, so a session off its first page or filter still shows. Rows are resolved by the history's resolver in one pass, one query per kind, from one repeatable-read snapshot scoped to the caller's account; the resolver takes several jobs with their inbox cursors, and the history read is its one-job case. Status lines are not entries: each entry carries its job's current attempt's latest status line as `agent_note`, or null while that attempt has none, as after a Start fresh. Web reads, which a history places beside their proposal, are left out.
- **Photo-view crops** (`media/content.ts`, `media/routes.ts`): `GET /api/v1/batches/:batchId/processing/sessions/:jobId/photo-views/:attemptId/:seq/crop` recuts a recorded view from its page preview through `media/region-crops.ts` and resizes it to the delivered size, as PNG. The delivered image was encoded once more, so this is a reconstruction. It has the history's scope, and it is not found for a removed version or another job's view; a region whose page was re-rendered at another size is refused.
- **Regroup moves:** `regroup` in `capture/evidence-observations.ts` returns each move with its source lot and whether it applied or was only suggested, or was unchanged because the observation was already there (no suggestion is written then, even on an edited lot), and the outbox item records them as `moves` beside the destination `lot_ids`, which older items keep alone. `propose_lot` records on its item whether it formed the lot, extended it, only suggested for it or changed nothing, judged from what it applied and the suggestions it wrote, and any `separation_reason` the session gave. `read_inbox` publishes `session_changed` in its transaction when it moves the acknowledgement cursor, so an open history shows what the session has read.
- **Adapters** (`session/session-adapters.ts`, `session/session-admission.ts`): `/2` admits Codex 0.166.0 and Claude 2.1.319 under the maintained offline policy. Codex uses strict parsing, disabled code mode and skill instructions, read-only/never policy and per-turn effective-configuration/MCP checks before turn/start. Claude verifies its executable version before starting, disables built-in tools and slash commands, disallows advisor, supplies strict MCP configuration and empty setting sources, and uses pre-input control initialize/mcp_status to verify effective configuration, the exact built-in agent set and the connected tool inventory before sending user text. Its later init check additionally verifies empty skills/commands/additional directories, default permission/output mode and the exact qualified built-in plugin set. Subscription sessions also report the built-in `web-fetch` agent and `cc-plugin-telemetry` plugin; both are admitted for 2.1.319 only, and any other agent or plugin is refused. API-key Claude additionally uses bare mode. Both retain runtime tool refusal and child reap ordering. The offline policy does not attest the tool surface of every actual subscription request. Live Codex subscription turns were observed receiving code-mode tools despite the disabled configuration, and the runtime guard cannot see code run inside `exec`, so Codex is not confined there; the profile remains native_unverified.
- **Conversation provenance:** a private marker in the per-job session directory binds the admission policy to provider, authentication and conversation ID. A missing marker refuses resume without consuming pending input. The revision-checked Processing replacement command starts a fresh attempt on the same lineage only on explicit operator action, refuses a held agent slot, and preserves inbox/cursor, history, accepted effects and the prior sealed identity pins. Stale identity pins refuse replacement and remain subject to claim-time checks. Losing local provenance requires replacement rather than an inferred upgrade.
- **Lock order:** capture (when publishing), then job and attempt, then the session row, for tool calls, claims, settlement, answers and interruption. Each tool call checks its capability and the running attempt again under those locks.
- **Cancellation:** Processing owns it. The runner aborts a turn when its attempt leaves `running`; a cancelled or superseded attempt is never revived, and the session settles `cancelled` once its child is reaped.
- **State machine** (`session/session-runner.ts`): a guarded claim moves a session from `queued` to `running` with a slot; settlement revokes the capability, frees the slot and moves it to `queued` (more inbox items), `waiting_input` (an open question) or `finished`, or to a typed failure state. No turn is continued silently: after an abrupt stop, a running session still holds its slot until the next start confirms its turn gone and releases it (see [held capacity](#held-capacity-at-startup)); that start then marks such sessions `interrupted`.
- **Slots** (`session/slots.ts`): a configurable limit (1–8, default 3) from Agent settings. Claims are serialized per actor, a `/1` lane holder counts as one slot, and queued sessions start oldest first, with Examine lead sessions ahead of per-lot ones. No session waits behind a queued Inventory, which may be held at its gate without a slot. Waiting and finished sessions hold no slot. A held slot also records its turn and what that turn started outside the worker (migration `0039`): `none` from the claim, then `host` before the native driver starts a provider process, or `vm` with the exact command just before the VM driver sends it (`recordChild` on the driver context). Each record is committed before its effect and cleared with the slot.
- **Evidence images**: by default `fetchEvidenceImage` cuts images from the version’s decoded page preview. Tool-capable VM sessions with `INTAKE_VM_EVIDENCE_IMAGE=original` deliver authorized whole JPEG or PNG version bytes within the existing run budget. Regions and PDF pages always use previews. A whole page is bounded to `AGENT_IMAGE_LONG_EDGE` (2,576 px), or to the lead session's 768 px overview; a region is cut from the full preview through `media/region-crops.ts`, then bounded. Each bounded preview is at most `AGENT_IMAGE_MAX_BYTES` (1.25 MiB), so its base64 fits the smallest relay frame: an unscaled image or the overview is PNG when that fits, otherwise JPEG at falling quality, and an image that fits at no quality comes back as metadata only. After encoding, the image's bytes are reserved from the run's budget, then a final transaction takes the batch row shared and the job, attempt and session rows, checks removal and the running session again, appends the `photo_view` and publishes `session_changed`. A refusal or a rollback before `COMMIT` releases the reservation and returns no image. A `COMMIT` whose outcome is unknown keeps the reservation, returns no image and answers `outcome_uncertain`; its view may exist for the withheld image. A view means the image was prepared for the response, not that the provider read it. The result's `delivered` gives the image's page, size, scale, region, media type and SHA-256. A version with no preview is refused. A lot session may cite a version it fetched. Lot sessions may rely on their own lot's `observation_set` and active `evidence_observation` sources; the lead session on any of its batch's.
- **Questions** (`ask`, `processing/session-answers.ts`):
  - **Shape:** `ask` takes one `bench-intake-question/2` question: its subject, reason, affected fields, an optional title and 1–4 steps. Each step has a prompt (500 characters), the assumption the session keeps working on and an answer kind: a choice of 2–6 options (stable slug IDs, labels of 80 characters, optional details of 160, and whether "Something else" is allowed), a number or text. Prompts, assumptions, titles and option labels need a visible character, so text of only spaces, control or format characters and combining marks is refused.
  - **Ask refusals:** the handler refuses text PostgreSQL can't store (NUL or an unpaired surrogate), naming its path; repeated step or option IDs; more than one number step; and a number step whose question is not about one live lot or doesn't list `quantity`, naming the step. A subject outside the session is refused at `/subject_id`, naming any number step. Any sealed envelope over the 32,768-byte `processing_message` limit is refused too, so a proposal with long text is caught the same way.
  - **Guidance and compatibility:** the tool description and the opening instructions both carry the one-question guidance (`tools/ask-guidance.ts`). Retained `/1` questions stay readable and answerable through `bench-intake-answer/1`, and an earlier runner question refuses a `/2` answer.
  - **Answer effects:** a `bench-intake-answer/2` answer gives one value per step; a number step may be answered in words instead. In one transaction under one capture lock it sets the lot's quantity for a number, then adds one note of "prompt — answer" lines for the other steps, records the answer and appends one `answer` inbox item. The note keeps one line per step, with any line break inside a prompt or answer turned into a space; the inbox item carries each step's value as written, a picked option's ID and label and a number's basis. Relying sessions are told as for any answer.
  - **Answer refusals:** the note must fit the capture note limit, and the inbox payload 32,768 bytes as PostgreSQL's jsonb text measures it. Either overrun, text PostgreSQL can't store, a wrong kind, an unknown option or a missing step (an empty answer included) is refused as `invalid_answer` before any edit, naming the step where there is one.
  - **Reads:** the Processing read sends each question once in its version's shape. Every question carries `subject_id`; session questions also carry `fields`, which an earlier runner question doesn't have. The contracts' `questionView` gives every reader one normalised view of either version. A `/2` question with one step is labelled by its prompt; one with several steps by its title, or by its first prompt when it has no title. A `/1` or runner question is labelled by its prompt and reads as one number or text step, with no assumption for a runner question.
  - **Answered questions:** every question carries `session_history`, whether the history route would serve its job now (`processing/session-history-job.ts`, the route's own job check; an `agent_session` row with no state, as the earlier native runner writes, doesn't count). An answered question carries `answer` (`processing/answered-questions.ts`, `answer-summary.ts`): its `answer_id`, `answered_at`, each step's prompt and value text (an option's label, "Something else" in the operator's words, a number as `186 · counted`, or the words; a `/1` or runner answer is one value with a null `step_id`), each cut at 200 code points and further until the member's canonical JSON is at most 1 KiB (`MAX_ANSWER_SUMMARY_BYTES`), and the same capture effects the history's answer entry gives. A session answer also carries `delivery`: `waiting` while its inbox item (`answer:<question>`) is above the lineage's cursor, otherwise `read` with the time of the logged advance that first passed it.
  - **Acknowledgement log:** migration `0037` adds append-only `agent_session_ack`, one `(from_seq, to_seq]` row per cursor advance, written in the advance's transaction by `acknowledgeSessionInbox` for both `read_inbox` and a steered turn's settlement, each of which publishes `session_changed`. Cursors acknowledged before the log got one baseline row with no time, so an answer they passed reads `read` with no time after later advances.
  - **Size tiers:** the read first measures the snapshot without any `answer` member and fails with `processing_capacity` if that is over the limit; then, newest answer first, it adds the full member while it fits, else `{answered_at, values_omitted: true, delivery?}`, else nothing, and never steps back up, so no newer answer shows less than an older one; it measures each member's exact serialized bytes. `ask` reserves `MAX_ANSWER_SUMMARY_BYTES` per question in the batch's result budget, so a batch holds about 70 small questions, where it held more than 100 before.
  - **Figures:** `ask` may carry up to five `figures`, each a view of an evidence page with up to eight marks, a caption and why it is shown (`tools/figures.ts`). A figure's version must pass the same delivery predicate as a proposal's citation (`deliveredSourcePredicate`), and its page must be one this session was given: `deliveredMedia` records each version's pages per attempt, so a Start fresh conversation must fetch a page itself before showing it, and on the VM path the release receipt binds the delivered page with the version, so a page counts only after the guest confirms it. A removed photo, a missing page, a region outside the page's preview or a mark outside the view is refused as a correctable result naming the figure and field. The figures are in the sealed spec, so the envelope and `requireRoom`, which also reserves room per figure in the read, count them. The same transaction records them and queues their view renders (see the [retained media boundary](../../ARCHITECTURE.md#question-figures)).
  - **Previews:** `ask` with `preview: true` validates, queues marked preview renders (refused as `preview_busy` beyond 20 unsettled per session), commits without storing a question, and waits up to `FIGURE_PREVIEW_WAIT_MS` (20 s) for them. It returns the marked pictures as images within the run's image budget and `FIGURE_PREVIEW_MAX_BYTES` together, or `preview_not_ready` with none; a state read after the wait doesn't count, and a preview swept while waiting returns `media_evidence_removed`. On the `shared-vm-agent/3` path an `ask` preview gets the evidence frame limit (`evidence-request.ts`), and the guest stages its images as files or inline (`stagePreview`) without a release, so a preview never grants a citation. The `shared-vm-agent/1` relay has no larger frame, so a preview there is refused before anything renders.
  - **Replacing a question:** `ask` may name `replaces`, an earlier question of the same job that is neither answered nor already replaced (otherwise a correctable `validation_failed` at `/replaces`). The same transaction records the pair in `processing_question_replacement` (migration `0037`) and supersedes the earlier question, and the read gives it `replaced_by`. The ask guidance says to name the question a new ask replaces.
- **Instructions**: sessions put catalogue values in the proposal's `catalogue` block with sources; the lead session cites each lot's observation set so its identity is stable.
- **Web page sources**: a `/6` proposal may cite a page the agent read, `{kind: 'web_page', url, title?, read_at?}`, in its top-level sources only. The URL must be absolute `http` or `https`, at most 2048 characters, with no credentials. It is not delivered evidence, so the delivery checks skip it, and the app shows it as agent-reported. A `/6` proposal with many long URLs can fit every field limit and still be refused by the sealed envelope limit (see Ask refusals).
- **Worker** (`session/session-worker-main.ts`): a separately supervised process with the same per-actor fence as the `/1` worker: the supervisor lock, then the [held-capacity check](#held-capacity-at-startup), run after its VM bridge starts. On SIGTERM or SIGINT it stops its turns and waits up to 30 s (`SHUTDOWN_TURN_SETTLE_MS`) for them to settle before it closes the provider-status channel, scheduler, bridge, tool server and pools, so a VM turn whose removal the guest confirms in that time releases its slot. Past it, the bridge ends every wait for a proof, the turns get 2 s to record their pending reap, and the slot stays held for the next start. It registers `intakeCommand` and `sessionResume` on `bench-sessions`. A sweep re-queues waiting, finished or interrupted sessions with pending inbox items and makes sure every queued session has a live workflow, oldest first by when each became queued, using workflow IDs keyed by attempt, turn count and a minute bucket; it also settles every idle session (not running or cancelling) whose attempt was cancelled, and queued sessions whose attempt was superseded. Each turn has a 15-minute deadline, after which the child is reaped and the session fails. A workflow waits at most 30 seconds for a slot. A duplicate run is harmless because only one claim can move a queued session to running.

### Held capacity at startup

`held-capacity.ts` runs in both workers once they hold the actor's supervisor lock (`worker.ts`). It reads every held slot and the lane and decides each from the slot's record. A slot is released only when its turn started nothing outside a worker (`none`) or when the paired guest answers `worker_removed` to the existing removal probe (`inspectTerminal` with `requireReap`) for the recorded command (`confirmReaped` in `shared-vm/coordinator.ts`), within 20 s per turn (`STARTUP_REAP_CHECK_MS`). The release is one `UPDATE` clearing what `releaseSessionSlot` clears, only while the slot still holds that exact turn and record, and every read and write of the check runs on the supervisor lock's own connection, so a worker that lost the lock releases nothing. `interruptRunningSessions` then interrupts the session, in both workers.

Everything else is kept, and the worker refuses with `agent_reap_confirmation_required`: a slot of another target or context, a `host` record (no process group is recorded), a slot claimed before turns were recorded, a VM turn with no bridge or no proof, and the lane. Each outcome is logged as `held_capacity_released` or `agent_reap_unconfirmed` with the attempt, slot or lane, and a fixed reason. Nothing is stopped or killed. With `INTAKE_AGENT_RECOVER_ONLY=1` (`pnpm agents:reap`) a worker runs only this check and exits.

## The Agents read

`GET /api/v1/agent-sessions` (`session/sessions.ts`) lists one row per session, which is a Processing job: its newest session attempt, with its earlier attempts folded under it (newest first, at most 20, each with its end and failure) and their count. Rows page by job, 50 at a time, ordered by that attempt's queue time, with an opaque cursor. One repeatable-read, read-only transaction gives the page, the counts and the summaries.

- **Filters** apply in SQL before paging, to the row attempt's state: Needs attention is failed, interrupted (which includes a session that can't resume), waiting for sign-in or waiting for an answer; Working is running; Waiting is waiting for an answer; Queued is queued or waiting for capacity; Done today is an ended attempt whose latest transition, which is into its current state, falls within the browser's day bounds (`day_start`, `day_end`), never `finished_at`. Every filter except All leaves archived batches out.
- **Counts** give every chip's count across the scope by the same rules; Done today only with day bounds. **Totals** ignore the filter, the page and archiving: attempts holding a slot or the lane (a cancelled attempt still holding one counts only here), and queued and waiting sessions.
- **Batches** summarise every batch in scope, newest activity first and at most 200, with its session count, how many match the filter and its first start, the earliest transition of any of its attempts into running. An optional `batch_id` narrows rows, counts, totals and summaries to one batch, which Processing's session list reads under All.
- **Start fresh eligibility** comes from `processing/start-fresh-eligibility.ts` on each row, on the history metadata and on each session job of the batch's Processing read.

## Pausing a batch's sessions

`pause.ts` keeps a paused batch as a row in `agent_batch_pause` (migration `0029`), set and cleared by `PUT /api/v1/batches/:id/agents/pause` and, for every live batch of the account at once, `PUT /api/v1/agents/pause`. Both lock the batch row for update, which orders them against a turn's claim: the claim holds that row shared, then finds the pause and leaves the session queued. While paused, a queued session claims no slot and holds no place in the slot queue, and the wake sweep neither resumes a waiting or finished session with unread inbox items nor wakes a queued one. A turn already running finishes its turn. Nothing is cancelled: queued sessions, answers and chat stay as they are, a worker restart reads the same row, and after Resume the next wake delivers what waited. The session list marks each session of a paused batch and lists the account's paused batches.

## Batch instructions reach the sessions

`instructions.ts` serves `POST /api/v1/batches/:id/agents/instructions`, which Processing calls after an instruction is saved, so a failed delivery never undoes the save and can be retried; the instructions route also tries it once after each save, best effort, so Capture's autosaved instructions reach the agents too. It appends each of the batch's current instructions (the whole batch's and each evidence group's latest version) to the inbox of every job's current session that is not over, as an `instruction` item keyed by the instruction's id, so delivering again adds nothing. A session created later gets the same items in the transaction that creates its job (`instructNewSession`, called when a job is started or restarted, when the Examine trigger creates the lead job and when a session is replaced), so instructions saved before Examine starts, or before a successor session, still reach it. A restarted or replaced attempt keeps the lineage's read cursor but starts a new conversation, so its copies are keyed by the attempt as well and arrive unread. The item is a system relay with no actor, because the runner and writer roles that start sessions cannot write `actor_id`; migration `0030` adds the kind and a trigger that refuses any instruction item whose id, text and group do not match a saved instruction of the job's batch. The session supervisor also relays any live session's missing latest instructions on every pass (`deliverMissingInstructions`), so an instruction saved while delivery failed still arrives; it share-locks the batches in id order before reading their latest instructions, so a save in progress is waited for and Pause all, which locks in the same order, cannot deadlock with it. A running session reads it as it works and a queued one when it starts; a waiting, finished or interrupted one has an unread item, so the wake sweep resumes it to apply it.

## Correctable tool results and citation references

Tool contract failures retain validation_failed and include bounded copied Ajv issues with schema-owned JSON Pointer paths, stable rules and fixed reasons; submitted values and unknown field names are excluded. Existing contracts validate callers retain their error behavior. Validation refusals publish no result and permit a corrected call under the same authority checks.

Successful fetch_evidence byte delivery includes the complete media-version source reference accepted by proposal validation. Its digest identifies the retained original version; the delivered image has its own digest in `delivered`, which the guest checks before staging it. Metadata-only responses, exhausted budgets and failed/revoked reads carry no source or delivery grant. A worker restart still requires refetching; knowing a digest does not grant access.

### Retained failure diagnostics

Session failures use typed application codes to construct a bounded diagnostic before persistence. The immutable `agent_session_failure` table associates each record with an exact attempt and turn; the API role can read, and only the runner can insert. Settlement uses a savepoint so a rejected diagnostic write cannot suppress the original failure or prevent capacity release after confirmed reap. Unconfirmed reap retains its slot. Worker recovery records interruption without inventing provider metadata.

Session lists and the history read's attempt headers expose each turn's category, summary, detail availability and recovery, when it failed, the attempt's last status line (however old), and a `cause` built only from the allowlists (`failures.ts`): the innermost code that says more than that the turn failed (`agent_turn_failed` and `agent_unknown` don't, nor does a code older than the contracts' `SESSION_FAILURE_CODES`) and the provider's error kind, result type and HTTP status. A failure with neither has no cause, which the app shows as not recorded. The contracts' `failureCauseText` turns a cause into one sentence. The details endpoint checks the retained command's actor, target and target context. Legacy records have unavailable details. Causes are bounded to four and the stored object to 16 KiB; raw exception messages, stacks, stderr, prompts, capability values, SQL and private paths are never serialized. A persistence failure emits only a correlation ID and a fixed operational event name.

### Shared VM session driver

The opt-in `shared-vm-agent/1` profile seals the provider, authentication route and model in a v6 input. The session coordinator owns the queue, slot and MCP capability. Its VM driver accepts a guest-initiated TLS 1.3 connection on loopback with a dedicated pairing CA and a verified peer identity. The one-turn guest container runs on its own VM Docker engine. The relay transports TLS bytes over Lima stdio. Only session files and the guest pairing identity are mounted, both from the guest filesystem.

The provider gets a per-turn loopback MCP proxy in the guest. The coordinator fixes its destination to the host session tool service and attaches the attempt capability. Each host operation revalidates its scope. Native adapters retain their current restricted tool policy. A lost transport after dispatch reports an uncertain reap and retains the slot. Closing the bridge ends any wait for a removal proof. Completed guest journals prevent a duplicate execution of identical command bytes. Automatic reconciliation of an uncertain launch, larger evidence transfers, public egress and managed subscriptions are open parts of the OpenSpec change.

The personal Claude subscription relay advertises its route during the paired TLS handshake. The coordinator selects it only for sealed shared-VM Claude subscription turns. The guest reads the current credential on launch, injects it into the Claude process and uses a loopback proxy backed by the guest Anthropic-only egress socket. A separate guest management service owns the revision-checked private store. Intake HTTP, DBOS and application backup jobs never handle this credential. See the [deployment guide](../../../tooling/deployment/README.md#personal-claude-subscription).

The Codex management container drives the pinned app-server's account RPCs. Pending sign-ins use a staging directory in private guest storage. Only a matching successful completion followed by a ChatGPT account read can promote that directory. Sign-in and logout use an exclusive guest filesystem lock, while Codex subscription turns take shared locks. These turns receive the managed Codex home and a provider-specific outbound proxy. The general relay and Claude relay have neither mount.

### Read-only provider status

`GET /api/v1/agents/provider-status` (`provider-status.ts`) reports each VM provider's sign-in status without the management key: Claude's token saved, with its save time where recorded, or not; Codex signed in, signing in or signed out; or unknown with a reason (`ProviderStatus` in the contracts). Each known state carries `checked_at`, when the guest established it, and Codex's says whether a newer check is running (`refreshing`). Unknown is never signed out. The answer carries no token, account, key or credential revision, so nothing can be saved with it; saving still needs the protected management read. `?refresh=true` is Check again: it skips the API's reused read and asks Codex for a fresh check.

- **Guest:** each credential process (`credential-main.ts`) also serves a status-only endpoint (`provider-status.ts`, `credential-status.ts`) on a Unix socket in its container's private `/tmp`. It offers one read and no action. Claude's read opens the token store read-only; the save time comes from `credential_meta`, written in the same transaction as each change, and is shown only while its revision is the store's current one, so a change made by an older image shows no time. Codex's read (`CodexAccount.readStatus`) answers at once: a pending login from memory, even an expired one; signed out when there is no account directory; `busy` during a sign-in change; and otherwise the last completed check, with its age, since one `account/read` takes longer than a request may wait. A check runs `account/read` without a refresh under the shared lock turns take, apart from any request: one at a time, started by a read when there is no result, the last check ended over 60 s ago, or Check again asks (at most once per 5 s), and stopped, its account process killed and reaped, after 10 s; ages and intervals use the monotonic clock. While no check has succeeded and one is running, it answers `checking`. A failed check keeps the previous result and its age; with none, it answers `timeout` (its process confirmed gone) or `unavailable` and is retried after 5 s. A check whose process isn't confirmed reaped starts no further check. A sign-in change stops a running check, rather than waiting for it, and forgets the last result, so the next read checks again at once; an operator status action without a pending login changes nothing and leaves the check running. A read that ends before its directory lookup does starts no check. The guest gives each read at most 1.5 s, or less when the coordinator's request says so, and keeps 0.5 s of it for an abandoned read to stop: it answers `timeout` only once that cleanup (such as reaping the Codex account process) is confirmed, closes the connection unanswered when it isn't, and starts no read when the budget leaves no room for cleanup. It also stops its work when the connection closes; a Codex check is not that work and keeps running. The guest dates a Codex answer by its age (`age_ms`), so the coordinator dates it on its own clock; an older guest's answer has no age and counts as read just now, and a request carrying `refresh` closes an older guest's connection, which then reads `service_unavailable`.
- **Transport:** each subscription relay keeps one status connection from that socket to the coordinator through `docker exec`, carrying opaque bytes. The credential process is the TLS client with the guest pairing identity, so only the paired coordinator can ask; the browser-facing management listener has no status path. The coordinator (`coordinator.ts`) keeps status connections apart from turn connections by their greeting (`bench-provider-status/1`), admits up to two of them per provider besides the eight turn connections, reads both providers in parallel within 1.8 s each, or the caller's shorter budget, sends `refresh` to Codex only for Check again, waits within its deadline for a status connection another read has borrowed (an absent one gets 0.5 s), and destroys a connection whose read runs out. The relay retries a status connection that fails or doesn't start within 15 s, stopping any pump it gave up on (with SIGKILL when SIGTERM isn't enough), with growing waits and without affecting its turns. With no status connection, a provider reads `vm_unreachable` when nothing paired is connected, `guest_outdated` when its turn guest greets without the status capability, and otherwise `service_unavailable`.
- **API to worker:** the API and the session worker share only the database and the Processing channel secret, so `provider-status-channel.ts` sends the request and its reply as PostgreSQL notifications, each with an HMAC over its scope and request ID. Every database role can see notifications, so the reply carries only display states: Claude's revision stays with the worker. The worker remembers each accepted request ID until it expires, so a replay is answered at most once, and accepts at most 64 live requests. It passes what is left of a request's budget to the coordinator's read, and drops a reply, closing its connection, when the request expires first; shutdown waits for replies in flight. It listens on a connection from its own pool, which its role's connection limit leaves no room to add to; the API's 2 s covers taking a connection, the queries, the reply and cleanup, after which it reports `worker_unavailable` and closes a connection it isn't sure of. It reuses a read for 5 s by the monotonic clock, but never one whose Codex check hasn't finished, so a client waiting for that check reads the worker each time; Check again neither reuses one nor joins one in flight, at the API, the worker or the coordinator, since that read may predate a sign-in change. A profile without agent sessions reads `not_configured`.
- **Last-session line:** `sign-in-failures.ts` finds each provider's latest queued sessions in the scope, in either sign-in mode, and shows the line only when every one of them used the subscription and its current turn's retained provider error is Claude's `authentication_failed`, Codex's `unauthorized` or HTTP 401. A missing token, missing credentials or an unreachable guest don't count.

### Native tools in the shared VM

The sealed `shared-vm-agent/3` profile selects a tool-capable paired supervisor and a separate provider container inside the same guest kernel. No worker runs `shared-vm-agent/2` any more: whichever session worker finds a retained `/2` attempt fails it with `agent_profile_retired` instead of running it. The coordinator matches both the provider route and the tool profile during dispatch. The supervisor owns the TLS identity and turn journal. A per-turn Unix socket carries the opening and scoped application tool requests into the worker; the coordinator supplies the MCP URL and attempt capability. Disconnect closes the worker transport and the guest launcher removes the turn containers.

The worker has loopback networking, a read-only root, no Linux capabilities, and guest-only workspace, selected provider and egress mounts. The single operator trusts sessions sharing this workspace and the selected provider account. Shell access inside a worker includes that account's process and mounted state. The app database, operator key, pairing identity and container engine are outside its mount namespace. The provider, `curl` and `WebFetch` reach the network only through the turn's egress proxy, which applies the turn's sealed web policy and protected hosts. See the deployment README for network policy and qualification.

### VM evidence representation

The development launcher and standalone relay pass `INTAKE_VM_EVIDENCE_DELIVERY` (`file` by default, or `inline`) into tool-capable guest workers. `stage-evidence.ts` owns verification, the private file and the returned representation. File mode omits the image block and tells the provider to open `local_file.path`, fetch again on later turns, and cite the source metadata. `native-turn.ts` owns cleanup when the turn ends. Authorization, rendition budgets and photo-view recording remain in the coordinator's tool path. The paired guest acknowledges a coordinator-issued, turn-scoped receipt after writing the response. Only that acknowledgement grants a fetched citation to a tool-capable VM session. Deploy the coordinator, supervisor and tool worker together.
