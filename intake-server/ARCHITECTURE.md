# Implemented intake application

T01 adds the Fastify/TypeScript foundation and `contracts`; T02 connects the React browser to retained manual capture. Merged T03 adds a separately supervised fake-only stock executor. T04 connects exact manual review, frozen preparation, approval, explicit dispatch and truthful results. No component calls Python, and capture alone grants no inventory-write authorization. [The approved implementation plan](../docs/bench-intake/08-implementation-plan.md) remains authoritative for later work; [T01](../docs/handovers/bench-intake-T01.md) and [T02](../docs/handovers/bench-intake-T02.md) handovers distinguish observations from fixtures.

## Public boundaries and process ownership

`api/server.ts` constructs an API without connections or workers. `main.ts` is the explicit loopback web entry point with signal-driven close, optional explicitly configured capture DB/read target and built same-origin static frontend. `registerCapture`, `registerManual`, `registerProcessing` and optional retained-media registration are explicit additive seams; constructing the base server still installs only health/bootstrap. The strict parser validates UTF-8, depth/size, duplicate decoded keys (including equal duplicate values), finite/safe numbers and ordinary JSON syntax before object parsing. AJV Draft 2020-12 performs no coercion/default injection/stripping. Complete outputs are validated before serialization, so an accidental private field fails instead of being silently exposed. Safe error DTOs suppress original messages/bodies. Host/Origin and CSRF checks are independent of domain authorization; they cannot grant mutation capability or substitute for T11 identity/access qualification.

`config.ts` accepts explicit injected settings and stable development actor/target/context IDs. Ordinary runtime libraries do not discover `.env`, log a key, fall back to username/password, contact inventory or launch a process on import. Explicit development launchers parse their selected server-side env file before invoking these runtime boundaries; direct starts and tests have no implicit dotenv discovery. The key is not a verified user identity. Web bootstrap does not claim target capability/permission verification. The protected root `.env` is outside T01's runtime configuration and was not read. Actual configuration-file/credential resolution and trusted actor/target persistence must be added with consuming features, not inferred from a successful health response.

## Manual capture boundary

`capture/routes.ts` installs GET list/read and POST create/edit/observation endpoints under `/api/v1/batches`. All lookups bind server-configured development actor plus fixed target/context. Commands require CSRF/Origin and payload-bound UUID idempotency; no browser-selected actor, origin, credential or raw inventory action exists. `capture/repository.ts` uses caller-owned transactions, batch row locks and expected revision comparisons (412, never silent overwrite). Read snapshots and stream cursors share a repeatable-read transaction. Observation creation is independent from explicit human selection and does not change field selections.

`migrations/0002_capture.sql` adds source, batch, typed subject/Part/lot, immutable human note, observation, selection and exact canonical command-history tables without changing 0001. Every physical lot retains its original source/contribution identity. Composite same-batch FKs and a deferred typed-extension constraint prevent cross-batch/type ownership. Notes/selections/observations/revisions are append-only through triggers and restricted capture grants; explicit selection commands retain old values and Part-link edits in original command bytes plus digest. No stock record or execution ownership is created by capture. Archive is reversible, not deletion or identity replacement.

The public snapshot keeps exact quantity/PK/revision strings and unset/unknown/clear/inherit/set modes. Omitted edit fields insert no selection revision; defaults cannot inherit themselves. Explicit choices/unknowns/clears survive default changes; inherited fields materialize in the browser projection without rewriting original selections. Capture currently bounds 100 subjects, 100 read observations and 240 KiB complete snapshots; excess edits roll back rather than retain an unreadable batch. Lists return at most the most recent 100 with explicit truncation; old direct URLs remain resumable. Large-batch pagination/bulk/restructuring belongs to later work.

`capture/read.ts` accepts only the existing transport's semantic read closure, never a write closure. It verifies returned PK/name, strict bounded JSON, 64 KiB and five-second total body deadline; denied/malformed/timeout is unavailable, not absent. Authorization precedes network traffic. `scripts/capture-setup.cjs` explicitly provisions development attribution/grants only in an allocated DB with trusted configuration; startup never migrates/provisions. T02 uses randomized owned test DBs/restricted roles, not shared `intake_dev` or real inventory. Merged T03's independent migration 0003/executor does not depend on capture SQL; T04 consumes the capture-owned `captureInTransaction` and executor-owned source/history/reservation seams; consumers do not query sibling catalogue SQL.

`inventory/transport.ts` is a target/context-bound transport guard, **not** approval/request-intent authority. Semantic reads are `get_part(pk)`, `get_location(pk)` and executor known-output `get_stock(pk)`; raw URLs/actions are not accepted. Writes require an explicit owned-disposable profile, a nonempty protected-host deny set and a literal loopback HTTP origin. DNS names, public/LAN origins, binding changes, protected aliases and redirected requests cannot pass. The protected loopback spelling/IPv6/localhost group is conservatively denied across ports. Literal-loopback writes prevent public DNS rebinding; there is no general configurable remote-write route. NodeHTTP makes at most one request with a five-second header/connection deadline and no retry/redirect algorithm. T03 replaced native Fetch after a controlled HTTP421 test observed it repeating POST. T02 bounds read bodies; T03 retains stock intents/results and interprets supported output receipts. The only list reads are `list_locations` and `list_supplier_companies`: fixed paths, an always-present `limit` (1–100), an offset of at most 10,000, `ordering=name`, an optional bounded `search` and a caller timeout that may only shorten the 5-second request deadline. No arbitrary request API exists. The apply process alone may receive a writable closure after it has independently authorized and committed its exact request intent; API/research must not receive one. Tests configure controlled endpoints as protected and prove zero forbidden sends; none target real inventory.

Protected-host classification uses WHATWG URL's validated canonical hostname, removes the terminal DNS dot and conservatively groups `localhost`, IPv4 127/8, IPv6 `::1` and IPv4-mapped IPv6 127/8 across ports. Mapped dotted/expanded forms normalize to IPv6 hex before classification. This does not resolve DNS or expand writable destinations: only HTTP `127.0.0.1` / `[::1]` remain eligible, and any protected loopback group denies both. Nearby non-loopback 126/128 addresses and `localhost.invalid` remain distinct; controlled public-seam tests prove both refusal before adapter/endpoint and allowed disposable positive controls. Independent review found the earlier exact-spelling classifier incomplete; the T01 handover retains the failing-before/passing-after evidence rather than claiming the original tests covered these aliases.

## Evidence observations and agent-formed lots

Migration `0019` adds `capture_evidence_observation` (an item seen in one region of one evidence version; unrelated to the inventory-read `capture_observation`) and `capture_lot_evidence_observation` (lot membership, `active` or `suggested`). Lots gain `origin`, `agent_session_id`, `operator_edited`, `estimated_quantity` with its `quantity_basis`, `observation_set_version` and `changed_revision`. `capture_revision` and `capture_subject` record the agent session beside the unchanged operator `actor_id`.

The Examine lead session writes through `capture/evidence-observations.ts` (`record_observation`, `propose_lot`, `regroup`) on its own `agent_writer` role, which inherits nothing from the runner and is granted by `grantAgentWriter`. Those writes lock only the rows they touch: a row changed after the agent's `base_revision`, missing or retired makes the call `stale`, while an unrelated operator edit does not. Rows the operator has edited only receive suggestions. Database guards refuse an agent principal that inserts operator rows or a subject without its session, or flips edit state. They also refuse it when it updates or relinks an edited or operator lot or observation except through a suggested row, renames a subject it did not create or a lot the operator edited (operator Part renames are not tracked, and the application never renames Parts as the agent), records a capture revision without its session or under another actor, or queues a non-`process` command. The role has no selection or note insert, so counted quantities and approvals stay human. Agent principals are the members of `intake_agent_writer_marker`, excluding superusers. Every write advances the batch revision and publishes `capture_changed`.

Operator observation edits (`observation`, `observation_move`, `observation_suggestion`) mark the observation and touched lots edited. So does every operator lot command (lot edits, bulk edits, `move_lots`), and split (per-child `observation_ids`), merge (union of active observations) and retirement mark their predecessor lots. Retired lots count as edited, so observations left on them are only suggested elsewhere. `media/read.ts` adds lots reached through active observations to `linked_subject_ids`. Region crops come from the decoded preview through `media/region-crops.ts` into a private cache outside `BlobStore`. Retained command records, idempotent request and response bytes and snapshot size checks use `canonicalRecord`, which keeps safe integers and is byte-identical to `canonical` for documents without numbers.

## PostgreSQL and exact authority

`migrations/0001_foundation.sql` owns explicit constraints/triggers and is reviewed as SQL, not generated schema push. It implements development operator, target/context, immutable command, outbox, semantic idempotency and UI-stream/event infrastructure. Target/current-context cycles are deferred composite FKs; wrong-target contexts, missing parents and bad digest lengths fail. Retained command/context/idempotency/event authority is append-only through triggers plus runtime grants; migration/DBA DDL remains trusted. Capture is additive in 0002. Merged 0003 adds independently owned executor deployment/source/approval/run/operation/request/result/effect/verification authority; T06 adds separately owned job/attempt/question authority in 0006 and additive media-aware profiles in 0007. Same-batch/wrong-job ownership in T01 tests is a **test-only representative DDL fixture**, not an implementation claim for future job tables.

`db/schema.ts` supplies reviewed Drizzle row declarations and inferred types for the implemented access paths. `pg` retains `bigint`/numeric text by default; Drizzle bigint mode is `bigint`, never JavaScript number. Public DTOs use canonical exact decimal/revision/PK/cursor strings with field-specific bounds. Stock quantity supports 13 integer/6 fractional digits, positive and no exponent/sign/leading zero/trailing fractional zeros; schema validation precedes any numeric insertion. The real-PG numeric fixture proves no boundary-rounded value is inserted. UTF-8 canonical documents sort keys by JavaScript code-unit order, preserve ordered arrays/human text, allow string/boolean/null scalars and reject number/undefined/custom objects. Callers must explicitly sort schema-defined set arrays before canonicalization. Retained bytes plus SHA-256, never JSONB reserialization, remain authority; one cross-language Unicode byte/hash vector is retained under `contracts/vectors`.

`db/database.ts` exposes `queryDatabase(connection)` for typed Drizzle access through an existing pool or checked-out client. Callers inside a transaction pass that same client; the adapter does not acquire another connection, start nested transactions or retry. Named domain queries use typed table declarations for routine reads/inserts/guarded updates.

`executeDatabaseQuery` preserves the original pg failure/SQLSTATE by unwrapping only Drizzle's query-error cause, avoiding its additional SQL/parameter-bearing message.

Processing and capture review use that adapter for ordinary reads/inserts, row locks, atomic revision increments and conditional updates on the caller's existing client. The dependency-closure CTE, grants and specialized `public.`-qualified authority reads stay explicit SQL. Capture review projects bigint revisions and instruction versions as exact decimal strings.

Drizzle phase 2 adds ACKed driver mappings for existing target, observation, executor and manual-review tables in their owning schema modules. Ordinary executor journal/reservation reads and inserts, deployment readers, observation reads/inserts, operator-review reads and retained preparation-media access use the same adapter and original transaction. Explicit projections preserve established boundary field names; bigint revisions/cancellation versions return exact decimal strings. Observation timestamp insertion binds the original text through a PostgreSQL timestamptz cast to avoid JavaScript Date truncating submillisecond input. SQL migrations remain untouched. The executor's query-only deployment gate stays explicit SQL rather than widening its deliberately narrow connection port.

Reviewed SQL remains the DDL authority. Explicit parameterized SQL retains the absent-key advisory lock and atomic stream-head allocation where it makes PostgreSQL locking semantics clearest. Neither inferred row types nor verified hashes validate retained JSON structure; consumers retain their runtime boundary validation.

`db/authority.ts` exposes payload-bound idempotency inside the caller-owned transaction, byte verification and commit-ordered event allocation. Idempotency serializes absent as well as present keys using a transaction advisory lock; exact canonical bytes are compared as well as their digest. Different property order is equivalent; changed semantic payload conflicts. Domain writes and dedup result must commit together. A lost commit acknowledgement is **not automatically retried**; consuming features must inspect stable keys read-only and retain uncertainty. No network call belongs inside a retried database transaction.

The global order is idempotency scope → target head → source guard → batch → subject/current heads sorted by ID → media revision → blob digests sorted by digest → per-handle lifetime sentinel → actor lane → job/attempt/question → run/operation/request → stream heads sorted by ID. Skip absent domains, never acquire earlier domains after later locks. `appendEvent` holds the stream-head row lock until the caller commits/rolls back; an unrelated transaction cannot publish a later sequence first. Consistent future snapshots require one repeatable-read view of state and stream head. T02 owns capture migrations/repositories; T03 owns source guards/execution tables and dedicated writer-lock connection; they must coordinate migration IDs and shared contracts rather than query each other's SQL internals. No distributed writer, advisory-lock-only failover or automatic uncertain-write retry is enabled.

## Exact manual approval and dispatch

`review/model.ts` builds only the selected dependency closure. Effective inherited defaults, selected lot/shared Part facts and relevant human notes bind review fingerprints. Unselected lot edits do not stale another lot; shared edits do. The API rejects duplicate/foreign/over-ten scope before reads or a partial successful plan.

`review/preparations.ts` commits a preparation command, then an intent before each actual Part/location read and a bounded result afterwards. Reads occur outside locks, with three concurrent requests and a thirty-second overall budget. Incomplete/unavailable reads never mean absence or an executable plan. A second locked dependency/history check precedes immutable plan/preview/index publication. The sealed prepare-outcome response binds the complete canonical preview, including human-facing labels and excluded lot IDs; workspace and approval verify its digest, schema, encoding and exact preview/command/batch/preparation identity. Approval rechecks current authority but executes the exact retained plan bytes; it never substitutes a freshly serialized draft.

Migration `0004_manual_review.sql` adds immutable review/preparation/read authority and exact batch/actor/source/lot/approval/run/stream parents. A narrow migrator-owned trigger enrolls only retained native capture identity into executor source authority. Its schema-qualified relations, fixed `pg_catalog` search path and revoked PUBLIC execution resist temporary shadowing; API/apply roles cannot enroll sources or replace the bridge. Conflicting original mappings fail, including backfill.

New approval, executor reservation/run, command/outbox, semantic idempotency and event commit together. Exact replay recalls the original approval/run even after later draft edits or fake stock deletion. Changed payload/actor conflicts. New approval checks cumulative source history; unresolved/unknown work blocks later rounds, and approved contributions never become replacement stock.

Start, cancellation and selected safe recovery are durable original-run commands. Only the explicit `review/runner-main.ts` process receives private fake apply configuration. Public DBOS registration/enqueue/inspection delivers commands; it grants no physical ownership. An already claimed dispatch is inspection-only on scheduler recovery. Only the supervisor/physical child may write, under the unchanged host/advisory/activation/witness protocol. Imports, web/autoreload and migrations start no runner.

Journal changes and dispatch receipts append projection events and advance the retained run revision/owning stream in the same transaction. Repeatable-read snapshots pair complete original journal outcomes with a consistent cursor. An interrupted physical owner is recovery-required, never permission to relaunch. The [T04 record](../docs/handovers/bench-intake-T04.md) distinguishes actual browser/process observations, controlled fault fixtures and unsupported production capabilities.

## Operator review and unapproved restructuring

T08 adds `src/operator-review/`, registered from `registerManual`. It composes the capture and review modules and reads media through the existing public media snapshot; it does not query Processing or media tables. The one schema-level dependency is `capture_instruction`'s composite foreign key to the evidence group table, which proves a group belongs to the batch without reading it. Migration `0008_operator_review.sql` adds append-only capture tables: lot lineage, lot retirement, warning dispositions and versioned batch/evidence-group instructions. Those four writes, and the review-context reads, use Drizzle on the caller-owned client. An unknown evidence group still fails as `group_not_found` from SQLSTATE `23503`.

`GET /api/v1/batches/:id/operator-review` is a repeatable-read projection. It returns each active lot's review state (`unreviewed`, `reviewed`, `changed_after_review`), typed blocking issues and warnings with any current dismissal, lineage, retired lots and the latest instructions. Review state uses the same exact-bytes rule as preparation.

Warnings are deterministic: `no_supporting_evidence` and `possible_duplicate_part`. A dismissal needs a reason and binds to the subject's fact digest, so it stops counting once those facts change. When a subject has a dismissal or predecessors, its review bytes use `manual-subject-review/3`; otherwise the retained `/1` and `/2` bytes are unchanged. Unresolved warnings block review, preparation and approval. Blocking issues cannot be dismissed. The gate also applies to lots created before T08, so an older unapproved preparation for a lot with no supporting evidence refuses approval until the warning is resolved.

Bulk edits, restructures (split, merge with explicit same-contribution confirmation, move between Part proposals) and instructions lock the batch, check the expected revision and commit one capture revision. Restructures refuse lots with an original contribution approval. With `preview: true` the server applies the command inside a savepoint, reports the exact impact and rolls back; previews keep no idempotency record and return no new IDs.

Retired lots stay in `CaptureSnapshot.lots` so Processing and media history remain readable; the snapshot marks them with an optional server-projected `retired: true`, which active lots omit so their bytes are unchanged. Capture edits, notes, media links and attachment selections refuse them with `lot_retired`, and selection for review or preparation treats them as blocking. Processing refuses new starts with `subject_retired` and treats their existing work as stale, as described in the [Processing boundary](src/processing/ARCHITECTURE.md#retired-subjects).

The inbox reuses exact operator review/dependency rules, original-run snapshots and ready original media previews; it sends no target requests. Each subsequent command still verifies its own current context. The composer never imports sibling SQL. Its bounded per-batch work reuses the full review projection; this is one browser request per page, not a claim of constant query cost or a throughput improvement. No migration, production grant, schema authority or execution policy changed. The manual test fixture adds two SELECT grants for Processing observations; the no-job path uses only the job probe; production full application provisioning already supplies them.

## Native provider sessions

`GET /api/v1/agent-sessions` also returns `sessions_supported`, true only when the configured processing profile is a session profile, so a client can tell "no sessions" from "sessions are not available in this setup".

## Capture settings and grouped context foundations

Capture supports one transactional `settings` edit for title, quantity/location defaults, retained human supplier/date/tag context and an optional appended note. Per-lot context preserves explicit inheritance/clear/unknown modes. Supplier choices bind to same-batch, same-target supplier-company observations. Calendar dates remain date strings; no context value creates an inventory effect. Immutable `capture_context` versions are omitted from older snapshots when absent and are retained across legacy edit kinds. Splits copy explicit context; conflicting merged context becomes unknown rather than guessed.

Group rename/retirement and per-evidence notes are append-only. `move_many` and `ungroup` serialize under the existing Capture/media locks and commit all memberships together. Ungroup retires active presentation without deleting originals, links, group identities or historical instructions. Current group notes reuse Capture's versioned instruction authority and reject writes to retired groups under the shared Capture lock.

Relevant group labels/notes and evidence notes enter additive `media-inputs/3` manifests. Existing /1 and /2 bytes remain decodable; Part attachments still cannot enter Processing. Capture context materializes as bounded untrusted human notes with retained IDs/actors/versions. Group/evidence note text remains verbatim with scope/version sealed separately in the media descriptor. Review fact/media digests invalidate stale dependencies. Native prompts receive only scoped retained context; no new tool/provider or execution capability is granted. Interpreted media and compiled HTTP validation share the same exact int64 bound.

These are additive backend contracts. Capture UI consolidation follows separately. Older frontend builds fail closed on unknown response fields after new context is stored and need reload; stale old revisions cannot erase context. Deploy compatible generated clients with consumers, preserve drafts and do not remove additive APIs before rolling consumers back.

## Bounded catalogue search

`capture/catalogue.ts` serves the searchable Default location, parent-location and supplier pickers through `GET /api/v1/batches/:id/catalogue/:model` (`location` or `supplier`) and `.../candidates`. Both routes authorize the batch scope, refuse archived batches and check the current target context before any target request, then check the context again after the read so a rotated context cannot publish a late result. The decoder admits only the InvenTree 1.5.0 / API 530 paginated envelope and a small projection per row; any other HTTP 200 body, a non-2xx status, a redirect or a transport fault is `catalogue_unavailable`, never an empty catalogue. A company without the supplier role invalidates a supplier list.

Pages are bounded at 512 KiB for both the body reader and the strict JSON parser. Search sends one strict upstream query (at most 50 results) and, for a numeric query, a separate exact detail read whose 404 is `not_found`. Candidates read up to 500 name-ordered records in pages of 100, with no search filter, under a 15-second budget: each page request (including waiting for headers) and body read receives only the remaining budget, and the snapshot is refused once it is spent; coverage reports loaded, total and truncation. That snapshot is what browser fuzzy ranking uses, so a misspelled query can still find a record the strict search omits. Upstream `next`/`previous` links are ignored and offsets are rebuilt locally. At most two catalogue reads run concurrently per process (`catalogue_busy` otherwise). Results are not observations: choosing one still uses the observation command, which performs the final detail read.

## Batch settings intent

Migration `0014_capture_settings_intent.sql` adds append-only `capture_settings_intent`, `capture_setting_note`, `capture_reference_draft_identity` and `capture_reference_draft` records, owned by `capture/settings-intent.ts`. The complete-state `batch_settings` edit writes title, the Default location selection, supplier/order/tag intent, batch and order notes and the active new-record draft set under one revision, using the existing batch lock, expected revision and payload-bound idempotency. Only facts that differ from retained state receive a new version.

Intent is human request, not an effect. Supplier absence is separate from its selection so it can be restored. Order reference and purchase date are Auto, None or Manual; Manual keeps exact text and calendar strings. Shared tags keep manual values and an independent Auto flag. Batch and order notes are distinct scopes; Remove writes a `null` tombstone and earlier text stays in history. These notes never append to the immutable human-note table.

Drafts have a stable client-generated ID whose kind is fixed by an identity row. Location parents must be same-batch, same-target location observations. Company logos are proved same-batch media by a composite FK, and the media-owned `retainedImageVersion` seam admits only PNG/JPEG versions. A draft omitted from a complete save is retired, not deleted. A location draft chosen as Default location is recorded on the intent record through a kind-checked FK, and the existing location selection becomes `unset`. No draft reaches the inventory transport; supervised creation is separate work.

Each intent change also writes the derived batch-level `capture_context` row, so Processing context notes, Review fingerprints and lot inheritance keep their existing inputs. Only fields whose intent changed are rederived; an unchanged field keeps its retained legacy mode, including `unknown` and `clear`, which the intent mapping cannot represent. Batches without intent map deterministically at read time through `effectiveSettingsIntent` in contracts; nothing is rewritten. Once intent exists, legacy `settings`/`defaults` writes of batch context or location are refused with `settings_intent_superseded`, because older clients cannot see the intent they would contradict. Snapshot fields `settings_intent`, `setting_notes` and `reference_drafts` are omitted when absent, keeping legacy bytes unchanged.

Location precedence: migration `0015_capture_group_location.sql` adds append-only `capture_group_location` (owned by `capture/locations.ts`) for evidence-group assignments; shared-Part assignments reuse `capture_selection` with `field='location'` on the Part subject. Both are `set` (a same-batch location observation) or `clear`; `unset` removes one, and snapshot fields (`parts[].location`, `group_locations`) are omitted when absent. A retired group's assignment is dropped from the snapshot. The pure `resolveLotLocation` in contracts resolves each physical lot: its own value, then its shared Part, then every active group holding evidence linked to the lot (these must agree), then the batch default; `clear` stops the fallback. `review/model.ts` blocks `location_conflict` and `location_groups_unavailable` rather than choosing, and records a Part or group source in the lot's review facts only when one applies, so legacy fact bytes are unchanged. Processing never reads locations and leaves Part assignments out of every sealed input version.

## Batch attention read

`attention/` serves `GET /api/v1/batches/:id/attention` (`BatchAttention`): the badges and need-you items for one batch's tabs. `reader.ts` reads the same processing, operator review and manual workspace projections the screens use, and `projection.ts` derives from them, purely: open questions and failed or interrupted attempts (routed to their Processing step), lots to check and lots changed after review, decisions, and failed or uncertain runs. Decisions are open blocking issues that need an operator choice (Part, quantity or location); status issues such as an earlier approval or an archived batch are not decisions, and approved lots count nowhere in Review. Items stop at 200 while the counts, including the per-step Processing counts, stay exact. The three reads are separate snapshots; the client keys the read by batch revision, so any disagreement is brief. The route is registered only with a database. Invalid IDs are 400, an unconfigured development setup is 503, and capture or processing failures map to "Batch attention is unavailable."

`GET /api/v1/connection-status` also reports `target.kind`: `owned_test` when the development stack runs the owned fake target (`INTAKE_TARGET_PROFILE=fake`), otherwise `configured`. The browser shows the former as "Test InvenTree".

## Header observation foundations

`header/` supplies read-only `GET /api/v1/connection-status` and `GET /api/v1/header-work` under the existing development Host/Origin and scoped authority boundary. The consumer header remains separate work. Connection reads reuse the fixed inventory adapter's authenticated `GET /api/part/?limit=1`, manual redirect refusal and 3-second abort deadline. Only HTTP status/JSON content type is observed; the body is cancelled and no Part data is retained. This establishes API reachability, not import compatibility or write permission. No browser-supplied target/credentials are accepted.

One immutable configured-profile closure owns one cached observation and one coalesced probe. Completed results cache 30 seconds; freshness expires at 60 seconds, including backward-clock refusal. Fresh failed checks remain unavailable, rather than being relabelled stale. Safe codes omit response bodies, credentials and raw failures. Unsafe or unconfigured navigation addresses are omitted. Current database target-context checks before and after reads fence cached/late observations after rotation; replacing the startup profile constructs a new cache. API request success and live-socket health remain separate frontend observations.

Work reads use one repeatable-read transaction, existing processing currency and manual receipt readers, plus active-session filtering before its history-independent limit. Physical lane ownership takes precedence even after logical cancellation; a foreign-context lane contributes only the existing safe occupied aggregate. Work and session collections have separate 100/50 limits/truncation flags, deterministic ordering and current-batch preference. Processing steps report only retained stage/state; import steps report approval/dispatch/effect certainty. `steps_complete:false` explicitly leaves unobserved detail unknown. Native session IDs, transcripts, percentages and mutation controls are absent.

Existing primary/foreign-key joins and `agent_session_history(queued_at DESC,attempt_id DESC)` support these reads. No migration or speculative index was added; collection bounds are not a claim that every historical scan is constant-time. Owned-PG qualification exercises actual API role grants, occupied agents beyond the first history page, independent truncation, current-batch order, scoped import readback and context rotation. No live target/provider qualification is implied.
