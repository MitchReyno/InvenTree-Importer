## Decisions, alternatives and actual package qualification

All packages remain at T01's exact pins, with no root manifests/lock/shared contracts/generated edits. Public Fastify/TypeBox schemas continue to own HTTP/scalars; no second HTTP/schema engine is added. The stock-only internal plan uses their existing exact scalar patterns with the shared strict JSON/canonical-byte helpers. Drizzle 0.45.4 remains in the existing bounded delivery adapter, while parameterized pg SQL and reviewed migration constraints own execution locks/authority. There is no ORM schema push or speculative catalogue schema.

pg 8.16.3 public `Pool.connect`/`Client.query`/connection events are exercised against PG17.10. A dedicated non-pooled `Client` owns the advisory lock and is never silently reconnected. An actual COMMIT-ACK fault exposed the foundation transaction wrapper's lack of a borrowed-client `error` listener: a query rejection alone did not consume the separate socket error event. The new owned `executorTransaction` handles both, destroys uncertain clients and never retries. The shared foundation wrapper is left unchanged; the coordinator proposal below describes the reusable fix. Approval consumers must use the qualified owned wrapper until the shared fix lands.

DBOS 5.4.0 actual `DBOSClient.create`, `enqueue`, `getWorkflow`, `destroy` and the existing public `deliverCommand` adapter were used, not private scheduler tables. Original stock commands are enqueued twice with exact retained arguments, yielding one workflow and zero HTTP/intent effects; a preexisting same-workflow changed argument is durably classified `payload_conflict`. This is delivery qualification only: no scheduler daemon/product handler is registered, and scheduler ACK/recovery does not authorize physical replay.

For host exclusion, [proper-lockfile's public design/options](https://github.com/moxystudio/node-proper-lockfile) were compared with the actual policy: `mtime` refresh, default stale 10 seconds/minimum 5 seconds, compromise detection and eventual stale acquisition do not prove a surviving physical child exited. Automatic release belongs to the acquiring process, not proof of a supervised descendant's exit. Adding it would introduce dependency/licensing/security cost without the required guarantee. Native atomic `mkdir`, exclusive synced files and explicit `child_process.fork`/exit observation are sufficient for a deliberately **non-expiring, non-stealable** local claim, not a custom durable scheduler. The resulting availability cost is intentional: parent death leaves apply blocked; no stale timeout/PID-based lock removal exists. Native process ownership is not a distributed-lock or hostile-admin guarantee.

The initial transport choice (native Fetch with manual redirects) was rejected by **observed** behavior: Node24 Fetch repeats a POST on HTTP421. The unchanged new `transport-single-send` test against T01 observed **two identical POSTs** and failed. Core `node:http.request`/`node:https.request`, `agent: false`, no proxy discovery and no retry/redirect algorithm now produce exactly one POST and HTTP421. The same test passes after the change. This is a real controlled HTTP negative regression, not a mocked call counter or planted expected output. The default transport injection seam remains for existing controlled tests; no arbitrary adapter is exposed through product routes.

This was a conservative unsupported-capability decision, not a failed startup or successful real HTTP qualification. A new real profile requires actual observed disposable endpoint/effect qualification and independent review; it must not reinterpret the fake capability as a production claim.

## Public integration seams for T04

These are internal TypeScript/server seams, not browser DTOs or test-approval routes. T04 owns current draft/preparation/dependency/review authorization, actor/object access, retained capture-to-original lineage, domain idempotency/events, approved plan creation and safe error/DTO mapping. Neither approval nor apply may fabricate new original-source identity to make history appear absent.

1. Trusted source owner calls `retainOriginalSource(client, { targetId, sourceId, originalSourceKey })` using retained original lineage. The approval/apply grants explicitly exclude source/deployment enrollment. Aliases must retain the same original key; changed mapping conflicts. There is no import of T02 SQL or sibling source code.
2. T04 retains the exact canonical bytes/digest of a `StockPlan` (`bench-stock-plan/1`, `bench-stock/1`, qualified capability, immutable deployment/epoch/target/context/continuity/source/original key, ordered stock operations). Each operation contains `operationKey`, immutable `contributionKey`, existing Part PK string, location PK string/null, exact positive quantity string and original-contribution barcode. No URL, raw credential or Part-create payload appears in this plan.
3. Inside its single caller-owned approval transaction, T04 invokes `reserveApprovedStock(client, { approvalId, preparationId, runId, commandId, actorId, bytes, digest })`. All IDs are UUIDs. Pass **retained bytes**, not `encodePlan` applied to mutable current state. The transaction commits T04's domain approval/idempotency/event alongside executor approval/run/operations/command/outbox/source guard. `preparationId` is stable: replay after lost COMMIT ACK adopts original returned identities; changed semantic payload or actor conflicts. Failure rolls all these writes back.
4. A trusted bounded dispatcher invokes `deliverStockCommand(pool, dbosClient, commandId)`. A scheduler handler must bind the exact original command arguments and use `startApply({ databaseUrl, gateRoot, runId, profile, recoveryIds? })` with server-held deployment settings. No browser-selected target/key/URL, automatic worker import, or unbounded outbox loop is supplied here. The child revalidates exact authority and ownership independently.
5. `cancelRun(client, runId, actorId)` and `selectRecovery(client, runId, operationKey, actorId)` are transaction seams requiring T04's command-level idempotency/access checks. A new cancellation version revokes older recovery selections. Only original pending or positively proven pre-dispatch no-effect operations can be selected; unknown siblings also block. `verifyKnownStock(pool, profile, { runId, operationKey, actorId })` retains a read-only receipt for an original confirmed output, never grants replacement.
6. `snapshot(poolOrClient, runId)` returns original run/state/per-operation certainty, confirmed PKs and all trustworthy attributed PKs. Missing/corrupt authority throws rather than returning a fresh/empty projection. T04 must map failures and original-run blocking explanations into shared public contracts when it owns that integration.

Provisioning owns private external deployment activation and source-owner permissions; neither runtime role can turn missing evidence into permission. `grantExecutor(pool, role, 'approval' | 'apply')` extends narrowly scoped foundation role provisioning; apply receives only intent/result/effect/verification insertion and required locks/guard settlement. This helper is **not** installed into the shared development grant helper by T03. Trusted fixture setup explicitly seeds deployment, source owner, activation and actor before calling the same reservation seam; there is no endpoint or disguised inference from arbitrary submitted source IDs.

## Safety evidence with independent expected outcomes

The runtime/PG/process tiers run on real local PG and actual HTTP/supervised processes with a controlled persistent inventory fake, not real InvenTree. The normal observed original operation is Part **29**, location **43**, exact quantity **1.000001**, fixed asymmetric original/contribution UUIDs and returned stock PK **7101**. The test's expected literal wire is independent of the request encoder:

```json
{"barcode":"bi1:10000000-0000-4000-8000-000000000011:20000000-0000-4000-8000-000000000022","location":"43","part":"29","quantity":"1.000001"}
```

- **Normal supervised path and fake restart:** exactly `GET /api/part/29/`, `GET /api/stock/location/43/`, one `POST /api/stock/` with the literal body; remote PG contains PK7101 and all intended fields. Listener restart retains all three request records and the stock. Adopting the complete original run sends zero further requests. A genuinely new contribution in a later round creates PK7102; deleting PK7101 does not permit its contribution to be recreated under new run/source/original aliases. Exactly two POSTs/two original contributions, only PK7102 remaining after deliberate deletion.
- **Approval adoption/authority:** same stable preparation and exact retained bytes adopt the original run, command and approval. Changed quantity conflicts, with one retained row of each kind. Wrong-operation parents fail composite FKs. Trigger-protected authority and guard identity reject edits/deletion. Explicit rollback leaves zero cancellation rows/HTTP. Source enrollment replay succeeds, changed original binding fails.
- **Real lost approval and intent COMMIT ACK:** the owned TCP proxy forwards COMMIT to PG and withholds its actual response through `ReadyForQuery`, then closes the client connection. PG retains one approval and original run is adopted after reconnect/inspection. Lost stock-intent ACK retains exactly one create intent but sends **zero POSTs**, returns recovery-required and rejects create recovery. Two actual ACK losses are independently counted by the proxy.
- **Remote acceptance, lost response:** fake PG commits stock7101 and the wire request, then closes the response. One POST, retained `transport_loss`, unknown certainty, no confirmed PK. Reinvocation sends no new create; original unknown recovery/new source round are blocked. Unknown also blocks untouched siblings and recovery IDs selected before the unknown arose; still three total wire records and one stock.
- **SIGKILL after intent/result:** a real physical child publishes a durable checkpoint and pauses before the test kills/reaps it. After intent: zero POSTs and unknown, never a retry. After result COMMIT: one POST and original confirmed PK7101 survive; restart reports that original PK without another create.
- **Original child survives dedicated DB connection loss:** terminating only its own PG backend releases the advisory lock, and a second dedicated client demonstrably acquires it while the old child remains alive. A replacement supervisor still fails host claim (`EEXIST`). Original child resumes into pre-dispatch refusal with zero POSTs and retains positive `none` evidence; only explicit original-run selected recovery after reaping creates PK7101 once.
- **Supervisor SIGKILL with HTTP in flight:** the fake has already committed PK7101 while holding its response, and the physical child remains alive after parent death. Replacement fails before any request. On release the child exits; the retained host claim **still** blocks a replacement rather than expiring/stealing. Exactly one POST/stock. This tests genuine parent/child death, not a simulated scheduler flag.
- **Cancellation race:** cancellation under the run/source locks before create authorization yields zero POSTs and settled-incomplete; original selected pending recovery later creates once. Cancellation after intent can allow the already-authorized first lot to finish, but not the next lot. A later distinct cancellation invalidates an older recovery selection, with no second POST.
- **Malformed attribution/redirect:** partial `{pk:7101}` preserves PK7101 as unknown in both effect and snapshot; it is not counted confirmed. Redirect yields unknown and zero requests to the controlled redirect sink. Both receive exactly one original POST and no retry.
- **Known-output verification:** three original-PK GETs retain `matches`, `missing_or_changed` after consumption, then `missing_or_changed` after deletion. Original confirmed history/PK remains; no second create or fresh-preparation replenishment. Exactly one POST, three `/api/stock/7101/` GETs and zero remaining stocks after deliberate deletion.
- **Missing/corrupt/disabled authority:** disabled activation, changed epoch/origin/build, missing activation, corrupt retained plan and missing run all refuse before HTTP; zero fake requests. Restricted apply role can read/lock but cannot approve/enroll/truncate/erase/change target profile or disable authority triggers.
- **Older PG authority restore:** a trusted test-owned SQL backup of canonical authority predates stock creation. Restoring that earlier authority while retaining fake records/stock and external witnesses leaves zero run history locally. A fresh source alias/run is conservatively blocked by the missing intent witness binding **before any new HTTP**. The original remote PK7101/one POST survives. This is a real PG logical authority rollback with retained remote/external state, **not** full `pg_dump`/blob/filesystem coherent backup qualification or permission to copy spike DBs.
- **Actual DBOS bounded dispatch:** exact original stock command delivered twice is ACKed under one workflow/input and produces zero request intents/HTTP. Same workflow with changed retained scheduler argument yields durable `payload_conflict`, never physical apply. Existing T01 DBOS process recovery/version tests continue to pass; their synthetic workflow is not counted as physical writer evidence.
