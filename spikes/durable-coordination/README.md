# Durable coordination investigation

This is the isolated Stage 1B Django/PostgreSQL/DBOS spike, not an application server, production scheduler or inventory executor. It consumes the [shared synthetic transcript](../shared/README.md). Every apparent provider action is simulated; no subscription, model API or inventory service is contacted.

## Reproduce

Use Python 3.12, uv and installed PostgreSQL **14 or later** binaries (`initdb` and `pg_ctl`) on PATH. The tested versions are recorded in [process-probe.json](evidence/process-probe.json). The local Python manifest/lock isolate these dependencies from `backend/`; do not add them to the backend manifest merely to run this investigation.

From repository root:

```sh
uv sync --locked --project spikes/durable-coordination
uv run --locked --project spikes/durable-coordination python spikes/durable-coordination/probe.py --state .temp/coordination-probe-new
uv run --locked --project backend pytest backend/tests/spikes/test_durable_coordination.py
COORDINATION_SPIKE_REAL=1 uv run --locked --project backend pytest backend/tests/spikes/test_durable_coordination.py
uv run --locked --project backend ruff check --config backend/pyproject.toml spikes/durable-coordination backend/tests/spikes/test_durable_coordination.py
```

The probe refuses an existing state directory, initializes its **own new** private cluster, creates only `coordination_spike_probe`, uses an OS-selected loopback TCP port, disables Unix sockets and stops only that cluster in its finalizer. PostgreSQL trust authentication is confined to that disposable local cluster; this is not a production authentication recommendation. It never accepts an existing service URL. Place the state on persistent local storage: database files, copied synthetic bundle, evidence report and worker/PostgreSQL logs remain after the process exits. Inspect them or choose a new state directory for another run; never reseed or remove someone else's state. No global install, existing database or shared infrastructure change is necessary.

The probe runs separate `entry.py migrate`, `submit`, `dispatch` and `worker` processes. `submit` is the Django command-side stand-in for a web request: it commits a job, immutable intent and outbox together, then can receive real SIGKILL before enqueue. `dispatch` can receive SIGKILL after the independent DBOS enqueue commit and before its application acknowledgement. Recovery redelivers the identical workflow ID and digest. The explicit worker is the only entry point that launches DBOS; importing the Django application and running migrations do not launch workers. There is deliberately no HTTP framework, frontend, approval model or generic lease scheduler in this spike.

For inspecting a retained owned cluster, PostgreSQL's `pg_ctl -D <state>/pg status` is read-only. Its `postmaster.opts` records the original port/options. Start/stop only the cluster you created; do not repoint the CLI at another server. Low-level commands need `COORDINATION_PG_PORT`, `COORDINATION_PG_DATABASE` and optionally `COORDINATION_BUNDLE` supplied by the trusted operator/probe, never a runner message. They restrict the host to loopback and the database/role to the spike namespace, but those names alone are not proof of ownership; the probe's new private data directory is the ownership guarantee.

## Boundaries demonstrated

- Application transaction owns Job → Intent → Outbox. Failed application transactions leave none of them. `on_commit` is not used as a substitute for durable intent.
- Workflow ID hashes `(batch_id, job_id, attempt_id)`; the stored digest binds the normalized request and explicit app version. The same ID cannot be submitted with a different payload/version. The worker checks both its actual DBOS workflow ID and executing `DBOS.application_version` own the intent before emissions, including before calling a potentially cached step. Six legitimate workflows reach SUCCESS; four deliberate runtime adverse rows reach ERROR with no extra accepted emissions. Manifest revisions hash exact bytes, not normalized JSON. Original manifest bytes remain in the immutable intent.
- DBOS owns a single queue with global and per-worker concurrency 1. The outbox is delivery only, not an additional job-claim mechanism. Its acknowledgement is deliberately a separate transaction from DBOS enqueue. Repeat delivery uses the original ID; the application, not assumed DBOS argument comparison, enforces payload identity.
- Before ACK, the dispatcher inspects the persisted DBOS row's app version, workflow/queue/class/config names and deserialized arguments. An adopted conflicting duplicate records `Outbox.conflict=runtime_metadata_conflict`, leaves ACK false, marks the current job `dispatch_conflict` and exits nonzero after processing other rows. Later passes report the conflict without re-enqueue/rebinding; unrelated healthy work still finishes. This is an explicit review disposition, not automatic recovery. Enqueue failures before a handle is returned propagate without ACK. There is no conflict-clear/reset command; preserve the bad runtime row and immutable intent for review rather than relabeling either.
- Messages are strictly decoded, checked against the shared schema, correlated to the current batch/job/attempt/input, sequenced and deduplicated by normalized content. Questions are committed before a waiting result may refer to them. Output artifacts are verified before publishing success, and the bounded fixture Part/lot/source identities are checked.
- The synthetic runner supports only the authored `attempt-1`/original and `attempt-2`/confirmed input journeys (a new batch ID may reuse the scenario). Other schema-valid attempt/input combinations are rejected before any Job/Intent/Outbox commit. A transcript must contain exactly one final result, and the runner refuses successful completion without a persisted terminal emission. These are deliberately narrow fixture-runner restrictions, not changes to the shared protocol or a general provider implementation.
- A waiting question is application state, not a parked DBOS workflow: the command returns successfully and releases its queue slot. A distinct second batch, derived from the same synthetic evidence in the private copied bundle, finishes while the first question is still unanswered. Both batches produce proposals only.
- A counted answer creates a different immutable input and `attempt-2`, atomically with its own outbox item. This authored simulation accepts only the fixture's counted-20 answer; it is not a general human-input parser. Obsolete answer revision, actor mismatch, old attempt and old input results are rejected.
- Restart after the application result commits but before the DBOS step checkpoint replays the step without a second accepted emission. Explicit `coordination-v1`/`coordination-v2` version fencing keeps old ENQUEUED and PENDING work from the incompatible-version process; restoring the compatible version drains it. Version labels exercise fencing, not the correctness of an arbitrary future code migration.

[state.sh](state.sh) prints read-only review state. The evidence JSON is an observed run, not a guarantee about remote side effects, arbitrary provider sessions, production availability, backup/restore or distributed ownership.
