# Design assessment

## Context and grounding

[docs/agent-sessions.md](../../../docs/agent-sessions.md) is the full reference for this change.

- **Part 1** documents today's code at `9db1921e`: inputs, outputs, hand-offs, re-steering, the state and event maps, and 14 gaps.
- **Part 2** is the target this change delivers: stage contracts, the Match step, the identity layering, the MCP tools, the instruction packs, and outputs into records.

This design records the decisions and the order of work, and doesn't repeat the contracts.

The complexity is high. The change touches every session's input and output, adds an app pipeline step (Match) with app-owned questions, extends the media decoder, adds a profile, and changes how Review, Records and approval use agent output.

## Goals and constraints

- **Goals:** those of the [proposal](proposal.md) and the deltas in `specs/`.
- **Constraints:**
  - Sealed inputs and pinned profiles stay immutable. A new instruction text needs a new profile row, digest, CHECK combination, contract literal and config entry once the profile is active; before PR-G2 activates `/4`, only tests seal it, so a later migration may replace its packs.
  - Admission compares exact tool sets and forbids skills, so new tools join a new tool profile.
  - The untrusted-data rule holds: notes, images, documents and web content are data, never instructions.
  - Retained attempts of earlier profiles stay readable. New formats are forward-only.
  - InvenTree is read only through the app's read credential. Writes go only through approval.

## Decisions and alternatives

### Per-stage instruction text: a stage pack table, not one profile per stage

- `shared-vm-agent/4`'s profile row holds the shared base instructions.
- Each stage's pack is in a new immutable table `processing_stage_instructions(profile_id, stage, bytes, digest)`.
- The session input seals `stage_instructions_sha256`, and the claim checks it as it checks the profile digest today.
- The system prompt is the base followed by the stage pack.
- **Rejected:** one profile id per stage (`shared-vm-agent/4-examine` …). The worker is paired to one profile (`session-runner.ts:499-507`), and the config allow-list is one profile per worker, so per-stage profiles would need a paired worker per stage or a pairing redesign.
- **Rejected:** keeping per-stage text in the unsealed opening. It isn't digest-bound, and these rules are authority.

### Briefs are built when the input is sealed

- Examine's input is sealed when its job is queued, as today. A `/7` Research or Images lot job is queued as an unclaimed lot with its pinned identity revision and mode but no attempt; its group's input, with the brief, is sealed at claim (see multi-lot sessions).
- The lead input builder and the group claim assemble the brief from retained state into `bench-intake-input/7`.
- `read_lot` and `read_batch` serve two views: with the sealed revision, the pages of the brief the session started from; without it, the current view and its revision. Every page returns a continuation token bound to its revision. A current-view read writes that revision's pages to the attempt's bounded page store, so later pages come from the same snapshot after an edit, and each page says when a newer revision exists; a session that wants it starts again without a token. A snapshot past the store's bound is refused as `brief_revision_unavailable`, and the session rereads the current view. Tests cover an edit between queueing and the first page read, and an edit between two current-view pages.
- The opening renders the sealed brief within 48 KiB, and summarises past it.
- The sealed manifest stays within the existing 240 KiB retained-input cap (`processing/limits.ts:2`). What doesn't fit goes to an immutable, bounded page store, `processing_input_page`, written with the input; the manifest seals each page's id and digest, so the sealed view never reads mutable capture data. A brief larger than the page store's bound is refused with `processing_input_capacity`, as today. Tests cover an edit to a field held only in a page.
- **Rejected:** building the brief at turn time. That breaks the sealed-input guarantee.

### Typed outputs replace the generic proposal for new work

- New proposal schemas: `examine-identity/1`, `research-identity/1`, `research/1` and `images/1`.
- The `propose` handler checks the kind against the principal's stage and mode, and the field allow-list per kind. `propose_images` is a separate tool so its recipe arguments are typed.
- Records read each field from its owning kind.
- The quantity estimate is `examine-identity/1`'s, and reaches Review as a proposed value. For `/7`, `propose_lot` refuses the `estimated_quantity` and `quantity_basis` arguments it accepts today (`capture/evidence-observations.ts:504,561-568`).
- `/5` proposals stay readable, and their values keep showing as attributions.
- **Rejected:** a generic shape with a stage field allow-list. Consumers would still parse one union, and Mitch chose typed outputs.

### Match is an app module with app-owned questions

- **Module:** `intake-server/src/processing/match/`, with three parts:
  - key extraction from the merged identity and match notes;
  - search over the InvenTree read credential (`intake-server/src/inventory/`) and this app's unapproved lots. The transport's read allowlist admits only fixed semantic reads and two list reads (`inventory/transport.ts:44`), so PR-C adds bounded Match list reads with named filters the pinned InvenTree 1.5.0 API offers (Part search, manufacturer and supplier Parts, stock by Part and batch, a Part's parameters and attachments, and a category's parameter mappings), modifying inventory-target-protection's allowlist. The owned fake that `pnpm dev` starts serves only a Part probe and single records today (`tests/fixtures/inventory-fake.ts:64-116`), so PR-C adds its list routes. The stock list has no barcode filter, so the import reference is looked up in this app's retained approvals of that contribution, which decide the hit, with a stock read by PK reporting any known output's status;
  - verdicts, sufficiency, decisions and pass-3 validation.
- **State:** per-lot match state in a `processing_match` table (keys, candidates with reasons, verdict, decision, modes, revision). A persisted Match outcome, either an operator decision or a clear verdict, carries an outcome revision and the stage modes, separate from search-request generations: a search that returns an equivalent result keeps the outcome revision, so proposals pinned to it stay current, while approval is still fenced until that search settles. The outcome and is what `research/1` and `images/1` pin. PR-B defines its contract with a test fixture, so typed outputs can be accepted before PR-C; PR-C supplies the real outcomes.
- **Questions:** a separate store, `processing_match_question` and its answer. `processing_question` can't hold them: it requires a job, attempt, input and message, its answer requires a continuation attempt (`migrations/0006_processing.sql:81-100`), and `processing/read.ts:248-262` reads through inner joins to all of them, while the match question exists before any lot job. Match questions use BI-019's stepped question contract and are pinned to the match revision and the candidate set they quote. Answers go through a Match answer route that records the decision and queues stages; an answer to a stale question is refused. Needs you reads both stores. Tests cover Needs you before any lot job exists and after a search makes a question stale.
- **Ordering:** search is a remote read, so it never runs in the transaction that triggers it (today `onLeadIdentity` runs inside the proposal transaction, `handlers.ts:1051`). The trigger commits a search request with the next per-lot search generation, naming the identity revision and keys; the search runs after commit; its result settles only if its generation is still the lot's latest, and the verdict, question or decision, and queueing commit together. An older result is discarded. The generation advances when the request commits, not when it settles, so answers, claims and new approvals check it under the lot's match lock: while a newer search is pending, an answer to the older question is refused and no stage is queued or claimed from it. Searches run in the API process, which owns the target-bound reader (`main.ts:144-153`); the session worker has no target reader (`agents/session/session-worker-main.ts:118-131`) and its role can't read `executor_operation` (`processing/grants.ts`), so session-side triggers only commit search requests. The contribution lookup uses the history query preparation already runs in the API (`execution/source.ts:94-106`). Committed, unsettled search requests are picked up by a durable sweep in the API process, and a result settles once per generation, so a restart between the commit and the InvenTree read loses nothing. Tests cover a restart between the commit and the read, two searches on the same identity settling in reverse order, and an answer and an approval arriving before the newer search settles. Batch answers follow the same rule. Pass 3 records its own validation result on the preparation, bound to the lot's current interactive generation, and leaves the interactive verdict and modes untouched; it never advances that generation or supersedes a question, and it runs only for a lot whose interactive outcome is settled, with no open question and no pending search.
- **Earlier-run access:** the history query finds hits across the target (`execution/source.ts:94-106`), while the run read needs the approver's actor and target context (`review/runs.ts:71-94,485-510`), so a hit blocks target-wide but its run link and stock status appear only when the operator may read that run.
- **Original-contribution answers:** today `lot_exclusion` refuses an approved lot (`capture/repository.ts:678-703`), so already imported on an original-contribution hit is recorded on the Match decision and projected in Review and Changes as already approved, leaving the Capture guard and approval history unchanged.
- **Queueing:** Match queues Research and Images with their modes, replacing `onLeadIdentity`'s direct queueing for the new profiles.
- **Waits:** `processing_match` persists which of the lot's stages wait for Match, because `waiting_input` holds only while the job has its own open question and any inbox item resumes it (`session-runner.ts:770-790`, `session-execution.ts:112-145`). Claim, resume, Start and replacement check the wait. A held lot's stage stays held, with unrelated inbox items for it pending, until a `match` inbox item delivers its mode. A late candidate holds only the affected lot: a running session gets a `match_hold` item for that lot, a distinct kind that reaches an active turn through live steering or `read_inbox`, applies no mode and never wakes a parked group, and stops work on that lot at the end of its turn and keeps working on its other lots; it is parked only when every lot it holds waits or is done (see multi-lot sessions). A resumed session keeps its sealed brief; the `match` item that ends its wait names the merged identity revision and mode, and its later proposals rely on that revision. Today the pin is checked only before the first turn (`session-runner.ts:524-529`), so the wait check also compares the identity revision at each resume, and a change after the decision searches again and keeps the wait. Tests cover a second identity change between the decision and the resume. Proposals published under a mode the decision changes are marked stale. Tests cover a late candidate while a one-lot Images session runs and, with multi-lot sessions, a peer lot publishing while the question is open, and an unrelated inbox item arriving while Research waits.
- **Rejected:**
  - an Inventory agent with a search tool (unrecorded search, a session per lot);
  - asking through an agent (it costs a session to relay an app decision).

### Identity layering

- The lot's identity is a merged view over Examine's base proposal and Research's amendments, built by the app. Each field records its source proposal.
- Changing it bumps an identity revision, which successors pin instead of a single proposal id. `pinnedIdentityCurrent` checks the revision.
- For agent-made, unedited lots, the merge proposes the label and draft Part fields through the capture edit path, as the lead's own lot edits do. Edited lots get suggestions. Research's `propose` runs on the runner connection, which has no Capture write grants (`agents/tools/handlers.ts:438-457`, `processing/grants.ts:44-57`), so it only records the amendment; an app-owned transaction on the `agent_writer` connection then applies the merge, after checking the amendment's base identity revision and the lot's operator edits. Tests run it with the deployed roles. The publication transaction also records the amendment as pending work under the lot's Match lock, and preparation and approval are blocked for the lot until the writer transaction settles it. The API holds no `agent_writer` connection (`main.ts:103-105`); the session worker does (`agents/session/session-worker-main.ts:73-77`). So the session worker's writer loop applies amendments: it commits the merge together with any resulting search request, which the API's sweep then runs. After a crash, that writer loop picks up a recorded amendment that isn't applied yet, keyed by proposal id, and applies it only if its base revision still holds. If an operator correction or another change advanced the revision first, the writer marks the amendment superseded under the lot's Match lock, clears the pending marker and sends the session a `revision/2` with the current revision; a process test restarts between the runner commit and the writer transaction.
- A session's amendments for one lot are serialized: while one is pending, `propose` refuses another for that lot with a correctable result naming the pending amendment, and the session publishes again once its `revision/2` names the applied revision. Successive compatible amendments from one session build on each other: each field keeps its own source amendment, a later amendment of the same session doesn't make an earlier one stale, and only a change by anyone else (Examine, the operator or another session) does.
- A replacing amendment (a different part) isn't merged. It opens a question.

### Image work in the media decoder, in TypeScript

- The decoder is TypeScript on `sharp` 0.35.5 and `@napi-rs/canvas` 1.1.0 (`media-decoder/package.json`). The skills' Python scripts are reimplemented there:
  - **recipe `/2` rendering:** crop, quarter turns, affine straightening at most 15° with a corner guard, bounded white balance, and contrast, gamma and sharpening that keep hue;
  - **the grid overlay:** canvas text over a `sharp` rendition;
  - **the montage:** `sharp` composite;
  - **the logo matcher:** Otsu thresholding, both polarities, 48×48 normalised correlation with aspect weighting, on raw buffers.
- **Parity tests:** each port is tested against outputs from the original scripts on fixtures.
- **The logo set** (6.9 MB, private use approved) is bundled with the decoder image.
- **The intake MCP tools** call the decoder through the existing dispatcher, so the decoder role stays restricted. Today only the media worker has the dispatcher socket and pinned decoder image (`tooling/deployment/host-media.compose.yaml:28-49`), and without a socket the runner launches Docker itself (`media/decoder-runner.ts:38-44`). Task 11 mounts the dispatcher socket read-only and the pinned image into the coordinator, which hosts the tool server (`host-runner.compose.yaml`), and the coordinator refuses image tools when no socket is configured, so only the dispatcher reaches the engine. A packaged test runs an image tool through it. The local launcher today gives the decoder image only to the media child (`tooling/dev.cjs:448`, `tooling/dev/stack.cjs:69`), so task 11 also starts the dispatcher locally and gives the session worker its socket and image.
- **Delivery:** on the VM relay only `fetch_evidence` gets the larger image envelope and has its replies staged (`agents/shared-vm/evidence-request.ts`, `native-turn.ts`). The relay is extended to the new image tools with one aggregate per-run image budget, and montage and logo-sheet replies are tested over the real relay.
- **Parity** is measured on the rendered crop pixels, before labels, downscaling or delivery encoding, for the geometric operations: crop, quarter turns and straightening. White balance keeps the script's per-channel gains (`.agents/skills/component-photo-crops/scripts/crop.py:161-168`), since only those can neutralise a colour cast, with each gain bounded to ±15%. Bounded gains alone can still shift a saturated colour by more than 5° (RGB 120, 60, 30 can move from 20° to 30°), so the renderer measures the largest hue shift over saturated pixels and scales the gains back toward 1 until it is at most 5°, refusing the recipe if it can't. It is tested for parity with the script only when that guard leaves the gains intact, for cast reduction on a neutral reference, and with a regression that exercises the guard. The script's contrast, gamma and sharpening also work per channel, which shifts hue, so recipe `/2` applies them on a luminance channel, exempt from parity and tested for hue retention on coloured-pixel fixtures. `preview_images` and approval share that render; the montage is checked separately to depict it.
- **Rejected:**
  - Python in the decoder (a second runtime);
  - scripts in the VM as the output route (no provenance).

### Multi-lot sessions (Mitch's decision)

- **Model:** jobs stay per lot. An attempt binds 1 to N lot jobs through a new membership table, `processing_attempt_lot(attempt_id, job_id, state)`. Today the schema ties an attempt to one job: the current-attempt key (`migrations/0006_processing.sql:49-50`), questions and answers (`:94`, `:109`), and the session, inbox, answer trigger and cursor (`migrations/0018_agent_session_runtime.sql:45,90,109,121`). Task 9 owns that schema change: the attempt keeps its first lot's job as an anchor for legacy constraints; each lot job's current pointer, questions and answers reference its membership; and the session, inbox and cursor key on the group's lineage id, with each item naming its lot. Legacy ids and one-job lineages are unchanged. A PG test answers a question for a non-anchor lot and moves that lot while a peer keeps running.
- **Mode:** the group's stage and mode are claim-time properties. A lot's mode may then change inside the group: an identify lot's `match` item gives it full or gaps mode, or closes it when Research is skipped, while its peers stay in identify mode. Tests cover an identify group whose lots get different decisions.
- **Which identity changes release a lot:** changes the group's own session didn't make: Examine republishing the identity, an operator correction or regroup, or another session's amendment. The session's own amendment, and the merge and Match search it triggers, keep the lot in the group.
- **Claim:** under a per-batch-and-stage lock, so two claimers can't take the same lot, the claim takes up to the sealed cap of unclaimed lot jobs of one stage and mode, oldest first, that Match allows: no Match wait, the current search generation, not superseded or stale. It stops adding lots before the group's combined media would pass the media input limits (`MEDIA_INPUT_MAX_VERSIONS`, 64, `contracts/src/media.ts:401`); a single lot over them fails as today. In one transaction on the session worker's provisioned `agent_writer` connection (`agents/session/session-worker-main.ts:73-77`), which already holds the insert grants for inputs, attempts, sessions, commands and outbox entries that the runner connection lacks (`processing/grants.ts:44-57,86-90`), it seals the group's `/7` input, overflow pages and media pins and creates the attempt, session, memberships, command and outbox entry; the runner connection then takes the slot as today. The claim-race and restart tests run with the deployed roles. Lots that become ready later go to a new session. Tests cover two claimers racing and a group whose combined evidence passes 64 versions.
- **Caps:** `research_lots_per_session` (default 5) and `images_lots_per_session` (default 8), integers 1–20, in the agent settings contract and Settings › Agents › Sessions, sealed per attempt as `settings-debug-mode` seals its settings. A cap of 1 reproduces one-lot sessions.
- **Brief:** a shared section, then one section per lot, each with an equal share of the 48 KiB budget and the rest in the page store. `read_lot(lot_id)` refuses lots outside the group.
- **Outputs:** typed proposals name their lot; `subject_id` must be an active member. Release records stay per attempt, but a citation also needs the cited evidence to be in the proposal lot's scope, as the handler's lot checks do today (`agents/tools/handlers.ts:674-759`). An Images recipe's source versions need the same lot scope. Examine keeps its batch-wide authority to propose for a live lot. Tests cover a cross-lot citation refused, evidence genuinely shared by two lots, and a proposal after a lot's release.
- **Skips:** a decision that skips a stage ends that lot's membership in the stage's group as finished, for a held Images lot as for a paused identify lot; the group settles when no active member remains.
- **Waits:** Match waits stay per lot. The session works on its other lots while one waits, and is parked, holding no slot, only when all its lots wait or are done. A lot's `match` item resumes that lot.
- **Inbox:** today one high-water cursor per lineage acknowledges everything up to a sequence (`agents/tools/inbox.ts:208-245`), and any unread item wakes the session (`session-execution.ts:112-145`). So lot items carry their lot and are acknowledged per lot, in a per-lot cursor beside the lineage cursor for batch-wide items. Wake-up counts unread items of lots that aren't held, and a current `match` item that ends a held lot's wait, so an all-held group wakes for its decision. A released lot's pending items move with it to its next session. Tests cover a held lot's chat at sequence 10 and a runnable lot's answer at 11, and an all-held group staying parked without a slot.
- **Routing:** revisions, `match` items and answers for a lot go to the lineage holding it. A lot whose identity is changed after the claim by anyone but the group's own session is released: its partial work is stale, because the successor's currentness includes its pinned identity revision; it is requeued as its own job; and the session gets a `revision/2`. That release revision is a group item on the original lineage, not a lot item, so it stays deliverable there after the membership ends while the lot's own pending items move with it. Tests cover a self-amendment that keeps the lot, a peer's amendment that releases it, and a release revision reaching a parked original group while the released lot carries its pending items to its next group.
- **Unclaimed lots before claim:** an unclaimed lot job has a new job state, `unclaimed`, and no current attempt; today's `ready` means a finished output and isn't reused. Task 9's migration makes `processing_job.current_attempt_id` nullable (`migrations/0006_processing.sql:29` declares it `NOT NULL`), with a check that allows null only while the job's current queue entry has no attempt: in `unclaimed`, and in the terminal `superseded`, `cancelled` and `failed` states reached from it. Regroup supersedes an unclaimed job under the claim lock, as it supersedes queued jobs through their attempts today (`processing/regroup.ts:21-45`), and a fresh identity requeues the lot as `unclaimed`, such as a cancel that wins the claim race or a lot whose own media is over the input limits. The job is unique per lot and stage (`migrations/0006_processing.sql:31`), so a lot requeued after a release or a group failure returns to `unclaimed` with a null pointer, and its earlier memberships stay as history. The claim loop scans unclaimed jobs durably, beside today's session-row recovery sweep (`session-execution.ts:146`), so a restart between queueing and claim loses nothing; the command and outbox entry are created with the attempt at claim (`session-attempts.ts:110`). The Processing read, which inner-joins through the current attempt today (`processing/read.ts:73`), left-joins and shows the lot as waiting for a session. Start and Start fresh return `ProcessingReceipt`, whose `attempt_ids` must be non-empty (`contracts/src/processing.ts:658`), so a new receipt version lists the accepted jobs and the attempts that exist, which may be none; a retry of the same command returns the same receipt before and after the claim and never queues the lot twice. Cancel today takes an attempt id (`processing/commands.ts:146`), so an unclaimed lot gets an attempt-free cancel by job and revision, under the same per-batch-and-stage lock as the claim: either the cancel wins and the claim skips the job, or the claim wins and the cancel acts on the lot's membership. Cancelling a claimed lot ends only its membership; the group's attempt ends only when no active member remains. Tests cover a restart between queueing and claim, a command retried before and after its lot is claimed, a cancel racing a claim with each side winning, a cancel before a retry claim, a lot that fails before claim, and cancelling the anchor lot while a peer runs.
- **Anchor:** the anchor job only satisfies legacy constraints. The capability resolver today requires the lineage id to equal the job id (`agents/tools/capability.ts:72-77`), and the tool guard and runner check the anchor's current pointer (`handlers.ts:478`); for a group they check the group lineage and attempt instead, and lot operations check active membership. The resume and recovery sweep and settlement also choose a group's latest attempt by lineage, not by the anchor job's attempt numbers (today `session-execution.ts:128-130` takes the job's highest attempt number), so a new attempt on the anchor lot can't hide the group. Releasing or starting fresh on the anchor lot doesn't end the session; a test covers it while a peer publishes and settles, then parks, receives an answer and resumes.
- **Per-lot ordering:** `read_inbox` and live steering (`session-runner.ts:623`) both deliver a lot's items in sequence order and advance only that lot's cursor, and only through the contiguous prefix the provider accepted. Today live steering skips an item the CLI declines and records the highest accepted sequence (`session-runner.ts:651-655`), and the VM reports one final delivered sequence; both paths instead report accepted items per lot, the relay carries that per-lot scope, and a declined item leaves it and every later item of its lot pending. A `match` item that ends a lot's wait is delivered after that lot's earlier pending items, never ahead of them; the lot stays held until that item is accepted. If the provider declines an earlier item, delivery for that lot stops at the gap and the mode change waits. Each `match` item names its search generation and outcome revision, and opening any match question, including a replacing amendment's, advances the outcome revision. Opening a question without a search also advances the lot's search generation under the Match lock, so any outstanding search result is discarded when it arrives, and Check again is deferred until the question is resolved; a test covers an older search result arriving after a replacing amendment's question opens. Under the lot's Match lock, a mode is applied only if both are still current and no question is open; otherwise the item is acknowledged as obsolete without applying its mode or dispatching a continuation. A test covers a replacing-amendment question opening between delivery and acknowledgement. Each item is rechecked when its mode is applied; one whose generation is no longer current is delivered in order as obsolete, changes no mode and doesn't block the current decision's item. While a newer search is pending, delivery of the lot's `match` item is suspended; when it settles with an unchanged outcome, Match reissues the mode as a `match` item for the settled generation, so a valid decision never strands the lot. A test covers a Check again that settles before the original item is acknowledged. The acknowledgement points stay as today's: `read_inbox` acknowledges a lot's items when the next call names them as read, and live steering commits its accepted items when the turn settles successfully (`session-runner.ts:761`); a `match` item's mode applies in the same commit as its acknowledgement. When that commit unlocks unfinished work for a lot, it also persists a durable continuation for the session, whatever else is pending, dispatched once the active turn settles, since the runner today settles a session with an empty inbox and no open question (`session-runner.ts:761-790`). Tests cover a decision that is the session's last inbox item, and one acknowledged while a held peer lot's chat is still pending, after each of which the same session publishes under the new mode with no further message. A crash before the turn settles leaves its slot occupied, and the supervisor refuses to start with `agent_reap_confirmation_required` until the reap is confirmed (`agents/worker.ts:18-28`); recovery dispatches a committed continuation only after that confirmed reap releases the slot, and an unconfirmed reap keeps it waiting. A committed acknowledgement is durable: a lost response or interruption after it keeps the acknowledgement, the mode and the continuation. Deliveries not yet acknowledged, and steering not yet settled, are delivered again in order. ## State, authority and failure behavior

| Concern | Handling |
| --- | --- |
| InvenTree unreachable during Match | The match state reads "couldn't search"; stages don't start; Check again retries |
| Search result changes after a decision | Pass 3 blocks approval only for its listed findings (a candidate Part or stock the outcome didn't cover, whether created or newly matching, an approved original contribution, or an identity that no longer fits); other changes need no new decision |
| Amendment conflicts with Examine or a human value | Not merged; a question settles it |
| A paused identify lot whose decision skips research | That lot's membership closes as finished and its identity amendment stays; the session continues with its other lots, and closes when none needs it |

- Migrations add the profile, the stage instructions, `processing_match`, the match question store, and the new outbox and inbox kinds.
- **Start before a lead exists:** once a configuration writes `/7` (PR-G2), an operator Start on a batch with no lead yet doesn't queue Research or Images; it waits for the `/7` lead and a stable identity, as stable-identity queueing does. - **Pipeline version by lineage:** from PR-A, the first PR that can write `/7` (behind the test-only switch), a batch follows its Examine lead's sealed input version. - **Upgrading a lead:** replacement today accepts only failed, cancelled, interrupted, unavailable or login-waiting sessions (`processing/session-replacement.ts:19-25`), so a drained lead that `finished` can't be started fresh. Task 11 adds an upgrade action, server and UI, that replaces a finished or idle earlier-profile lead with a `/7` attempt, keeping its history and pending evidence. - **Cutover (Mitch accepted these steps on 2026-11-23):** an actor's supervisor holds an actor-wide lock (`agents/worker.ts`), so `/3` and `/4` workers can't drain the same actor at once. Drain `/3` work before switching the actor's profile; pausing isn't enough, because paused attempts stay queued for a `/3` worker (`session-runner.ts:497-507`). The drain has three steps. First, a drain fence on the actor stops every boundary that creates or requeues a `/3` attempt: the Examine trigger's new lead (`processing/examine-trigger.ts`), `onLeadIdentity`'s successor queueing, a settling turn's requeue for pending items, Start, replacement and the resume sweep. A turn already running may finish; it settles without requeueing, and its pending items stay in the inbox. New evidence for a batch without a lead stays unprocessed, and the trigger's scan picks it up after the switch. Second, the drain is complete when no `/3` attempt is running, none is queued and claimable, and the actor's lane and agent slots are all free. Cancelling an attempt marks it `cancelled` before its process group is reaped, and an unconfirmed reap keeps its slot occupied (processing-agent-sessions "Cancellation and recovery"); the `/4` supervisor refuses to start while a lane or slot is occupied (`agents/worker.ts:18-29`), so the drain waits for normal settlement or a confirmed reap. Attempts left waiting for input, login or capacity aren't resumed under `/3`: after the switch, the upgrade action replaces a waiting or parked lead with a `/7` attempt that carries its history, answers and pending items, and supersedes waiting and parked successors, including Inventory, whose lots requeue through Match.
