## Unexpected challenges

- **2026-11-24T02:56+11:00, task 9 (PR-E):** The Capture fixtures' media clients refuse uploads on purpose, so the drop and paste checks and the demo used a throwaway copy of `GroupedCaptureProof` with a slowed in-memory upload, not committed. Headless browsers have no file manager or clipboard files, so drops and pastes were dispatched with a real `DataTransfer` of files. The installed Playwright has no matching WebKit build, so desktop Safari was not checked.
- **Task 2 (PR-A):** `screenshots:frontend` cannot capture `header-disclosure`: Public Sans never loads on that fixture, before and after this change. The other ten fixture pages are compared.
- **2026-11-24T03:14+11:00, task 4 (PR-B):** the revisionless-command audit (task 4.1) found three chat sends that name their session from the Processing read and carry no revision: Review Map's `TellExamine`, Records' Ask and Processing's sharper-photo request. TellExamine, Records' Ask and the sharper-photo request show the quiet "Updating…" reason and are checked again at dispatch. The session drawer's chat is not gated: the operator opened that session explicitly, and its own timeline read owns it.
- **2026-11-24T03:14+11:00, task 4 (PR-B):** no command on the Processing or Review keys writes its receipt with `setQueryData` today: Processing's commands, Pause and Review's answers already invalidate and reread. The rereads after receipt writes in PR-B are therefore those existing invalidations; Review Map's media receipt stays with PR-C.

- **2026-11-24T10:00+11:00, task 5 (PR-C):** moving Capture's media read onto `useFreshRead` changed test timing enough to expose a focus leak: a delete dialog closed because its workspace unmounted still ran `returnFocus`, which focused a same-id group region on the next page. `MediaWorkspace` now moves no focus once it has unmounted.

- **2026-11-24T16:34+11:00, task 12 (PR-G, fixed in the follow-up PR-G2):** the first live read on the real VM reported Claude correctly but Codex `unknown`/`timeout` on every one of five reads, each taking 1.1–1.4 s. The guest's share of the API's 2 s is 1.5 s, less 0.5 s kept for cleanup, and a Codex read had to spawn a fresh `codex app-server`, initialize and run `account/read` in that second. Measured on the real VM with Mitch's approval, one such read took 1498 ms cold and 1872 ms for a second read (`signed_in`, VM idle, 2 CPUs, load 0.45), so it can never fit, and it is slower under load. PR-G's tests used a fake account RPC that answered at once.

- **2026-11-24T03:41+11:00, task 11.1 (PR-F), rollout and recovery of the save receipt migration:** migration `0035` adds the receipt table and the per-scope pruning watermark. Every intake process checks the exact migration list at startup and quarantines a mismatch, so the API and the session worker must run the same build. To roll out:
  1. Drain and stop every intake process (the web entry point, the session worker and any runner), as for any intake deploy.
  2. Take a backup (`pnpm --filter @invimport/intake-server operations backup`).
  3. Migrate and grant with the new build: the deployment's provisioning step (`operations/deployment-provision.ts`) runs the migrations and then `grantProcessing`, which gives the API role its receipt privileges. The development stack does both when it starts (`dev/setup.ts`).
  4. Start every process on the new build only.

  If the rollout fails after step 3, recover forward (fix and redeploy the new build), or restore the step 2 backup and start the older build. The older build can't run against the migrated schema, and the migration is never edited or reversed in place.
