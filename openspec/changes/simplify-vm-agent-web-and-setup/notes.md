# Implementation notes

Implementation of `simplify-vm-agent-web-and-setup` (BI-017) started with PR-A (tasks 1 and 2). PR-B to PR-E remain.

## Changes to the plan

- **2026-11-19T16:40+11:00, task 1 (PR-A):** Review found that established public tunnels had no limit, so idle ones could crowd the provider out of the 64 MiB egress container. The `shared-vm-execution` delta gained "Public tunnels are bounded" (32 public tunnels, closed after two minutes without data either way; provider tunnels exempt) and the refusal reason `too_many_connections`.
- **2026-11-20T03:40+11:00, task 5 (PR-B):** `Diagnostics.tsx`, which the plan names, was removed by the settings-debug-mode work. The readiness facts now show in `LocalSetup.tsx` (Settings › Developer and the dev-mode popover) and in Copy debug info (`debug-info.ts`), so the web state is reported there.
- **2026-11-20T04:10+11:00, task 11 (PR-B):** No reader test case needed moving: PR-A already ported the reader's destination and non-public-answer cases to `test_guest_egress.py`, and its redirect test has no egress equivalent because a CONNECT proxy never follows redirects. The worker smoke test now sends the reader's old private and protected targets to each egress socket instead, and drops the public RFC fetch until a turn can have public pages on.
- **2026-11-20T04:40+11:00, task 5 (PR-B):** The readiness contract replaces `research` with `web` without a new API or live protocol version. A tab left open across the upgrade validates the old shape, so its local setup check shows as unavailable until it is reloaded. Moving the version was rejected: the frontend checks `api_version` and the live protocol as fixed literals, so a new version breaks an old tab the same way, and there's no reload-on-mismatch to trigger. The proposal's compatibility line now says this.
- **2026-11-20T04:40+11:00, task 6 (PR-B):** Claude's built-in tools are verified from the `system/init` frame, which the CLI emits only after it receives the opening message. The pre-input admission checks configuration and MCP tools. So a CLI reporting an extra built-in sees the opening before it is refused, though before any tool runs. This ordering predates the change and applies to host sessions too. Moving the check earlier was rejected because the control protocol's `initialize` response doesn't list built-in tools.
- **2026-11-20T05:40+11:00, task 4 (PR-B):** A queued `shared-vm-agent/2` attempt in a paused batch stays queued until the batch is resumed, and is retired then. Pause already keeps every queued session waiting, inbox intact, until Resume. Retiring attempts inside a paused batch was rejected because it would change what pausing means.
- **2026-11-20T05:40+11:00, task 11 (PR-B):** The live tools qualification checks the agent's own report that a turn without a web setting is refused a public page. The harness-controlled proof of the proxy's refusal is `tool-worker-smoke.sh`, which sends its own CONNECTs through each egress socket and asserts `403` with `destination_refused`; task 10's requalification runs both. Adding a second harness request inside the live turn was rejected because the turn's egress socket isn't reachable from the host test.
- **2026-11-20T09:30+11:00, task 3 (PR-C):** The `app-settings` delta was checked against the merged BI-016 text. Its Agent settings section differs only in the Web research paragraph and this change's two scenarios, and its deferred list only by dropping the web research switches, so no rebase edits were needed. BI-016 hasn't synced its specs yet, so the delta's header comment still names its version.
- **2026-11-20T09:30+11:00, task 3 (PR-C):** The settings use checkboxes with a Save, not switches. The design system's `Switch` is for settings that apply at once, and every other Agents subsection uses checkboxes before its Save. The spec's word "switches" is read as the two settings.
- **2026-11-20T09:30+11:00, task 3 (PR-C):** BI-015 (`complete-design-refresh-backend`) listed the web research switches in its scope. Its README and index entry now leave them to this change.

## Unexpected challenges

- **2026-11-19T14:41+11:00, task 1 (PR-A):** pnpm 12 refuses filtered task runs through a symlinked `node_modules` (`ERR_PNPM_UNSAFE_TASK_RUN_STATE_PATH`), so `pnpm lint` failed in a worktree linked to the main checkout's `node_modules`. The worktree uses its own `pnpm install --frozen-lockfile` instead.
- **2026-11-21T02:10+11:00, task 7 (PR-D):** The isolated real run found that `limactl list <name>` exits 1 for an instance that doesn't exist, rather than printing nothing as the tests assumed, so a fresh setup failed at the VM step. `vm:setup` now lists every instance and picks the named one, the fake world lists instances the same way, and Lima's and the provisioning scripts' own messages are forwarded with a prefix so a failed step shows its cause.
- **2026-11-21T02:10+11:00, task 8 (PR-D):** A Markdown edit under `intake-server/src` (the agents architecture document) changed the digest and caused a rebuild on the next run, because the app image copies that directory. This follows from hashing what the Dockerfiles copy without applying `.dockerignore`: the cost is an occasional unneeded rebuild, never a stale image.

## Decisions made during implementation

- **2026-11-19T14:41+11:00, task 4:** Mitch confirmed the plan's recommendation for retired attempts: a `shared-vm-agent/2` attempt that a `/3` worker finds fails with `agent_profile_retired`. Running `/2` attempts on the old tool surface was rejected.
- **2026-11-19T14:41+11:00, task 1 (PR-A):** The provider path skips a protected name that fails to resolve, instead of refusing the provider connection as the old tunnel did. Tailnet and other private names often don't resolve in the guest, and the spec keeps provider hosts reachable; public access still fails with `resolution_failed`. Keeping the old fail-closed provider behaviour was rejected because it would stop every session whenever one protected name is unresolvable.
- **2026-11-19T14:41+11:00, task 1 (PR-A):** The provider path keeps its IPv4-only lookup, which is unchanged behaviour. The public path resolves IPv4 and IPv6 and requires every answer to be public.
- **2026-11-19T15:00+11:00, task 2 (PR-A):** `turnPolicy()` opens public pages only for profiles in an allowlist, which is empty until task 4 adds `shared-vm-agent/3`, so a `/2` manifest carrying `web.public_pages` can't open them. Trusting the sealed field on any tool-worker profile was rejected because design D10 reserves web access for `/3`.
- **2026-11-19T15:00+11:00, task 2 (PR-A):** A policy that can't be written is a recorded `agent_turn_failed` before the provider starts (`native-outcome.ts`), rather than an exception outside the journal that left the slot waiting on worker removal.
- **2026-11-19T15:00+11:00, task 2 (PR-A):** The policy file limit is 16 KiB in both writer and reader, enough for 32 protected names of 253 bytes. The reader requires exactly the three keys, no duplicates and an integer version.
- **2026-11-19T15:19+11:00, task 1 (PR-A):** "Public" is decided by explicit IANA special-purpose lists for IPv4 and IPv6 as well as `is_global`, because Python 3.12's tables let `192.0.0.0/24`, `192.88.99.0/24` and `3fff::/20` through. Relying on `is_global` alone was rejected because its answer changes with the Python version in the runner image.
- **2026-11-19T15:19+11:00, task 1 (PR-A):** The proxy tries checked addresses IPv4 first, up to three, instead of only the first answer. The guest's Docker bridge has no IPv6 route, so a dual-stack site whose first answer was IPv6 would otherwise fail.
- **2026-11-19T16:04+11:00, task 1 (PR-A):** Provider and public DNS run on separate four-slot resolver pools with a 10-second deadline per CONNECT. A full pool refuses with `resolution_failed` instead of queueing, so stalled public lookups can't hold up the provider. A shared default executor was rejected because a burst of slow public lookups queued provider traffic behind it.
- **2026-11-19T16:04+11:00, task 1 (PR-A):** A protected name whose target lookup fails is still `protected_destination`, while a successful private answer stays `not_public`. Both orders were needed: the tailnet scenario wants `not_public`, and an unregistered subdomain of the InvenTree host must not look merely unresolvable.
- **2026-11-19T18:10+11:00, task 1 (PR-A):** Revocation is the point where a protected answer is published. Since the move to loop-owned state (2026-11-20T01:30 below), publishing aborts every affected stream before it returns, which also discards what the transport had buffered, so the relay makes no further write. Guarding asyncio's own nonblocking sends separately was rejected as unnecessary once the abort is part of the publication.
- **2026-11-19T18:40+11:00, task 1 (PR-A):** A protected name blocks every address it has answered with during the turn, not just its latest answer. Lookups from the provider and public paths can finish in any order, and keeping every answer means none is lost and no ordering is needed. Ordering answers by when lookups started was rejected because the actual start of a resolver-thread lookup isn't observable from the caller. A name that moves off a shared address keeps that address blocked until the turn ends, which fails closed.
- **2026-11-19T19:30+11:00, task 1 (PR-A):** The last protection check before a dial and the start of the TCP connect aren't one atomic step. A protected answer published in that instant can let a handshake reach the address. The check after the dial then aborts the connection before any byte is relayed. Making the check and the start of the connect one step was rejected because it means opening sockets by hand in place of asyncio's connection setup. The handshake carries no agent data.
- **2026-11-19T19:55+11:00, task 1 (PR-A):** A protected lookup that outlasts a public request's DNS deadline refuses that request with `resolution_failed`, but doesn't latch the turn. The lookup keeps running on its resolver thread. A final failure latches the turn when it arrives, and a late success adds its addresses to the blocked set. Latching on the deadline was rejected because a slow resolver isn't a name that doesn't resolve, and it would close the web for the rest of the turn.
- **2026-11-19T20:40+11:00, task 1 (PR-A):** A public CONNECT refused by its form, such as a wrong port or a private suffix, runs no DNS and publishes nothing, even when it names a protected host like `inventory.internal`. Form checks stay DNS-free so a malformed request can't take a resolver slot. Every CONNECT that does resolve refreshes all protected names. Resolving an exact protected name here as well was rejected, because the request is already refused and the next resolving CONNECT refreshes that name anyway.
- **2026-11-19T21:30+11:00, task 1 (PR-A):** A turn keeps at most 1,024 protected addresses. A protected record that rotates past that bound fails the turn closed: every tunnel, provider included, is revoked, and every later request is refused with `resolution_failed`. Evicting older addresses was rejected because it would unblock an address a protected name had used. Refusing only public requests was rejected because the provider could then reach an address that went unrecorded.
- **2026-11-19T23:10+11:00, task 1 (PR-A):** A destination whose DNS answer has more than 32 distinct addresses is refused with `destination_refused` before any address is watched or dialled. Setup watches every answer, so without a cap one request could allocate state for thousands of addresses. Trimming the answer to the first 32 was rejected, because an address left out could become protected without the request seeing it.
- **2026-11-20T00:30+11:00, task 1 (PR-A):** A CONNECT to a protected name is refused because of the name, so its reason comes from the name rather than from DNS timing. It is `not_public` when that name's own answer held a private address, `resolution_failed` once a protected lookup has failed this turn, and otherwise `protected_destination`, including while the name's own refresh, or another one, is still running at the deadline. Reporting `resolution_failed` for an overdue refresh in this case was rejected: the request would be refused whatever the lookup returned, and the stalled-lookup case was already required to stay `protected_destination`.
- **2026-11-20T00:50+11:00, task 1 (PR-A):** A public request's DNS deadline is the moment its wait on the protected refreshes returns. A refresh that lands between the timer firing and the wait resuming counts as on time, and its answer is checked like any other. Timestamping each publication against a separate clock was rejected: it only moves the boundary by the event loop's scheduling delay, and the answer has arrived and been checked either way.
- **2026-11-20T01:30+11:00, task 1 (PR-A):** After 55 review rounds, the egress was refactored so the event loop alone owns the protected addresses, the failure and overflow latches, the in-flight refreshes and the open tunnels. Resolver threads now only run lookups and hand their answers back. Most findings from round 26 on were orderings between a resolver thread publishing and the loop deciding. Each new lock moved the boundary instead of removing it. With one owner, a decision made between two awaits sees one consistent state, and a publication revokes and aborts every affected tunnel before any other coroutine runs. Ten tests that exercised lock boundaries that no longer exist were removed, and one test now checks that a publication revokes every affected tunnel before it returns. The spec also no longer fixes which reason a request reports when several apply at once. Continuing to add locks was rejected: the review loop showed no sign of converging.
- **2026-11-20T02:30+11:00, task 1 (PR-A):** Provider tunnels have their own bound of 64, separate from the public cap of 32 and still exempt from the idle timeout. Without it, a worker could hold enough provider connections to exhaust the egress container's memory or file descriptors and cut off its own provider. Counting provider tunnels against the public cap was rejected because a public burst could then block the provider.
- **2026-11-20T09:30+11:00, task 3 (PR-C):** Agent settings carry the two values as one `web` object, `{ public_pages, prefer_datasheets }`, the same shape as the sealed input, stored in two new columns (migration `0034`) that default to on, so a row saved before the migration reads them as on. The input schema version is unchanged (`bench-intake-input/6`), since BI-016 didn't bump it.
- **2026-11-20T09:30+11:00, task 3 (PR-C):** Profiles without web access seal `web` explicitly as both off, rather than leaving it out, so every new attempt's input says what it ran with. Synthetic sessions carry no agent settings and seal none.
- **2026-11-20T09:30+11:00, task 3 (PR-C):** Settings › Agents reads readiness to decide whether the profile has web access. Until readiness answers, or if it fails, the settings stay usable: disabling them on an unknown state would hide the saved values for no reason, and saving them changes nothing for a profile without web access.
- **2026-11-20T13:30+11:00, task 3 (PR-C):** `DisabledFeature` always showed "Coming later", which is wrong for settings that work under another profile. It and `SettingRow` take an optional badge, and Web research shows "Not for this profile". Every other deferred row keeps "Coming later".
- **2026-11-21T09:00+11:00, tasks 7 and 8 (PR-D):** The test harness reused from `dev-vm.test.cjs` is the injected `exec(command, args, options)` that resolves with standard output and rejects on failure. `dev-vm-setup.test.cjs` builds a fake guest behind it; host pairing and key files are real files in a temporary directory, and Git runs for real so the digest is the checkout's.
- **2026-11-21T09:00+11:00, tasks 7 and 8 (PR-D):** The checks and steps live in `tooling/dev/vm-provision.cjs`, the digest in `tooling/dev/runner-digest.cjs`, and `vm-setup.cjs` holds the setup order, the `pnpm dev` refresh and the command entry. The operator key rule is in one script, `bridge/operator-key.sh`, which both personal scripts call; `vm:setup` checks the same rule in Node before running any of them. `personal-codex.sh` now always takes the key file argument.
- **2026-11-21T09:00+11:00, task 8 (PR-D):** The refresh checks the operator key before it rebuilds or loads anything, not only before reprovisioning, as D9 orders it. With the VM unmanaged, `pnpm dev` compares only the local runner image's label, so it never touches a VM it doesn't manage.
- **2026-11-21T09:00+11:00, task 8 (PR-D):** The digest picks files the way Git does (tracked, plus untracked files `.gitignore` doesn't exclude). The Dockerfiles' own `.dockerignore` files are hashed, so a change to them invalidates the digest, but they don't filter the file list: a file Docker ignores can change the digest without changing the image, which only costs a rebuild.
- **2026-11-21T09:00+11:00, task 7 (PR-D):** Setup and refresh failures print their code with what they concern (the step, service, tool or both paths), through `failureLine`; `pnpm dev` uses it for these errors instead of the bare code.
- **2026-11-21T10:30+11:00, tasks 7 and 8 (PR-D):** After the first review: `vm:setup` boots the VM first and checks the pairing and operator key before it builds or writes anything, so a mismatch stops the run with nothing changed. D8's table lists images before the VM; checking identity first needs the guest, so the order changed. A pairing also has to match: the host's `ca.pem` must equal the guest's, so certificates from another pairing are refused. `operator-key.sh` now creates the key itself, only when both sides are absent, refuses an empty key or a host key without a guest key, and installs without replacing a guest key that appeared meanwhile.
- **2026-11-21T10:30+11:00, tasks 7 and 8 (PR-D):** A guest service container is accepted only when every bind mount it has is inside the configured guest directory; one that mounts another installation's directories stops the run with `vm_guest_service_conflict` and is never replaced. Each provisioned service is checked as running on the current image and origin two seconds after its script returns, since `docker run --detach` returns before a service could fail. The runner image carries `org.bench-intake.image-role=runner`, and a runner tag that names the app or guest tag is refused.
- **2026-11-21T10:30+11:00, tasks 7 and 8 (PR-D):** The first Ctrl-C during `vm:setup` stops the run after the current step and still stops a VM it started; the second quits at once. A failed VM stop fails the run, and the ready message prints only after cleanup. `pnpm dev`'s VM side is in `startManagedVm`, so a test can show the refresh runs before any relay and a failed refresh starts none.

## Open items

- **The paired-VM smoke wasn't run for PR-A.** The only paired VM is the operator's own, which tests must not touch. `tool-worker-smoke.sh` runs in task 10's requalification instead, with the operator's go-ahead.
- **The paired-VM smoke checks a web-off turn only.** `tool-worker-smoke.sh` confirms that the provider connects and a public host is refused through each egress socket, and that `/run/policy` stays out of the worker. Checking `curl` through the worker's own proxy after a policy turns web on needs a live `/3` tool turn, so it belongs to the task 10 qualification run.
- **Pending requests share one listener.** The egress accepts at most 16 connections still sending their CONNECT line, each for five seconds. Provider and public requests arrive on the same socket through the worker's proxy, so no capacity can be reserved for the provider before the line is read. An agent holding those slots can only stall its own turn.
- **IPv6-only sites are unreachable from tool turns.** The egress container sits on Docker's default bridge in the VM, which has no IPv6. The checks accept public IPv6 answers, but the connection fails. Enabling IPv6 on that bridge is deployment work outside this change.
- **Protected subdomains are learned only when asked for.** A refused CONNECT to a protected subdomain such as `api.inventory.example.com` publishes that subdomain's public addresses, so its aliases and any open tunnel to them are blocked from then on. The proxy can't list a protected name's subdomains, so a subdomain on its own address that no request has named stays unknown until one does. Protecting such hosts needs them listed among the deployment's protected origins.
- **The session worker recovers retained sessions before its scheduler launches.** It now validates the scheduler URL and confirms the database accepts its login before recovery. A login that connects but can't create the DBOS schema still fails only at `DBOS.launch()`, after recovery has interrupted retained sessions. That ordering predates this change. Fixing it means launching the scheduler before recovery while holding back workflow dispatch until recovery finishes, a restructuring of worker startup outside PR-A.
- **Codex's `shell_environment_policy.set` is unproven against the real CLI.** Admission expects `config/read` to report the proxy variables the adapter sets. The 0.166.0 bindings describe the setting, but only a live Codex turn shows whether `config/read` reports it; if it doesn't, admission refuses guest Codex sessions. Task 10's requalification checks it, and Codex `webSearch` items, on the paired VM.
- **The paired-VM checks for PR-B weren't run.** The Chromium start under `browser-policy.sh`'s seccomp profile, and a runner image built from a fresh personal guest image, need the operator's paired VM, which tests must not touch. Task 10's requalification covers both. The runner stage was built locally on an older base image, which proves the build context but not that `bench-web` is gone from a fresh image.
- **A key made on one side only stays a mismatch.** `vm:setup` writes the host key file and then installs it in the guest. If the run is interrupted between the two, the next run refuses with `vm_operator_key_mismatch`; deleting the host key file (when the guest has none) lets it start again. The spec's one-side rule was kept rather than installing a lone host key.
- **The management services' origin under the tailnet is unproven.** Setup binds them to the tailnet origin when `INTAKE_DEV_TAILSCALE` is on, as the spec and README say, while the tailnet proxy presents requests to the app as the loopback origin. Whether the credential panels work through the tailnet with that binding needs a live check.
- **Two checkouts building at once share the intermediate tags.** `bench-intake-app:dev` and `bench-intake-personal-guest:dev` are fixed tags, so two checkouts running `vm:setup` or a refresh at the same moment could build the runner from each other's base images. The runner's own digest label would still describe this checkout, so the result could be wrong without a later rebuild. Building one checkout at a time avoids it; per-build tags were left out of this change.
