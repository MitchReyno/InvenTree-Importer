## Decisions made during implementation

- **2026-11-19, task 9 (PR-D):** Every agent subsection's form goes through `useSubsectionForm`: it follows a newer load while untouched, keeps an edit through another subsection's save, and sends the loaded value for every field it doesn't own. An edit remembers the settings it started from, and a change to its own fields from elsewhere is a conflict found before sending, since the revision is shared across subsections. `useDirtyForms` holds the one navigation guard while any form is edited.

- **2026-11-19, task 6 (PR-C):** The model suggestion lists moved to contracts (`AGENT_MODEL_SUGGESTIONS`), because the server needs each provider's first suggestion for unsaved settings and the migration backfill.
- **2026-11-19, task 6 (PR-C):** An over-long description style or instruction text is refused by the contract (400) before the settings checks run. `invalid_agent_settings` (422) covers the provider and step rules, any model over 128 characters, and text PostgreSQL can't store unchanged (NUL or an unpaired surrogate).
- **2026-11-19, task 6 (PR-C):** The style is sealed as an optional `part_description_style` on the session input, so inputs sealed before it still decode; it is left out when no style is saved.
- **2026-11-19, task 8 (PR-C):** The connection reader stays callable and gains `check()`, so existing reads and tests are unchanged. The check mutation lives in the shared header observations, so the server menu and Settings share one pending state.

- **2026-11-19, task 11 (PR-E):** `saved_at` is the saved file's modification time, which the rename keeps. The file holds the token as JSON with the InvenTree origin and target context it was checked against, and a load for another origin or context ignores it, so a token is never sent to a different InvenTree. The secrets directory must be a real, owner-only directory owned by the server's user, and must not overlap the served `frontend/dist`.
- **2026-11-21, review round 16 (PR-E):** The check now needs exactly HTTP 200, not any 2xx, and every listed entry must be a part with a positive integer `pk`.
- **2026-11-21, review round 15 (PR-E):** Check and save classified the candidate's probe as the status pill does, from the status and content type alone, so a 200 whose body failed part-way could replace a working token. It now sends one probe and saves only after reading the whole part list answer (bounded in size and time) and finding `{results: [...]}` or a plain list.
- **2026-11-20, review round 14 (PR-E):** macOS gives one directory two real paths (`/Users/…` and `/System/Volumes/Data/Users/…`), so the published-directory checks at startup and per static request now compare device and inode along the ancestor chain as well as path strings. A link target containing `..` is refused, since `path.resolve` would collapse it lexically rather than as the filesystem does.
- **2026-11-20, review round 13 (PR-E):** Checking the path as written and then resolving it separately left a gap between the two, and a trusted link could lead through an unchecked one. Startup now opens the secrets directory from the root one component at a time, checking every directory before entering it and every link before following it, and making missing components with an exclusive mkdir. The write-bit rule now applies to directories only, since Linux reports every link as 0777 and would have refused a user's own link on the Ubuntu CI job. The Linux path is reasoned through and left to that CI job; it wasn't run locally.
- **2026-11-20, review round 12 (PR-E):** The configured secrets path is now checked as written before any link in it is followed, so a link another user planted at or above it is refused rather than followed to a store they chose. The launcher no longer creates the directory; the API creates and checks it. A test can't create a link owned by another user without root, so the tests plant one under a directory others can write instead.
- **2026-11-20, review round 11 (PR-E):** Only a lock with a verified dead owner is recovered; an absent lock is claimed again and an unreadable one fails closed. Missing components of the secrets directory are created top-down and every ancestor is rechecked once all exist. A concurrent-claim test then failed intermittently: deleting a lock in place briefly leaves an empty directory, which macOS lets another starter's rename replace, so locks are now renamed aside before deletion; 20 repeated runs then passed.
- **2026-11-20, review round 10 (PR-E):** The ancestor check refused every macOS access list, including the `deny delete` on home folders, so the API couldn't start with the launcher's default directory; the tests had only used the temporary directory. It now refuses only entries that grant access, and skips ancestors not yet created, and all seven development state roots on this machine pass. The recovery lock no longer expires, so a paused recovery can't be overtaken; one left by a crash needs removing by hand with no server running. The browser's unobserved state also clears the old version.
- **2026-11-20, review round 9 (PR-E):** Stale-lock recovery goes through a recovery lock taken with an exclusive mkdir; its holder removes the lock only if it still names the dead owner it saw, and a starter that can't take the recovery lock is refused. The concurrent-recovery test can't force the exact interleaving in one process, so that is covered by inspection. The API token row now says approvals use the approval runner's own credential.
- **2026-11-20, review round 8 (PR-E):** The secrets directory is resolved once at startup and that path is used for every check, the lock and each file operation. The lock is a directory holding the owner's PID, placed by one rename so it is never seen empty; a stale lock is moved aside by a rename only one starter can win, and the release runs once and removes only its own lock. Node has no portable advisory file lock, so this is a PID lock rather than an OS lock.
- **2026-11-19, review round 7 (PR-E):** Startup refuses a secrets directory whose ancestors another user could change, and each server claims its store with a lock file for its lifetime, so two API processes can't hold different tokens over one directory. The scoped connection reader drops an answer that a token change overtook during its final context check.
- **2026-11-19, review round 6 (PR-E):** On macOS the store also refuses a secrets directory or token file with an access list, which mode bits don't show, and checks a new temporary file before writing. The Vite guard checks every candidate its static handler tries. A token command advances the browser's check counter as soon as its receipt arrives, and a check is compared again just before it publishes; the same-moment test can't force a receipt to land during that final cancel, so that interleaving is covered by inspection. Every remaining Vite path needs a link planted in the checkout by the same OS user, who can already read the owner-only file, so the guard is defence in depth rather than a boundary against that user.
- **2026-11-19, review round 5 (PR-E):** The echo check is an explicit transport option for the app's reads and the candidate probe only, so the approval runner's create and verification outcomes are unchanged. The Vite guard also checks the `index.html` a directory request would be answered with.
- **2026-11-19, review round 4 (PR-E):** The read transport ends any response body that contains the token its request sent (raw or JSON-escaped, across chunks) with `target_echoed_token`, which covers catalogue, record and probe reads alike. A target that spells the token with `\u` escapes is not caught; that is a hostile InvenTree, which already holds the token it issued. The Vite guard runs again after the HTML fallback. The masthead's refused-token line names the token's source.
- **2026-11-19, review round 3 (PR-E):** A secrets directory inside the repository checkout is refused too, since the Vite dev server can serve any workspace file. Vite has no public directory and refuses any request whose real file is the token, whatever name the request used. A `version` string from InvenTree that contains the token the probe sent is dropped, so a hostile target can't echo it into connection status. A confirmed command's source stays shown until a read made after it reports one.
- **2026-11-19, review round 2 (PR-E):** The static-file handler checks each request's real path against the secrets directory, and the Vite dev server denies the token file names, since an `INTAKE_SECRETS_DIR` inside the workspace could otherwise be served through `/@fs`. A confirmed command shows its token source at once, before the next read arrives. A status request retries once after a reset and then answers unobserved.
- **2026-11-19, review round 1 (PR-E):** A rename or unlink is the commit point, and the directory flush after it is best effort, so the file and the holder can't disagree after a late failure. A second command while one runs is refused with `credential_change_in_progress` rather than queued past its caller's deadline. Both commands check the current target context. The browser sends token commands as plain calls instead of TanStack mutations, which would keep the token as mutation variables in the shared cache.
- **2026-11-19, task 11 (PR-E):** Replacing the token needs a configured read target. Without `INTAKE_DEV_API_KEY` the app is in setup mode, bootstrap keeps depending only on that key, and the commands answer `setup_required`.
- **2026-11-19, task 11 (PR-E):** A reset of the connection reader counts generations, so a probe still running with the old token can't become the observation after a replace or revert; a read or check waiting on it probes again.
