## Unexpected challenges

- **2026-11-23T08:27+11:00, after #240:** With the cause kept, Mitch's next failed Examine session named it: `agent_frame_capacity`. Claude Code echoes every tool result into its stream-json output, so one delivered image puts about 1.7 MB of base64 on a single line, over the 256 KiB per-line ceiling `AgentChild` has had since #67 (set for sessions without tools); its 2 MiB per-turn ceiling would stop any long tool session too. The original 4 MB photos failed the same way, so this, not the provider's image limits, is the most likely cause of the earlier failures. Claude in a VM tool worker now reads with 4 MiB per line and 512 MiB per turn, the latter as a runaway guard, and `strictJson`'s largest explicit limit rose from 2 MiB to 8 MiB to parse those lines. Codex keeps the default limits: it reports image views by path, and its adapter holds every notification until the turn ends. Parsed frames waiting to be read are capped at 8 MiB, since a parsed frame takes many times its wire size in memory and the worker has 640 MiB.

- **2026-11-23T04:07+11:00, after PR-B (#239):** Mitch's Examine sessions on the merged code still failed as `agent_turn_failed` with no provider error. Either the failure was not Claude's own, or the final frame was lost and the host settled from the outcome-only journal; the record can't tell which. The tool worker and the guest keep refusals, login failures and `resume_unavailable` as their own outcomes, but map every other typed code (such as `agent_protocol_invalid` or `agent_result_missing`) to `agent_turn_failed`, and the worker logs nothing. Both frames now carry that specific code as `cause` (`agent_unknown` for an untyped error, never its text); each receiver keeps it only if it is a registered failure code, and the host stores it among the diagnostic's causes. A turn settled from the journal keeps no cause, as it keeps no provider error.

- **2026-11-23T00:08+11:00, task 5 (PR-B):** Review found that `shared-vm-agent/3` runs the provider in a separate tool worker, whose outcome frame reached the guest supervisor as a bare outcome; a turn failure even fell through to a generic `tool_worker_refused`. The mapping moved to `shared-vm/worker-outcome.ts`, used on both sides of the worker socket, so the provider error crosses it and is re-checked by the supervisor. Codex `error` notifications with `willRetry` no longer end a turn.

- **2026-11-23T00:02+11:00, PR-A:** A process tier was still running in the PR-A worktree when the commit was amended, and its serial `dev-stack` test had temporarily appended invalid TypeScript to `intake-server/src/dev/listen.ts`, which `git add -A` committed and pushed to #238. The file was restored from `interactive-app` and force-pushed before CI or merge; parallel work now uses a separate worktree.

- **2026-11-22T23:32+11:00, task 2 (PR-A):** Review found that bounding pixels didn't bound bytes: a detailed 1,650 px PNG was about 8 MB, over Claude's 10 MB once base64-encoded and over the 2 MiB relay frame. Every delivery now has a 1.25 MiB cap, with PNG then falling JPEG quality. Review also found that the merged path checked removal only before the read, where the old original path checked it at the read; removal is now checked again after encoding. Spec, design and tasks updated.

## Decisions made during implementation

- **2026-11-23T00:16+11:00, task 4 (PR-B):** A Claude login failure keeps the kind `authentication_failed` but no result type or HTTP status: the adapter settles `agent_login_required` at that assistant message, as before. Waiting a bounded time for a later result was rejected because it delays every login failure to add two fields to a case the kind already names.
- **2026-11-23T00:16+11:00, task 5 (PR-B):** A browser tab left open across the upgrade rejects a diagnostic carrying `provider_error`, since contract objects are closed, and shows "details unavailable" until it is reloaded. A versioned endpoint was rejected for the same reason as the readiness change in `simplify-vm-agent-web-and-setup`: the frontend checks the API version as a fixed literal, and this panel is debug-only.

- **2026-11-23T00:02+11:00, task 4 (PR-B):** `http_status` comes from Codex's `httpConnectionFailed`-style kinds and from Claude's result `api_error_status`, which Claude reports when it gives up on an HTTP error such as 529. The kind lists are the values read from Claude Code 2.1.319 and codex-cli 0.166.0; a newer CLI's new kind is retained as `unknown` until the lists are updated.

- **2026-11-22T22:56+11:00, task 2:** A lot session's pinned derived versions stay fetchable: the lead session's originals-only filter now applies to Examine only, since the merged path would otherwise have refused derived versions the old original branch served. ## Open items

- **Task 6.3 was not observed live.** No lot session has been seen fetching a 6144 × 8160 original on the VM, and no failed turn has shown a live provider error; both are covered by tests only. Accepted by Mitch on 2026-11-23.

- **Output limits for other image routes and for parsing.** `shared-vm-agent/1` sessions also receive `fetch_evidence` images over MCP but keep the 256 KiB line limit, like host sessions. And a 4 MiB line of many small JSON values could still take a few hundred MiB to parse; Claude's output echoes tool results the app supplies, so the per-line limit was lowered rather than a structural parsing budget added. Found reviewing the frame fix, 2026-11-23T08:42+11:00.

- **Host Claude tool sessions keep the 256 KiB line limit.** A `native-agent/2` session on the host also gets `fetch_evidence` images, so its echo of one would still fail with `agent_frame_capacity`. Only VM tool workers got the larger limits; the host profile is expected to be retired with BI-010. Found reviewing the frame fix, 2026-11-23T08:29+11:00.

- **No local test crosses the real tool-worker socket.** `worker-outcome.ts` is unit-tested on both sides and the host frame has a process test, but `tool-worker.ts` is an entrypoint with a fixed socket path, a provider proxy and a real CLI behind it. The live check showed a specific cause (`agent_frame_capacity`) crossing it; a live provider error crossing it has not been observed.

- **A JSON-RPC batch of several `fetch_evidence` calls can outgrow a VM relay frame.** The relay gives the larger evidence reply limit only to a standalone `fetch_evidence` request, so a batch whose images together exceed the default frame fails after the host has recorded delivery. This predates the change (the old path sent originals of up to 8 MiB), and the provider CLIs send single requests. Refusing batches that contain `fetch_evidence` is a follow-up. Found in PR-A's review, 2026-11-22T23:45+11:00.
