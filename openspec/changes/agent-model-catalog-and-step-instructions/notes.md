## Changes to the plan

- **2026-11-25T18:30+11:00, planning:** the plan PR's six read-only review rounds (GPT-6.2 Sol) reshaped the catalogue's sign-in handling (a guest-owned generation, a conditional publish and a `stale_sign_in` state), added task 7 / PR-F for multi-lot groups, and moved `sent_effort` to a dispatch report. Round 6's three findings were fixed without a further round; the PR description lists them.
- **2026-11-26, PR-A:** one migration, `0042_agent_effort.sql`, adds both `agent_provider_settings.default_effort` (task 1) and `agent_session.sent_effort` (task 2), since both ship in PR-A.
- **2026-11-26, PR-A:** the effort's shape is checked by the contract (`AgentEffort`) and a column `CHECK`, so a bad effort is refused as `invalid_contract` before `checkAgentSettings`, not as `invalid_agent_settings`. The design said "checked only for shape on save", which this keeps; only the error code differs from the model ID's.
- **2026-11-26, PR-A:** the `/4` input's schema takes `OneTurnAgentSelection`, which has no `effort`, as well as `nativeInputManifest` dropping it, so a one-turn input can't carry one even if a caller forgot to strip it.
- **2026-11-26, PR-B, task 3.1.1:** the second capture, through the guest's egress in a local test VM with no token, wasn't run. The first already answers the question: with a placeholder token and the network refused, the pinned 2.1.319's `initialize` lists only its five built-in aliases (`default`, `sonnet`, `fable`, `opus`, `haiku`) with unversioned names, where the networked read lists 14 entries. So the guest read runs with the turn's Anthropic-only egress, as the design allowed for; whether it also needs the token is left untested, since the guest always sends it. Both replies are test fixtures, and they hold no account detail.
- **2026-11-26, PR-B, task 3.1.3:** no shared-VM relay or tool turn passes an API key into the guest (`relay.mjs`, `tool-turn.sh`; `environment.ts` reads it from the guest process's environment, which has none), so both API-key modes keep the built-in list in the shared VM. Host profiles read them with the worker's own keys.
- **2026-11-26, PR-B:** the table adds `attempt_in` and `reading_in`, where the last attempt ran and where a running read runs, so after a profile change a list, a failure or a read from the other route isn't shown as this route's. It adds `generation_seq`, advanced whenever the worker observes a new sign-in generation (the first included, on the locked row), which a publish must still match, so a read that sampled the old generation before a poll saw the new one never becomes current. It also adds `refresh_seq`, so a refresh requested during a read is kept for the next one rather than cleared by it, `reading_since`, for the API's `reading` state, and `read_in`. The API answers `read_in` (`vm` or `host`) so the card can say where a list was read, and the refresh answers a receipt with the authentication and stale flag.
- **2026-11-26, PR-B:** `request_model_catalog_refresh` is a `SECURITY DEFINER` function owned by the migration's owner, since the runtime roles are made per deployment, with `EXECUTE` granted to the API role only. The design said it would be owned by the worker's role; the effect is the same, and the runner role can't call it.
- **2026-11-26, PR-B:** the worker listens for `bench_model_catalog` on the provider status listener's held connection rather than a connection of its own, since the runner role's connection limit leaves none to spare.
- **2026-11-26, PR-B:** a reply discarded for a sign-in change is read again at most three times; after that the attempt is recorded as `unavailable`.
- **2026-11-26, PR-B:** Claude's catalogue read runs in a third container, `bench-claude-catalog`, not in its management process as the design put it. The management container needs a network for its published port, so a CLI started there could reach past the Anthropic-only egress; the catalogue container has `--network=none` like a turn's, the store and egress read-only, the pairing identity, a 64 MiB `/tmp`, 512 MiB and 128 processes. `vm-provision.cjs` and the relay know it. Codex's read stays in its management process, under the account lock, as its account checks run.
- **2026-11-26, PR-B:** the API answers the built-in list for a mode the configured profile can't read (`catalogRoute`), so a list stored under an earlier profile, such as a host API-key list after a move to the shared VM, is never served. The shared-VM spec's API-key scenario now says so.
- **2026-11-26, PR-B:** each subscription relay carries two catalogue connections, so the 60 s generation poll runs beside a read of the same provider instead of waiting up to 20 s behind it. The poll also covers a disabled provider whose list the API still serves.
- **2026-11-26, PR-B, task 3.2.3:** the Codex sign-in change waiting for a catalogue read is a unit test over `CodexAccount` with a recording RPC (`shared-vm-codex-catalog.test.ts`), not a process test: the order of the shared read's reap and the exclusive change is what it proves, and no relay is involved.
- **2026-11-26, PR-C:** the failed read's note and Try again, the built-in and earlier sign-in notes, and the "Older models (N)" toggle are entries inside the picker's list rather than a banner with a button: a button inside react-select's listbox can't be reached from the keyboard. `SearchablePicker` gained `formatOptionLabel` and `keepsMenuOpen`, which keeps the menu open, and the search, when Try again or the toggle is picked; pickers that don't pass it behave as before.
- **2026-11-26, PR-C:** `POST /api/v1/agents/models/refresh` takes an optional `authentication`. The sign-in dialogs change the subscription sign-in whatever method is saved, so they name `subscription`, and a token replaced while the API key is saved marks the subscription's list; switching back then shows it as from an earlier sign-in. Without it the request reads the saved method, as before. The design's request shape was `{provider, invalidate?}`.
- **2026-11-26, PR-C:** a step on Default has an Effort select too, disabled and showing the default provider's effort, since the settings can't hold an effort for a step with no model of its own.
- **2026-11-26, PR-C:** picking a model resets the effort only when a list read under the current sign-in says the model lacks it. A typed exact ID, a model from the built-in list or from an earlier sign-in's list, or a list for another sign-in method keeps the saved effort, since nothing current says it lacks it; picking the model already chosen changes nothing.
- **2026-11-26, PR-C:** a switch of a provider's authentication sends no refresh request, though the design listed it among the triggers: the request reads the saved authentication, so it would have to wait for the save, and the worker's next pass already reads a list for an authentication it holds none for. Check again, Try again and the sign-in dialogs do request one.
- **2026-11-26, PR-C:** the card's line follows the spec's wording, without the CLI version the R4 board showed, and the "Not accepted" warning stops after "takes no “Extra high”", without the board's guess at the level the CLI would run instead.
- **2026-11-26, PR-C:** a saved model the read list doesn't hold is named from the built-in list when it is there ("Opus 4.6"), else by its ID, as the spec's scenario shows it; while the first read runs it shows by its ID.
- **2026-11-26, PR-C:** on a phone, Effort sits under the model picker, so the model's name keeps the row's width.

## Unexpected challenges

- **2026-11-26, PR-A, task 2.1:** Codex 0.166.0 describes `TurnStartParams.effort` as overriding "the reasoning effort for this turn and subsequent turns". This does no harm here: a session resumes only its own attempt's thread (`agent_session.native_session_id` belongs to the attempt), and every turn of an attempt sends the same sealed effort or none, so no turn inherits another attempt's override.
- **2026-11-26, PR-B:** the pinned Claude CLI answers its offline alias list without any sign of failure. The worker refuses a reply that names no model by its exact ID, which the offline list never does and the networked one does, so a failed egress keeps the last list as a failed read. The live check (task 6) should still confirm the full list arrives in the guest.
- **2026-11-26, PR-B:** Codex 0.166.0's `model/list` in API-key mode answers offline from its built-in catalogue, which also lists `gpt-5.5`; the ChatGPT list doesn't.

## Decisions made during implementation

- **2026-11-26, PR-A:** `default_effort` is optional in the settings DTO (absent is Default) rather than a required nullable field, matching the step's optional `effort` and keeping clients that send the whole settings object valid; the column is nullable. `sent_effort` appears in the session history attempt only, absent while none was sent; the session list and header reads are unchanged.
- **2026-11-26, PR-A:** Claude's effort counts as dispatched once the opening is written to a process started with `--effort`, which comes before its `init`; Codex's once the `turn/start` carrying it is written, after `onStarted`. In the shared VM the guest reports it in a `sentEffort` frame, and the coordinator refuses any value other than the sealed one.
- **2026-11-25T15:02+11:00, planning:** step instruction edits reach only work queued after the save, not running sessions. BI-022's implementing session suggested delivering an edit as an `instruction` inbox item; that kind is bound to a batch's saved `capture_instruction`, settings are global so one edit would wake finished sessions in every batch, and the approved board keeps running sessions on their text. Recorded as an open item for Mitch.
- **2026-11-26, PR-B:** a folded Claude model takes the name of its exact entry, else of an alias other than `default`, else its ID; `default` marks the model the CLI's `default` alias resolves to. Anthropic's models API efforts are the `capabilities.effort` levels marked supported, in the reply's order.
- **2026-11-26, PR-B:** a host API key's generation is `no-api-key` while none is configured, so removing a key marks the list stale rather than leaving it current. A turn's CLI version requests a read once per version, and never for a list from a models API, which has none.
- **2026-11-26, PR-B:** a Claude read across a token change answers `unavailable` in the guest; the dialog's invalidation, or the generation poll outside the dialogs, then requests the reread.
- **2026-11-26, PR-C:** the Processing pill warns about the model a step's new sessions run: its own while its provider is on, else the default provider's default model, as the selection resolves. It shows on every agent step, Inventory included.
- **2026-11-26, PR-C:** a list is used only for the sign-in method the settings show: while the server's answer is for another (a switch not yet saved, or saved but not read again) the picker shows that provider as reading its models, with the saved model by its ID and Effort waiting, and every confirmed settings save reads the catalogue again.
- **2026-11-26, PR-C:** when the browser's own catalogue request fails or can't be sent, the pickers show its last answer, or the built-in list, and raise no warning, since nothing says the list is current. A provider's failed read still warns from its last good list, which is from the current sign-in.
- **2026-11-26, PR-C, Mitch's decision after review round 8:** if the server refuses a sign-in dialog's invalidation, the browser doesn't resend it. The dialog stays open saying the model list may be out of date for up to a minute ("Token saved. Claude's model list may be out of date for up to a minute.", or Codex's), and the server's 60 s sign-in generation poll marks the list, as for a change made outside the app. Rounds 1 to 8 had built a browser-side fence that kept the list marked and resent the request until acknowledged; round 8 showed it couldn't both keep the old list from showing as current and recover once the new list landed without a sign-in generation from the server, so it was removed. A card shows only the newest sign-in change's outcome, across visits to Settings › Agents. While a ChatGPT confirmation is being recorded the dialog says so and holds its key field and Disconnect, and then closes; a confirmation never closes a dialog opened again since.
