# Frontend architecture

This document describes the implemented manual intake application under `frontend/`. Read the [shared architecture](../ARCHITECTURE.md), [shared guidelines](../CODE_GUIDELINES.md) and [frontend guidelines](CODE_GUIDELINES.md) for its boundaries and change policy.

## Current application

React and TypeScript run in a Vite browser application. `index.html` loads `src/main.tsx`, which mounts `App` under React StrictMode. `src/App.tsx` uses the validated generated contracts client against the same-origin Fastify API. Bootstrap supplies development-mode attribution and an ephemeral CSRF token, never an inventory key. `App` builds the optional feature clients (agents, attention, catalogue, media, operator review, processing, records) from that token and provides them through `components/clients/ApiClientsProvider.tsx`; components read them with `useApiClients()` from `clients/api-clients.ts`, and an absent client means the feature is unavailable. Leaf components that take an explicit `client` prop keep it. `Batch` provides its capture commands (`edit`, `observe` and the stage `reload`) through `components/batches/BatchCommandsProvider.tsx`; workspaces read them with `useBatchCommands()` from `capture/batch-commands.ts`, which throws outside a batch. Leaf editors keep explicit command props, and an absent `edit` prop still means read-only. Retained batch list/create/read/edit/archive commands store state in PostgreSQL, not localStorage. A hash URL retains batch and selected subject/editor; refresh loads saved server state. Closing the browser does not erase batches or notes.

`src/components/capture/CaptureWorkspace.tsx` coordinates the header, evidence column and Batch settings column, each in its own `.tsx` file. Batch list/detail components live in `src/components/batches/`; retained data/client types and pure display mapping stay in `src/capture/`. Capture has no Physical lots or Part proposals panes; manual subject create/edit, Part choice and attachment choice open in Review's focused `ReviewSubjectEditor`, which reuses `CaptureEditor` and the existing capture commands. Shared Part proposals never combine physical lots. Exact quantity and PK strings stay strings; notes visibly identify human provenance. Defaults and explicit lot selections retain unset/unknown/clear/inherit/set distinctions. Reading a configured target's existing Part/location creates an observation; selecting it is a separate human action. No browser command accepts a target URL, actor or inventory secret. Capture fields support manual quantity, location, existing Part choice, labels, links and append-only notes; retained media has its own boundary below.

Each save carries the loaded batch revision. A 412 preserves local inputs and displays current saved values; explicit discard/reload is required, never silent rebase or last-write-wins. A single dirty editor disables subject navigation/archive, with explicit discard. The app-owned navigation guard receives synchronous dirty callbacks from Capture and nonempty new-batch title/note forms. It blocks same-document links and hash/history route acceptance while retaining the mounted form and exact input; native unload is protected too. Save/create or explicit discard releases the guard. Transient review selections/archive filters do not lock navigation. A failed/uncertain save remains visibly unconfirmed; it is not blindly retried. Archive retains history and disables editing until explicit resume. Review and Changes use the generated manual client; Processing exposes retained jobs and questions through its retained coordinator and explicitly selected fixture/native profiles. Retained uploads and crop preparation are described below. Native provider sessions require a separately supervised worker; there is no Python runtime connection.

Capture lays the evidence card and the settings column side by side on the canvas's flex bases, wrapping into one column once both no longer fit; below `bp-compact` the Proposed lots glance moves under the capture tiles and `BatchSettingsPanel` folds behind a summary, its fields staying mounted so drafts survive. The panel holds one mounted RHF draft: the title, the batch notes, one Default location, supplier (No supplier, existing or new draft), the disabled purchase-order preview directly below supplier, Shared part tags and Custom instructions; Quantity mode is gone from the panel and per-lot exact quantities stay in Review. The batch notes field is drawn in the evidence card through a portal slot that `CaptureWorkspace` hands over, while the panel still owns and autosaves it. Write a note opens an inline append-only evidence note in the evidence column. Lot editors preserve explicit context overrides; Capture and Review label effective human context separately from approved inventory effects. Under Default location one line names the lots that override it, each linking to Review, which shows a lot's full capture context. The Review subject editor sets a shared Part's location for its lots, and each evidence group carries its own location control; both are application defaults, never inventory fields. Review's Location fact and table column name the source (lot, shared Part, evidence group or batch default) through the shared contracts resolver, and report disagreeing groups or unread group membership instead of falling back. Placement comparison and native 200%/360px/390px evidence are in [the settings qualification](https://github.com/MitchReyno/InvenTree-Importer/blob/e3ac646/docs/bench-intake/evidence/capture-settings/README.md).

Capture's editor and the separate `components/batches/NewBatchForm.tsx` use pinned React Hook Form. Native fields register directly; Controller adapts the existing quantity/reference controls without changing their modes or exact string values. `capture/editor-model.ts` owns initial values and command construction. Editor defaults remain fixed for the mounted selection, so newer snapshots do not reset a human draft. Synchronous event callbacks still feed the application navigation guard. The form package does not own revision authority, uncertain acknowledgements or payload-bound delivery keys; new-batch creation and Capture edits preserve revision/payload-bound retry intents independently of form submission state. After an unconfirmed edit, a changed payload requires explicit saved-state reconciliation; exact unchanged retries reuse the original key. The settings panel has no Save button: `capture/save-queue.ts` is a per-batch serialized owner for the `batch_settings`, instruction and logo-upload commands. Valid edits send after a 500 ms idle debounce or on blur, and freeze payload, expected revision and key per request; later edits are sent against the acknowledged revision. IME composition suspends every dispatch until it ends, and a disposed queue never dispatches. While a lane's request is unconfirmed, every newer draft is kept, including one equal to the old saved value. Conflicts and uncertain acknowledgements block further commands until an explicit keep, exact retry or discard-and-reload. A clean panel adopts newer saved values; a dirty one never resets. Editing needs a fresh scoped observation (the shared header connection read or the batch's capture read, succeeded within 60 seconds and not now failing) and an online browser; reconnection reads current state before admitting writes or exact retries. Evidence media, evidence note and settings commands do not overlap: each is fenced while another is unacknowledged, and settings stay paused after an evidence change until the read of its new revision is accepted (a failed read keeps them paused, with an explicit refresh). While disconnected, unsent drafts can be discarded locally; sent or unconfirmed requests keep their own recovery. A newly observed instruction version becomes that lane's saved baseline and text unless the lane holds a draft or an unacknowledged request; adoption never sends. Only the newest post-evidence refresh releases or fails the settings gate. Supplier and location observations apply only while their choice is the newest intent of a mounted field, against the form's current drafts. Typed tag text that has not been added keeps navigation protected. Dirty owners report clean only on unmount or confirmation; a replaced parent callback receives the current state.

`components/review/ManualWorkspace.tsx` coordinates retained reads driven by live hints, bounded polling fallback and explicit commands. Review presents physical-lot selection, human evidence and exact saved choices; selecting a shared Part never includes another lot. The first slice accepts at most ten selected lots. Changes › Ready to add shows the ticked and left-out lots, every record the preparation creates or uses, and the frozen plan digest. Its URL pins the preparation identity across polling/reload; removed or stale plans disable approval instead of substituting another latest plan. Replacement requires explicit choice. Selected/shared dependency changes require fresh review/preparation; unseen capture changes disable review until explicit reload.

Changes › Ready to add lists a new location or supplier among the records it creates, and a stock item under a location made earlier in the same run. Capture's new-location and new-supplier forms state that nothing is created from the form; a draft is created only after approval on a supporting target. Added names a confirmed new record by PK and keeps an uncertain one unresolved. Review's Location fact and the batch supplier context name a pending new-location or new-supplier draft ("created only after approval") instead of an empty or unknown value.

`components/changes/` displays Ready to add and Added (see Changes below), including original approval rounds and journal certainty. Approval and queueing are separate actions. Unknown outcomes have no create-again control; cancellation cannot undo an authorized request. Only server-advertised original-operation recovery is offered. App-wide activity is a bounded, explicitly truncated retained-run snapshot, not simulated progress. Commands carry neither browser authority nor inventory credentials.

Styling follows the [Bench Intake Design System](https://claude.ai/artifact/TbKY47cDmdA3Nuh2jufTmo). `src/theme/tokens.json` is its token file; `scripts/generate-tokens.cjs` generates `src/theme/generated/tokens.css` (light and dark CSS custom properties with `color-scheme`) and the typed `tokens.ts` map that module-scope styled-components read, so a theme switch needs no re-render. Frontend lint fails when the generated files are stale, when a documented text/ground pair is below its contrast threshold in either theme (`scripts/check-contrast.cjs`, also run by the build), or when a component uses a literal colour. The same check (`scripts/check-literal-colors.cjs`) fails on any literal spacing, radius, size, type, motion, layer, opacity or breakpoint value that equals a token meant for its CSS property; a value whose role has no token says so with a `literal-allowed: <reason>` comment. `src/theme/theme.ts` sets `data-theme` on `<html>` from the stored Light, Dark or System choice (`bench-intake.theme`) or the OS scheme, after an inline script in `index.html` has set it before first paint. Public Sans (variable) and IBM Plex Mono 400/500 are self-hosted through `@fontsource` packages imported by `GlobalStyle`, which otherwise contains only document/reset/font/focus defaults. Design-system components (Button, Pill, Banner, Tabs, SegmentedControl, FilterChips, DataTable with BulkBar, KeyValue with SourceChip, ProblemCard, ItemRow, RecordStatePill, TargetChip, ChangeSummary, StickyFooter, StatusTimeline, Dialog, Toast and the rest) live in `components/ui/` under the design system's names; screens render them rather than keeping their own copies, and every notice is a `Banner` inside an element carrying its status or alert role. Panels, headings and text primitives are in `components/ui/primitives.tsx`; form inputs and fields are in `forms/` (imported as `#/forms`). Styling-only state uses transient `$` props. The legacy stylesheet is removed. Layout/UX follows the primary [original HTML prototype](../docs/bench-intake/reference/bench-intake.html), [Capture](../docs/bench-intake/reference/03-capture.png), [Review workspace](../docs/bench-intake/reference/02-review.png), [Inbox](../docs/bench-intake/reference/01-inbox.png) and [phone frame](../docs/bench-intake/reference/10-phone.png); see the [reference index and historical limitations](../docs/bench-intake/reference/README.md) before the secondary derivative board. The [main specs](../openspec/specs/) and latest contracts override prototype simulations. Capture follows the original two-column hierarchy: evidence actions and groups on the left, Batch settings and Go to review on the right, one column on narrow screens. Review keeps queue/evidence/decision. No fake media or simulated processing/execution is added to mimic unavailable breadth. The batch screens follow the [redesign canvas](https://claude.ai/artifact/TFjujLEMdBcqdRUBbvJKRf); Changes replaces the original approval and results screens.

`components/masthead/Masthead.tsx` owns the brand header: the "Bench Intake" title with its `Dev mode` badge, the scoped status action slot and the optional child navigation slot over a faint dot grid. `ElectronicsCurrent.tsx` adds a decorative, `aria-hidden` canvas of isometric outline-style electronic parts drifting right to left behind the title. The pointer stirs nearby parts, and switches react to it. The canvas never fetches, writes or touches application state. Its scene logic lives outside the component tree in `src/electronics-current/`: palette, outline material kit, part builders by family, weighted catalogue, pure flow maths and the scene controller. The component feature-detects WebGL 2 before dynamically importing that scene chunk, so unsupported browsers and jsdom never download three.js and keep a plain masthead. `prefers-reduced-motion` renders a single static frame without an animation loop. Unmounting cancels a pending start, the loop, the resize observer and all GPU resources. The part count scales with masthead width; narrow screens dim parts under the text instead of hiding them.

`src/App.test.tsx` covers exact string emission, human attribution, archive/resume and concurrent-edit conflict through a jsdom/component boundary. Component tests alone are not browser or production-access qualification. `ManualWorkflow.test.tsx` adds exact selected/digest emission, explicit stale-display reload and unknown-result controls.

## Design alignment and evidence inspection

The shared masthead, `Dev mode` badge, status disclosures and batch header use compact spacing so working evidence appears earlier on desktop and phones. On narrow screens the labelled lot-filter strip scrolls within its own row, selection actions share two columns with wrapping labels, and desktop-only shortcut hints are omitted; safety/read-state notices remain visible.

## Review Lots and Map

Review › Lots opens on the first queued lot, so its evidence and details show without a separate step; each queue row's "Show" button changes the lot. The details pane starts with the lot's record chain (Part, Stock item, Location), a link to the lot's open Processing question when it has one, and a per-lot Mark reviewed that states why it is disabled. Exclude is shown disabled until record edits back it. Each problem offers fixes from `operator/problem-actions.ts`, on the lot itself or on the screen that owns them (Part choice, Records, Capture, the Map, or the lot's open question). The Workspace and Table share one selection and the URL filter (Needs answer comes from open Processing questions on the lot or its Part, `openQuestionsByLot`, and says when they are not yet read; there is no Excluded filter until Exclude exists); the Table may select beyond the Workspace's 10-lot approval cap for bulk edits.

Review › Map (`components/review/ReviewMapStage.tsx` and `ReviewMap.tsx`, model in `operator/review-map.ts`) shows evidence files beside active lots: a file supports a lot when it is linked to the lot, its Part, or a lot it was split or merged from (lineage from the operator review's retired lots, walked to the server's depth), or when one of its observed regions is in the lot. Once observations exist, each file lists its regions (active observations on its versions, labelled by their first non-empty marking or text) with the lot each supports. It flags files no lot uses and lots resting on one file. Its edits reuse existing commands: the media `link` edit to link or unlink a file, capture `add_lot` (with a note naming the file) then a link for "New lot from this", the capture edit `observation_same_item` for a region's "Same item as…" (offered among the regions of its own lot, with "Not the same item" to clear it; the lot's heading counts its items once with `lotItemCount` and says how many were seen twice), and the restructure dialog for split, merge and move, which are locked for lots already added and while the latest operator review is unread; until then the no-evidence flag and the unused flag on a retired lot's files say history is still being checked, and those files cannot start a new lot. Links through a lot's Part or an earlier lot show as such and are not unlinked here. Files sharing a name are numbered once over the batch's media snapshot (`evidenceDisplayNames`), so the Map, Review, Processing images and Capture agree, with identifiers only in a viewer (Review's Details, Capture's file viewer). Tell Examine (`TellExamine.tsx`) appears only while the batch is not archived and has an Examine lead session that is not cancelled (`examineLead`); it sends free text as chat to that session's inbox, not through the batch instructions command, and keeps the text when it is not sent.

## Review Records

Review › Records (`components/review/records/`) reads `GET /api/v1/batches/:id/records` through `records/useBatchRecords.ts`, keyed by batch revision. While a record the target already holds is open, `useExistingValues` reads `records/existing` and the detail shows an In InvenTree table beside this batch's values. A step's value reads with its source kind and agreement in words (`operator/value-evidence.ts`), as Examine's readings and a lot's observations do. A type rail lists each type's new, existing and to-decide counts; the list shows a type's records; the detail shows each value with "Set by you", the step that proposed it, or "Estimated by Examine" for an AI lot's quantity estimate, which is accepted or replaced on the lot, and what an edit reaches ("Applies to …, used by N lots"), from the shared `recordScope`. Editors send `record` capture edits: companies and templates map batch-wide, and a Part's name, description, tags, category (mapping or dropping each parameter), parameters and sourcing edit in place. A Part without a spec starts a new one through the `part` edit. `records/model.ts` checks an edit with the shared `applyRecordChange` before sending it, so a refusal names the Part; the server checks again. Each editor keeps its draft until a save is accepted, reports it to the navigation guard, and blocks opening another record until it is saved or discarded. A refused save's "Load current values, keep this draft" reloads without touching drafts; the batch's "Discard local edits" drops them. A field a step proposed offers Ask (`AskControl`) when that step's session works on the record's Part (first) or one of its lots and can still read messages, on a batch that is not archived; it messages the session's inbox and shows "Asked <Step>" until the field's value changes. Unsent Tell Examine and Ask messages, with their idempotency keys, are kept in `processing/pending-messages.ts` across leaving the page, and count as unsaved work only while their form is shown; discarding a record, or the batch's "Discard local edits", drops its Ask messages too. Without sessions there is no Ask. A proposed new manufacturer or supplier from a catalogue proposal, on a Part being created that has no company in that role, is a company record per Part that needs a decision, labelled "<name> for <Part>"; `ProposedCompanyEditor` shows `CompanyDecision` (its likely match, if any) and another observed company in the role, either of which sets that role on that Part with its proposed number. Every other catalogue value that cannot enter a spec comes from BI-006's `assessCatalogue` rule (in contracts), each with why it is not supported yet: a proposed-new category or a description that does not fit is explained at the Part's category or description field when the Part lists that field; values with no field of their own (such as a parameter the category cannot take, a company that is new on a Part not being created, a supplier with no SKU, a supplier price, or a reference no longer matching what was read) are listed under "Not supported yet", each with the agent's reason.

A new Part's record opens with "≈ Not reusing <Part>: <why>" and "Use <Part> instead" (the capture `part` edit setting that existing Part) when its step chose not to reuse one, held back while one of the Part's fields has an unsaved draft, and says under Category why it was chosen and the alternative considered. Records › Parameters (`ParameterMatrix.tsx`, model in `records/parameter-matrix.ts`) marks a template the category needs and a Part lacks as "Required here" with "! missing" and the step's reason, a value its sources disagree on with ◆, and gives each disagreement a row ("the label says 25 V; a distributor page says 35 V. Using the label.") with "Use <value>" (the parameter's `set_parameter` record edit, through the same checked save as a record's own fields and disabled while records are stale, refreshing or archived) and "Ask <step>" through `AskControl` when that step has an open session, its unsent text guarding navigation like a record's.

## Changes

`ManualWorkspace` still owns the manual commands, their errors and the pinned preparation; under Changes it renders `components/changes/ReadyToAdd.tsx` and `Added.tsx`, which replaced the old approval and results screens.

Ready to add lists reviewed lots without problems, with the shown preparation's lots ticked. Ticking or unticking one prepares exactly the ticked lots again, and approval stays disabled until that preparation is current (still in the workspace read); a preparation that is stale or already approved says so and is never replaced silently. With no preparation yet, the ticked lots wait for "Show what will change", so opening Changes never reads the target by itself. Lots left out link to the Review filter that shows why. "What will change in InvenTree" reads `GET /api/v1/preparations/:id/tree` once per preparation (`client.tree`) and shows it By type or as a Tree grouped by category or by location; `changes/model.ts` builds all three from the one node list, so their counts per state agree. `PreparationTreeView` follows the WAI-ARIA tree pattern (one tab stop, arrows move and expand or collapse, Home and End jump) and states each node's New, Update, Exists, Choose or Not ticked in text. An update lists its field changes ("Image · none → Image for …") in both views; a lot left out stays in the category Tree, dimmed, with its reason and a link to it in Review, and is left out of By type, the location Tree and Only changes. Until the tree is read, or without it, By type shows the preview's stock items, Parts and locations, and the Tree option is absent. By type rows link to their lot or Part record in Review. The sticky footer names the test target and "Approve N lots and add to InvenTree".

Added opens on an outcome strip (stock items added, records being checked, values InvenTree refused, and the test target), then each round (`RoundOutcome`) with links into InvenTree through the connection status's web address (`header/useTargetNavigation.ts` reads the header's cached connection read and never fetches it), pending preparations, lots not included and an activity log of rounds in approval order, each with the hour and minute its run's `approved_at` gives. An uncertain stock item is checked by its import reference and offers no create-again action; resume, inspect and attachment repair are the server-advertised recovery commands; a value InvenTree refused as invalid (`rejected` in the run read) says so, links to where it is set: "See in Review" for a Part value, Part attachment or stock item (its Part record or lot), "See in Capture" for a new location or supplier draft, and is not counted as being checked; a round held only by refusals says that it stays open and holds the batch's source, so a corrected value cannot be sent yet. One never sent is not marked. Links into InvenTree use its web UI paths (`web/part/<pk>/`, `web/stock/item/<pk>/`). Only the connection status, the Ready to add footer and the Added outcome strip name the test target; there is no app-wide disclaimer footer.

`tests/fixtures/changes.html` (`ChangesProof`) renders Changes from an in-memory manual client that prepares the ticked lots, approves and settles a queued round; nothing reaches an API, provider or InvenTree.

## Processing and Agents

`processing/source.ts` is the `ProcessingSource` adapter: step progress in counts, open questions with their step, subject, assumption and active lot, and sessions only for jobs with a `session_state`, each with its active lot and latest status line; it also names the Examine lead session and gives each lot's newest line (`subjectStatuses`). Session rows show the status line, Review's Lot details show the lot's agent line (`AgentLine`), and Capture's glance shows each lot's line, read by `processing/session-status.ts` from the processing snapshot. The adapter also builds the pipeline: the batch's Examine lead job, then each lot's Research, Images and Inventory cells (session work only) with how many of their proposals are stale or provisional. The Overview's Pipeline card (`PipelineRows`) shows Research ∥ Images → Inventory per lot; job cards label stale candidates with the reason and provisional ones while a question is open. The Examine step page adds `ExamineView`: every region the lead session read in each photo with the lot it belongs to, then each lot with its observations, the lead's candidates and their sources, and its quantity basis. Legacy Reading and Identifying jobs still render as job cards on Examine. `ProcessingWorkspace` keeps the data and command logic and renders the Overview (steps, sessions, Needs you, the batch instruction field, activity, links to Review and Changes) or one `StepPage` per step (state, questions, sessions, outputs, a link to Capture). A session opens in a drawer with its open questions, timeline and chat. The instruction field saves explicitly through the same `instruct` command as Capture and keeps its own navigation-guard source. Saving either the instructions or a question answer reloads Processing, so neither can save while the other has an unsaved draft. The field waits for the saved instructions, says when they are unavailable, and gives the archive as the reason they cannot change.

`components/agents/AgentSessions.tsx` is the Agents page: slots in use against the saved limit, the model for new sessions and how many sessions wait for the operator; filters for running, waiting, queued and finished today; sessions grouped by batch with names from a batch read, each group linking to its Processing. "Pause all agents" in the summary (with "Resume all agents" beside it while any batch is paused, since some can be paused while others run) and "Pause all" on each batch group (`PauseButton.tsx`) pause or resume through the agents client, and the shown state follows the next session read, so a refused change says so and leaves it as it was; an unfinished session of a paused batch reads "Paused". Processing's sessions card offers the same Pause all or Resume for its batch, read from the batch's processing snapshot, and says while it is paused. When the list says sessions are not supported, the page says the server's processing profile does not run agent sessions instead of showing an empty list.

## Batch navigation and attention

A batch has four tabs: Capture, Processing (Overview, Examine, Research, Images, Inventory), Review (Lots, Map, Records) and Changes (Ready to add, Added). `src/navigation/batch-route.ts` is the one parser and builder for `#<batch>/<tab>/<view>[/<subject>][?query]`; every in-app batch link uses `batchHref`. Old routes redirect with `location.replace`, keeping the rest of the path and the full query: `approve` → `changes/ready`, `results` → `changes/added`, `review/<lot>` → `review/lots/<lot>`, `processing` → `processing/overview`, and `reading`/`identifying` → `examine`. A legacy `#<batch>/<subject>` link opens Review › Lots (`#<batch>/review/lots/<lot>?edit=<lot>`, or `?edit=<part|add_lot|add_part>`). Redirects pass through the normal navigation guard.

`components/batches/BatchHeader.tsx` renders the title, counts, Archive or Resume, the four tabs and the active tab's second row. Every badge comes from one `GET /api/v1/batches/:id/attention` read (`attention/useBatchAttention.ts`, keyed by the batch revision): open questions and failed attempts on Processing and its steps, lots to check and decisions on Review, ready and failed or uncertain runs on Changes. `NeedYouPanel` lists the same items grouped by owning tab and closes once one is chosen. Step badges use the read's exact per-step counts, since its item list stops at 200. If the read fails, the header shows "Needs you unavailable" rather than nothing to do. The Records badge and the panel's decisions are the records waiting for a choice, one per record, each opening that record in Review › Records; the stage follows a link to a record unless a draft is open. The Changes tab opens bare Ready to add. `Batch` remembers the preparation last shown in this batch, whichever tabs came between, and the workspace opens it if it is still current, otherwise the newest. The choice replaces the history entry, so Back never lands on a route that redirects again. A preparation pinned in the URL is never replaced; if it is gone, the workspace asks for an explicit choice. `Batch` keeps the dirty-draft state, so Archive is disabled while a draft is unsaved.

`components/batches/Batches.tsx` presents a New batch action, a Continue card for the recent batch and an All batches card with search and Show archived, with tab links, retained thumbnails and workflow observations; revision numbers are not shown. A row says what the batch's agents are doing (`stageLine`: "Sorting into lots · N found so far", "Research · 3 of 5") in place of its lot count, and its evidence by kind under the state (`evidenceLine`); a row and the Continue card both count possible duplicates, and the card gives the same stage line. The recent batch appears only in its Continue card until searching, when it participates in matching results. Server-wide title search, archive inclusion and ten-row paging use one validated read. `BatchStageLinks` links each batch's four tabs; `BatchWorkflow` presents observations rather than command authority.

Capture shows each evidence file as an `EvidenceFileTile` (preview, lot count, note) inside its group; crop, rotation, download, byte identity, the note editor and lot links live in the file's viewer, which refuses to close only over its own unsaved note; while that note's save is unconfirmed, the viewer offers the retry and discard itself, so a refused retry leaves the text in the editor, with the reason shown in the viewer. A read-only Proposed lots glance (`processing/proposed-lots.ts`) names each active lot with its state (Approved, Ready, To review, Changed, Blocked) and links it to Review. Save status shows "Saved" without the revision, which stays on the element as `data-revision`. See the remaining mockup composition below.

`components/operator/EvidenceViewer.tsx` displays linked retained source/version/page choices through the existing object-scoped preview route. Selection pins evidence ID, version ID, page number and preview ID for that focused lot lifetime. Polling never substitutes a newly added version or a changed/missing page; unavailable selection requires an explicit choice. Changing lots remounts the viewer. Bounded zoom and keyboard-scrollable overflow inspect the retained preview without changing original/approved bytes. A pending first media read is visibly loading; a failed first read explicitly leaves file presence unconfirmed. Failed reads with cached media label the last retained snapshot; failed preview loads offer only a retry of the selected preview. Exact source/version/page/preview query fields persist inspection across reload; zoom remains local to this viewer.

`LotEvidence` places the image immediately after its evidence heading, with source/page/zoom controls and retained human notes below. Repeated lot/Part introductions are omitted; the queue and decision panel retain that identity. Fixture candidates remain below the human evidence. The Decision panel names an explicit new shared Part create accurately and offers candidate comparison only for existing-Part choices. No presentation action prepares, approves or changes evidence.

## Retained read coordination

Pinned TanStack Query coordinates bootstrap, batch reads, manual workspace and activity. The generated AJV-validated client façades remain the transport boundary. `queries/client.ts` explicitly disables retries and focus/reconnect refetch; manual/activity observers poll every two seconds. Loopback reads attempt even when browser connectivity reports offline. Existing client deadlines still bound requests; cache cancellation does not claim physical cancellation of non-abortable ports.

`components/query/ServerStateProvider.tsx` owns an in-memory cache. App separates bootstrap from the private cache and keys its lifetime by origin, actor, target and target-context IDs. Scope replacement cancels and clears the previous private cache; no browser persistence is installed. `useServerScope()` and `serverQueryKey(scope, ...resourceIds)` provide the shared seam for additional readers.

Cache data is an observation, never edit or command authority. Capture retains its accepted loaded snapshot until a confirmed save or explicit reload. React Hook Form drafts, dirty navigation, pinned preparation identity, review selection, last preview and payload-bound delivery intents remain outside the cache. Repeated reads cannot reset them. A cached manual preview stays disabled until the mounted observer verifies a read; failed or paused reads retain history while disabling freshness-sensitive commands. Confirmed commands and subsequent failed status reads have separate outcomes.

`ServerState.test.tsx` verifies scope isolation and late prior responses. App/manual component tests cover deduplication, periodic recovery, paused reads, accepted revisions, retained drafts, pinned preparation identity and lost acknowledgement.

## Retained media and crop state

Bootstrap exposes optional media capability only for an initialized, explicitly configured
private store. App supplies the generated media client only when that capability is true.

without resetting pending input. Capture and media dirtiness remain separate.

RHF coordinates group and frame/aspect forms. Moveable controls only the crop overlay;

The crop dialog portals to the document body so responsive hiding of Capture context cannot hide an open modal. From repository root, `pnpm dev`, `pnpm typecheck`, `pnpm lint:frontend`, `pnpm test:frontend` and `pnpm build` delegate to this application. Root normal tests also run backend checks. See [repository layout](../docs/repository-layout.md).

## Operator review workspace

Review is an evidence workspace over the same retained facts; it adds no second truth model. `Batch` reads the `OperatorReview` projection through `operatorReviewClient` beside the capture snapshot, and shows it only when its revision matches the accepted batch revision. Retired lots stay in the capture snapshot for history, but Capture, Review selection and new Processing attempts hide them. Processing job history for a retired lot stays visible.

`components/review/ReviewWorkspace.tsx` coordinates the Evidence and Table modes. The URL holds the focused lot, the mode and the filter (`#<batch>/review/lots/<lot>?view=table&filter=warnings`); transient selections do not. The queue groups active lots by urgency: blocking, warnings, changed after review, needs review, reviewed, approved. Pure filter, grouping, URL and provenance rules live in `src/operator/review-model.ts`.

Components under `components/operator/` own focused responsibilities:

- `LotEvidence` shows lot, Part, batch and predecessor-lot notes, linked media previews and Processing proposals labelled fixture-only. Proposals are candidates, never chosen values. A `/4` estimate is labelled estimated; "Use estimated quantity" is a human lot edit offered only while its attempt is current (`ready`) and the lot has no human count, its own or an exact batch default it inherits; superseded attempts are history only. Suggested tags are listed apart from human tags and can be merged into a new shared Part's create spec only, using the inventory adapter's duplicate policy (`tagKey`: only all-ASCII names fold case). Batch manual shared tags are offered the same explicit merge (`SharedTagsChoice`); an existing inventory Part's tags are never changed.
- `DecisionPanel` shows fact rows with provenance (human set, inherited default, override, unknown, cleared, unset), the lots sharing a Part proposal, blocking problems and warnings. `CompareMatches` sets observed Part candidates side by side and confirms the shared edit with the exact affected lots before the capture edit. `QuickLotEdit` makes lot-only quantity/location edits.
- `IssuePanel` and `DismissWarning` record a reasoned dismissal bound to the warning's dependency digest. Blocking issues have no dismissal control.
- `TableWorkspace`, `ReviewTable` and `BulkEditPanel` provide the table projection, explicit row selection and bulk quantity/location edits. `RestructureDialog` splits, merges (with explicit same-contribution confirmation) and moves lots between Part proposals. Every bulk or structural change shows the server dry-run `ImpactSummary` first, then applies the same change.
- Batch instructions appear as Custom instructions inside Batch settings and autosave through the same queue, and a saved instruction is also sent to the batch's agent sessions (the server tries once after each save; after a save from Processing, Batch sends again through the delivery route and keeps the outcome across Processing's reload, and the instruction field says how many sessions it reached or offers a retry when it failed); each evidence group owns its instruction form. Group/evidence context is retained human input, not an approved inventory effect.

`operator/useRetainedCommand.ts` binds one payload to one idempotency key. An uncertain outcome, including a typed server 5xx, keeps the exact payload and key for retry; a definite refusal or a revision conflict releases them. A conflict keeps local form input and requires explicit reload. Operator forms report native changes synchronously and aggregate dirty state by source, so closing a clean sibling cannot release another form's guard. Dirty drafts block internal lot/view navigation, editor closing and sibling commands that would remount them; explicit discard is available. A matching accepted operator projection keeps draft owners mounted if polling fails or discovers a different revision. New commands are fenced while it is unavailable, but pinned uncertain retries remain usable. Shared-Part comparison stays open after a resolved refusal and closes through the confirmed revision remount or explicit discard. Pending previews freeze their fields and discard late results after a form-generation change; later edits invalidate the preview.

Keyboard shortcuts (J/K move, R mark the focused lot reviewed, E edit quantity, V focus evidence) are ignored inside form fields, with modifier keys or while a dialog is open. Dialogs use native modal `<dialog>` and restore focus to the opener. Narrow screens keep the list → focused lot flow, and the table scrolls inside a labelled region rather than the page. `OperatorReview.test.tsx` and `OperatorSurfaces.test.tsx` cover these behaviours with injected fakes.

## Live server updates

`components/operations/LiveUpdates.tsx` owns one scoped WebSocket lifetime beneath `ServerStateProvider`. Validated ready/change frames cancel older read publication before refreshing retained queries; hints arriving during that refresh are queued for another fresh read. No socket payload owns edits or executes a command. Exact cursor strings survive reconnect. Healthy channels suspend routine polling, disconnections restore the existing two-second fallback and truncated stream windows retain a slower safety poll. Returning to the foreground (focus, reconnect or the tab becoming visible, through `browser/useOnForeground`) reconciles retained reads. Malformed/regressing frames and incompatible protocol versions require an update without clearing unsaved input. Bootstrap refresh after restart rotates development authorization; private actor/target/context changes still replace the entire keyed cache. Settings autosave uses HTTP commands only; agent dialogue requires separately reviewed command semantics. Connection establishment is never command acknowledgement.

## Capture grouped workspace

`MediaWorkspace` composes three evidence entry actions above named groups and ungrouped originals. `useEvidenceWorkspace` owns the accepted media projection, exact selected IDs/revision and one payload-bound retained command. Polling cannot replace dirty group/evidence editors or membership selections; confirmed receipts cannot be rolled back by an older read. Crop polling may update derived output while the original crop intent stays pinned.

`EvidenceDragContext` uses exactly pinned dnd-kit React/DOM adapters; pointer, keyboard and touch dispatch the same atomic `move_many` command as explicit selection controls. A conflict preserves selection until explicit reconciliation. Rename, evidence notes and group instruction editors keep loaded revisions and explicit save/discard. Review/viewer renders retained note provenance beside the same linked evidence identities. Grouping does not choose subject links or attachments.

Picking files uploads them at once; there is no separate retain step. `media/useUploadQueue.ts` owns each picked File with its own idempotency key and expected revision, outside form state, and `MediaWorkspace` provides its ports. Photo and PDF pickers accept several files and bind their intended group before the picker opens. The queue sends one file at a time, because each upload and each group move advances the media revision: it reads the current revision, uploads, then adopts the receipt through a fresh membership read and a separate move command. That move trusts the read it has just made, not an earlier failed poll the handler's render still shows.

Each picked file shows as an `UploadTile` in its target group's evidence grid, or the ungrouped grid when it has no group or its group has gone. `MediaUpload` keeps only the pickers. The group header shows "Uploading 2 of 3", counting every file picked together, including any already added or refused. Uploading is indeterminate because the fetch request reports no byte progress.

Each tile's status is a live region: "Not added" and "Upload not confirmed" are alerts, and the other states are polite status messages. Retry and Read again keep focus on their tile; they never touch the selection, so a selection held after a refused move does not disable them, and queued uploads do not disable clearing or reloading that selection. Dismiss moves focus to the next tile's enabled control, else the previous tile's, else the group region. A focused tile that leaves on its own, because its file was added or a read overtook its notice, hands focus to its group region. Unmounting the workspace stops new requests and follow-up reads; a request already sent finishes on its own.

Outcomes are handled per file:

- **Refused:** each of these shows "Not added" with the reason and Dismiss, and later files continue:
  - a file that fails the type check or the size and label checks shared with the contracts client (a label must be well-formed UTF-16, so URI encoding cannot fail);
  - a failed revision read before sending, so nothing was sent;
  - a 4xx response;
  - a second revision refusal.
- **Lost response:** "Upload not confirmed" keeps the exact request. Retry resends the same key, revision, label and bytes; a receipt is adopted, and a 412 proves the file was not kept, so it is sent once more with a new key at the current revision.
- **Move not saved:** the retained original stays selected in its confirmed ungrouped projection, and its tile in the target group says "Added to Ungrouped". While that move's intent or selection is held, later files are not moved: they stay in Ungrouped with the same notice and leave the selection unchanged. Refresh and later finishes drop the notice once a read shows the file in any group, and the tile is hidden as soon as the latest read does.
- **Failed read after a receipt:** reported separately and read again on request; it never authorizes another upload.

Files uploading or awaiting Retry or a read count as unsaved work. Media, settings and instruction drafts share navigation protection without allowing a clean sibling to clear it.
