# Frontend architecture

This document describes the implemented manual intake application under `frontend/`. Read the [shared architecture](../ARCHITECTURE.md), [shared guidelines](../CODE_GUIDELINES.md) and [frontend guidelines](CODE_GUIDELINES.md) for its boundaries and change policy.

## Current application

React and TypeScript run in a Vite browser application. `index.html` loads `src/main.tsx`, which mounts `App` under React StrictMode. `src/App.tsx` uses the validated generated contracts client against the same-origin Fastify API. Bootstrap supplies development-mode attribution and an ephemeral CSRF token, never an inventory key. `App` builds the optional feature clients (agents, attention, catalogue, media, operator review, processing, records) from that token and provides them through `ApiClientsProvider`; components read them with `useApiClients()`, and an absent client means the feature is unavailable. Leaf components that take an explicit `client` prop keep it. Every React context object and its hook live in `src/context/` (API clients, batch commands, compact status, confirmation, header observations, live-update health and poll interval, record save and server scope), and consumers import them from `#/context`. A provider whose only job is to supply its context, including one holding that context's own state, lives beside it; a component with wider responsibilities (`ServerStateProvider`, `LiveUpdates`, `RecordsStage`, `App`) renders the context's `.Provider` itself. `Batch` provides its capture commands (`edit`, `observe` and the stage `reload`) through `BatchCommandsProvider`; workspaces read them with `useBatchCommands()`, which throws outside a batch. Leaf editors keep explicit command props, and an absent `edit` prop still means read-only. Retained batch list/create/read/edit/archive commands store state in PostgreSQL, not localStorage. A hash URL retains batch and selected subject/editor; refresh loads saved server state. Closing the browser does not erase batches or notes.

`src/components/capture/CaptureWorkspace.tsx` coordinates the header, evidence column and Batch settings column, each in its own `.tsx` file. Batch list/detail components live in `src/components/batches/`; retained data/client types and pure display mapping stay in `src/capture/`. Capture has no Physical lots or Part proposals panes; manual subject create/edit, Part choice and attachment choice open in Review's focused `ReviewSubjectEditor`, which reuses `CaptureEditor` and the existing capture commands. Shared Part proposals never combine physical lots. Exact quantity and PK strings stay strings; notes visibly identify human provenance. Defaults and explicit lot selections retain unset/unknown/clear/inherit/set distinctions. Reading a configured target's existing Part/location creates an observation; selecting it is a separate human action. No browser command accepts a target URL, actor or inventory secret. Capture fields support manual quantity, location, existing Part choice, labels, links and append-only notes; retained media has its own boundary below.

Each save carries the loaded batch revision. A 412 preserves local inputs and displays current saved values; explicit discard/reload is required, never silent rebase or last-write-wins. A single dirty editor disables subject navigation/archive, with explicit discard. The app-owned navigation guard receives synchronous dirty callbacks from Capture and nonempty new-batch title/note forms. It blocks same-document links and hash/history route acceptance while retaining the mounted form and exact input; native unload is protected too. Save/create or explicit discard releases the guard. Transient review selections/archive filters do not lock navigation. A failed/uncertain save remains visibly unconfirmed; it is not blindly retried. Archive retains history and disables editing until explicit resume. Review and Changes use the generated manual client; Processing exposes retained jobs and questions through its retained coordinator and explicitly selected fixture/native profiles. Retained uploads and crop preparation are described below. Native provider sessions require a separately supervised worker; there is no Python runtime connection.

Capture lays the evidence card and the settings column side by side on the canvas's flex bases, wrapping into one column once both no longer fit; below `bp-compact` the Proposed lots glance moves under the capture tiles and `BatchSettingsPanel` folds behind a summary, its fields staying mounted so drafts survive. The panel holds one mounted RHF draft: the title, the batch notes, one Default location, supplier (No supplier, existing or new draft), the disabled purchase-order preview directly below supplier, Shared part tags and Custom instructions; Quantity mode is gone from the panel and per-lot exact quantities stay in Review. The batch notes field is drawn in the evidence card through a portal slot that `CaptureWorkspace` hands over, while the panel still owns and autosaves it. Write a note opens an inline append-only evidence note in the evidence column. Lot editors preserve explicit context overrides; Capture and Review label effective human context separately from approved inventory effects. Under Default location one line names the lots that override it, each linking to Review, which shows a lot's full capture context. The Review subject editor sets a shared Part's location for its lots, and each evidence group carries its own location control; both are application defaults, never inventory fields. Review's Location fact and table column name the source (lot, shared Part, evidence group or batch default) through the shared contracts resolver, and report disagreeing groups or unread group membership instead of falling back. Placement comparison and native 200%/360px/390px evidence are in [the settings qualification](https://github.com/MitchReyno/InvenTree-Importer/blob/e3ac646/docs/bench-intake/evidence/capture-settings/README.md).

Capture's editor and the separate `components/batches/NewBatchForm.tsx` use pinned React Hook Form. Native fields register directly; Controller adapts the existing quantity/reference controls without changing their modes or exact string values. `capture/editor-model.ts` owns initial values and command construction. Editor defaults remain fixed for the mounted selection, so newer snapshots do not reset a human draft. Synchronous event callbacks still feed the application navigation guard. The form package does not own revision authority, uncertain acknowledgements or payload-bound delivery keys; new-batch creation and Capture edits preserve revision/payload-bound retry intents independently of form submission state. After an unconfirmed edit, a changed payload requires explicit saved-state reconciliation; exact unchanged retries reuse the original key. The settings panel has no Save button: `capture/save-queue.ts` is a per-batch serialized owner for the `batch_settings`, instruction and logo-upload commands. Valid edits send after a 500 ms idle debounce or on blur, and freeze payload, expected revision and key per request; later edits are sent against the acknowledged revision. IME composition suspends every dispatch until it ends, and a disposed queue never dispatches. While a lane's request is unconfirmed, every newer draft is kept, including one equal to the old saved value. Conflicts and uncertain acknowledgements block further commands until an explicit keep, exact retry or discard-and-reload. A clean panel adopts newer saved values; a dirty one never resets. Editing needs a fresh scoped observation (the shared header connection read or the batch's capture read, succeeded within 60 seconds and not now failing) and an online browser; reconnection reads current state before admitting writes or exact retries. Evidence media, evidence note and settings commands do not overlap: each is fenced while another is unacknowledged, and settings stay paused after an evidence change until the read of its new revision is accepted (a failed read keeps them paused, with an explicit refresh). While disconnected, unsent drafts can be discarded locally; sent or unconfirmed requests keep their own recovery. A newly observed instruction version becomes that lane's saved baseline and text unless the lane holds a draft or an unacknowledged request; adoption never sends. Only the newest post-evidence refresh releases or fails the settings gate. Supplier and location observations apply only while their choice is the newest intent of a mounted field, against the form's current drafts. Typed tag text that has not been added keeps navigation protected. Dirty owners report clean only on unmount or confirmation; a replaced parent callback receives the current state.

`components/review/ManualWorkspace.tsx` coordinates retained reads driven by live hints, bounded polling fallback and explicit commands. Review presents physical-lot selection, human evidence and exact saved choices; selecting a shared Part never includes another lot. The first slice accepts at most ten selected lots. Changes › Ready to add shows the ticked and left-out lots, every record the preparation creates or uses, and the frozen plan digest. Its URL pins the preparation identity across polling/reload; removed or stale plans disable approval instead of substituting another latest plan. Replacement requires explicit choice. Selected/shared dependency changes require fresh review/preparation; unseen capture changes disable review until explicit reload.

Changes › Ready to add lists a new location or supplier among the records it creates, and a stock item under a location made earlier in the same run. Capture's new-location and new-supplier forms state that nothing is created from the form; a draft is created only after approval on a supporting target. Added names a confirmed new record by PK and keeps an uncertain one unresolved. Review's Location fact and the batch supplier context name a pending new-location or new-supplier draft ("created only after approval") instead of an empty or unknown value.

`components/changes/` displays Ready to add and Added (see Changes below), including original approval rounds and journal certainty. Approval and queueing are separate actions. Unknown outcomes have no create-again control; cancellation cannot undo an authorized request. Only server-advertised original-operation recovery is offered. App-wide activity is a bounded, explicitly truncated retained-run snapshot, not simulated progress. Commands carry neither browser authority nor inventory credentials.

Styling follows the [Bench Intake Design System](https://claude.ai/artifact/TbKY47cDmdA3Nuh2jufTmo). `src/theme/tokens.json` is its token file; `scripts/generate-tokens.cjs` generates `src/theme/generated/tokens.css` (light and dark CSS custom properties with `color-scheme`) and the typed `tokens.ts` map that module-scope styled-components read, so a theme switch needs no re-render. Frontend lint fails when the generated files are stale, when a documented text/ground pair is below its contrast threshold in either theme (`scripts/check-contrast.cjs`, also run by the build), or when a component uses a literal colour. The same check (`scripts/check-literal-colors.cjs`) fails on any literal spacing, radius, size, type, motion, layer, opacity or breakpoint value that equals a token meant for its CSS property; a value whose role has no token says so with a `literal-allowed: <reason>` comment. `src/theme/theme.ts` sets `data-theme` on `<html>` from the stored Light, Dark or System choice (`bench-intake.theme`) or the OS scheme, and `src/theme/masthead-style.ts` sets `data-masthead` from the stored masthead style (`bench-intake.masthead`: `bar`, `window` or `fade`, default `bar`); the two are independent. `src/theme/masthead-motion.ts` keeps whether the electronics move (`bench-intake.masthead-motion`: `on` or `off`, default `on`) and sets `data-masthead-motion`; Settings › Appearance's "Animate the electronics" switch (`MastheadMotionSwitch`) changes it without touching the style. An inline script in `index.html` sets all three before first paint. All three controllers read and write through `theme/device-preference.ts`, which falls back to the default when storage is missing, throws or holds an unknown value. `debug/debug-mode.ts` keeps debug mode (`bench-intake.debug`, `on` or `off`, default off) through the same helper. With it off, internal identifiers, digests, revisions, raw state codes and the local setup diagnostics are not rendered; `DebugDetails` shows them in place as dashed blocks marked "Debug" only while it is on, and `App` renders `PageDebugPanel` under every page, listing the route, batch identity, the cached agent settings revision, the batch's processing profile (`runner_status` from its cached Processing read), live-update state and each mounted read (`debug/useDebugReads.ts`, a query-cache subscription that starts no request). Settings › Developer (`DeveloperSection`) holds the switch, the local setup check (`LocalSetup`, formerly the page-footer diagnostics), Reload app data and Copy debug info (`DevToolActions`, `debug/debug-info.ts`). Public Sans (variable) and IBM Plex Mono 400/500 are self-hosted through `@fontsource` packages imported by `GlobalStyle`, which otherwise contains only document/reset/font/focus defaults. Design-system components (Button, IconButton, HelpButton, ShortcutsButton, Pill, Banner, Tabs, SegmentedControl, FilterChips, DataTable with BulkBar, KeyValue with SourceChip, DescriptionField, TreeView, CompareTable, SettingsNav, SettingRow, Switch, NumberStepper, AiMark, ProblemCard, ItemRow, RecordStatePill, StatePill, EventTime, TargetChip, ChangeSummary, StickyFooter, StatusTimeline, Dialog, Toast, ActionsMenu and the rest) live in `components/ui/` under the design system's names; screens render them rather than keeping their own copies, and every notice is a `Banner` inside an element carrying its status or alert role. `components/ui/icons.tsx` inlines the design system's small SVG set (AI sparkle, help, info, settings, menu, back) in `currentColor`. `AiMark` draws the sparkle in the `ai` token on its `ai-weak` tile, hidden from assistive technology, and centres itself on the label it is given. A `SourceChip` shows only its source, an info icon and, for a certainty that needs attention, a leading glyph; its accessible name and tooltip carry the certainty, and it opens `SourceChipPopover` with the field, certainty, reason, evidence and the Open evidence and Edit value actions its caller supplies. `DisabledFeature` wraps a deferred control through a render prop that gives it `aria-disabled` and the explanation's `aria-describedby`; the control stays focusable while the wrapper stops clicks, key presses, input, paste and drops before they reach its handlers. `SettingRow` and `DescriptionField` render a disabled reason through it. Screens mark agent touchpoints with `AiMark`: the Agents heading, the Proposed lots heading, the Agent sessions card, the session drawer's title, and the batch, group and Tell Examine instruction boxes; never values, source chips, pills or per-field Ask. Agent lots carry a ＋ New pill rather than a sparkle. Explanations that headings and legends used to print in grey sit behind a `HelpButton` (Capture's "About groups", the Map's "How to read the map"), and Review's shortcut list behind a `ShortcutsButton`. Every source chip passes its field, value and one sentence on why: readings through `operator/value-evidence.ts`, record fields through `review/records/FieldSourceChip.tsx`, and a lot's provenance through `operator/ProvenanceChip.tsx`. An action in the chip's popover that moves focus, such as Open evidence, keeps it there; otherwise focus returns to the chip. Panels, headings and text primitives are in `components/ui/primitives.tsx`, including `PageStack`, which spaces a page's top-level sections one page gap (`space-7`) apart and clears their outer margins; `PageContent`, every Settings section and the page roots stack on it; form inputs and fields are in `forms/` (imported as `#/forms`). Dropdowns follow one guideline, shown in the component gallery's "Choosing a dropdown": a choice of InvenTree records, of something that grows with the batch (lots, Part proposals, groups, evidence versions, preparations) or of a typed exact value uses a searchable picker on `forms/SearchablePicker` — `SearchableReferencePicker` for catalogue records, `ModelPicker` for models and `ChoicePicker` for a list the caller already holds, such as the batch's observed records, which searches by every typed word. A short fixed list is chosen per screen: a `SegmentedControl` for two to four short options that fit one line at phone width (Capture's Part action, a move's destination), otherwise a styled native `Select` (quantity and date modes, document pages, crop ratios, the bulk bar's field). The pickers' search text never reaches an enclosing form's change handler, so a form marks itself dirty only from a pick, and picking the option already chosen changes nothing. A `ChoicePicker` whose empty value only prompts is `clearable`: "Not chosen" comes first and undoes a choice. A picker inside a disabled fieldset takes `disabled` as a prop, since the fieldset doesn't reach it; a required one announces it and its error and takes focus on a refused submit (React Hook Form's `field.ref` as `inputRef`). In a dialog, Escape with a picker's menu open closes only the menu (`ModalFrame`). Tab leaves a picker without picking, and Enter in an open menu never submits the form around it. The Review Map's pickers open their menus in a layer over the page (`menuInLayer`), so the diagram's scroller can't clip them. Styling-only state uses transient `$` props. The legacy stylesheet is removed. Layout/UX follows the primary [original HTML prototype](../docs/bench-intake/reference/bench-intake.html), [Capture](../docs/bench-intake/reference/03-capture.png), [Review workspace](../docs/bench-intake/reference/02-review.png), [Inbox](../docs/bench-intake/reference/01-inbox.png) and [phone frame](../docs/bench-intake/reference/10-phone.png); see the [reference index and historical limitations](../docs/bench-intake/reference/README.md) before the secondary derivative board. The [main specs](../openspec/specs/) and latest contracts override prototype simulations. Capture follows the original two-column hierarchy: evidence actions and groups on the left, Batch settings and Go to review on the right, one column on narrow screens. Review keeps queue/evidence/decision. No fake media or simulated processing/execution is added to mimic unavailable breadth. The batch screens follow the [redesign canvas](https://claude.ai/artifact/TFjujLEMdBcqdRUBbvJKRf); Changes replaces the original approval and results screens.

`components/masthead/Masthead.tsx` owns the brand header: the "Bench Intake" title with its `Dev mode` button (`DevModeButton`), the breadcrumb and the scoped status slot. The button opens a developer tools popover: the build summary, the debug mode switch, a short local setup summary read only while it is open, Check setup again, Reload app data, Copy debug info and a link to Settings › Developer. Settings › Appearance chooses where the electronics current lives (`masthead-style.ts`). In the bar (`bar`, the default), the bar carries the dotted ground and its own current. Behind the whole window (`window`), the root carries the dotted ground (`GlobalStyle`), the bar is a translucent blurred surface, cards that sit on the page (`Panel`, the Batches `Card`, `SettingsCard`, Processing's `Card`, Capture's Evidence card and Proposed lots glance (not on a phone, where it sits inside Evidence), the Agents summary and session groups, the Records rail, list and record card, the parameter matrix, Review's scope bar and map columns, and the Debug panel in debug mode) take the shadow token, and text placed directly on the page opts into a ground patch (`onField`, or `groundBehindOnField` for blocks such as the Settings nav; `components/ui/field.ts`). Headings inside surfaces never take one. Fading down (`fade`) draws the ground and current in a 420px band that fades out and scrolls away, and the bar has no ground of its own. `MastheadBackdrop`, mounted by `App`, renders `MastheadField` for `window` and `fade`, keyed by the style so a change releases the previous scene: a decorative layer at `z-index: -1`, below every in-flow and positioned element and above the root's ground, so no element around the app gains a stacking context. Fading down's mask shows parts in the bar's text gap (with its compact dimming) and, below the bar, only outside the route's page-width column; `Masthead` publishes the gap stops and its height on the root for it. `AppMasthead` sets the breadcrumb: "Batches" alone inside a batch, because the batch header names it, and "Batches / <page>" on Agents and Settings. `HeaderStatus` fills the slot with the activity pill, the connection pill and the Settings gear (`#settings`); there is no separate Open InvenTree button and no "⋯" menu. The connection pill opens the server menu (`ConnectionDetails`): host, version and last check, a sentence on what approvals write to (the test target, or the live inventory), the static Dev mode badge (`DevBadge`), then Open InvenTree, Check connection now (`CheckConnectionButton`) and Server settings (`#settings/inventree`), and a sentence when InvenTree refused the read token, and, only in debug mode, the API, transport and target diagnostics as a debug block; the theme lives in Settings › Appearance. The activity pill leads with `AiMark` for fresh Processing work on a desktop; the phone button always carries it. Inside a batch it shows neither the batch title nor its questions, which the batch header owns; outside it names the batch it shows from that batch's cached read. At phone width (`bp-compact`) the bar holds the brand, "Dev", the agents status button (the mark, spinner and step segments, with the step states in its description) and a menu button (`PhoneMenu`) whose dot and accessible name carry the connection state; the menu holds Agents, Settings, the server details with Open InvenTree, and the theme (`settings/ThemeChoice.tsx`, shared with Settings › Appearance), and the gear and connection pill leave the bar. A visually hidden status beside the menu button announces connection changes. The agents status button keeps its content's width, with narrower segments, and the brand shrinks (19px, then ellipsised) before any button clips. At that width `BatchHeader` follows itself with `IntersectionObserver` (`browser/useOutOfView.ts`). Once it has scrolled away, a fixed row condenses it: back, title, the need-you count, the masthead's condensed status and menu, and the sub-tabs below. App provides that status through `CompactStatusContext` as a second `HeaderStatus` (`variant="condensed"`: the mark and spinner, no live region). Both copies show one set of reads: App wraps the page in `HeaderObservationsProvider`, which calls `useHeaderObservations` once (one clock, one foreground listener), so the condensed copy sends no reads and shows the current state as it appears; a `HeaderStatus` outside a provider reads for itself. Fixed positioning keeps the row from shifting the page it covers. While it shows, the document's `scroll-padding-top` is its height, so focused content scrolls clear of it. Its sub-tabs are named "…, condensed" and mark the current one without `aria-current`, and a control focused in it hands focus to the same control in the full header (by `data-focus-key` or address) before the row goes. `ElectronicsCurrent.tsx` adds a decorative, `aria-hidden` canvas of isometric outline-style electronic parts drifting right to left, as a `band` behind the bar's title or a `field` behind the page. The pointer stirs nearby parts, and switches react to it. The canvas never fetches, writes or touches application state. Its scene logic lives outside the component tree in `src/electronics-current/`: palette, outline material kit, part builders by family, weighted catalogue, pure flow and rope maths, and the scene controller. A part may own a `hanging` piece, such as the solder wick's loose end, that hangs in world space rather than turning with its part. The scene adds it to a shared `hanging` layer when it builds the part, updates it after placing parts each frame (a new one starts hanging straight down, so the still frame shows it hanging) and removes and disposes of it with its part. The component feature-detects WebGL 2 before dynamically importing that scene chunk through one module-level promise shared by every mount, so unsupported browsers and jsdom never download three.js and keep a plain masthead. `prefers-reduced-motion` renders a single static frame without an animation loop. The animation switch is a separate input: with it off the scene is built and drawn once (`paused`), and switching it stops and starts the same scene (`pause()`, `resume()`) so parts keep their places. Every start path, including scrolling back into view, checks the switch, reduced motion and visibility; a theme change or resize while stopped redraws the kept parts. Unmounting cancels a pending start, the loop, the resize observer and all GPU resources. A band's part count scales with its width, and narrow screens dim parts under the text instead of hiding them; a field's count follows its area (about 25 on 1440 × 900, within 6–40), renders at a pixel ratio of at most 1.5 and re-lays out when its height changes.

`src/App.test.tsx` covers exact string emission, human attribution, archive/resume and concurrent-edit conflict through a jsdom/component boundary. Component tests alone are not browser or production-access qualification. `ManualWorkflow.test.tsx` adds exact selected/digest emission, explicit stale-display reload and unknown-result controls.

The pause and resume buttons (`components/agents/PauseButton.tsx`), Tell Examine, Ask and the personal Claude credential request use `lifecycle/useAsyncAction.ts` for their busy flag and failure text. It keeps no payload or key and shows one failure text whatever the cause, and a second run while one is pending is skipped. Tell Examine and Ask bind their retry key to the kept text in `processing/pending-messages.ts`; other payload-bound retries keep their own payload and key, for example through `operator/useRetainedCommand.ts` (see Operator review workspace).

## Design alignment and evidence inspection

The shared masthead, `Dev mode` badge, status disclosures and batch header use compact spacing so working evidence appears earlier on desktop and phones. On narrow screens the labelled lot-filter strip scrolls within its own row, selection actions share two columns with wrapping labels, and desktop-only shortcut hints are omitted; safety/read-state notices remain visible.

## Review Lots and Map

Review › Lots opens on the first queued lot, so its evidence and details show without a separate step; each queue row's "Show" button changes the lot. The details pane starts with the lot's record chain (Part, Stock item, Location), a link to the lot's open Processing question when it has one, and a per-lot Mark reviewed that states why it is disabled. Exclude is shown disabled until record edits back it. Each problem offers fixes from `operator/problem-actions.ts`, on the lot itself or on the screen that owns them (Part choice, Records, Capture, the Map, or the lot's open question). The Workspace and Table share one selection and the URL filter (Needs answer comes from open Processing questions on the lot or its Part, `openQuestionsByLot`, and says when they are not yet read; there is no Excluded filter until Exclude exists); the Table may select beyond the Workspace's 10-lot approval cap for bulk edits.

Review › Map (`components/review/ReviewMapStage.tsx` and `ReviewMap.tsx`, model in `operator/review-map.ts`) shows evidence files beside active lots: a file supports a lot when it is linked to the lot, its Part, or a lot it was split or merged from (lineage from the operator review's retired lots, walked to the server's depth), or when one of its observed regions is in the lot. Once observations exist, each file lists its regions (active observations on its versions, labelled by their first non-empty marking or text) with the lot each supports. It flags files no lot uses and lots resting on one file. Its edits wait for a media read of its own and reuse existing commands: the media `link` edit to link or unlink a file, capture `add_lot` (with a note naming the file) then a link for "New lot from this", the capture edit `observation_same_item` for a region's "Same item as…" (offered among the regions of its own lot, with "Not the same item" to clear it; the lot's heading counts its items once with `lotItemCount` and says how many were seen twice), and the restructure dialog for split, merge and move, which are locked for lots already added and while the latest operator review is unread; until then the no-evidence flag and the unused flag on a retired lot's files say history is still being checked, and those files cannot start a new lot. Links through a lot's Part or an earlier lot show as such and are not unlinked here. Files sharing a name are numbered once over the batch's media snapshot (`evidenceDisplayNames`), deleted files included at their upload `position`, so the Map, Review, Processing images and Capture agree and a delete or restore renumbers nothing, with identifiers only in debug mode, in each viewer's debug block (Review's evidence viewer, Capture's file viewer). Tell Examine (`TellExamine.tsx`) appears only while the batch is not archived and has an Examine lead session that is not cancelled (`examineLead`); it sends free text as chat to that session's inbox, not through the batch instructions command, and keeps the text when it is not sent.

## Review Records

Review › Records (`components/review/records/`) reads `GET /api/v1/batches/:id/records` through `records/useBatchRecords.ts`, keyed by batch revision. While a record the target already holds is open, `useExistingValues` reads `records/existing` and the detail shows an In InvenTree table beside this batch's values. Descriptions show once, through `DescriptionField` with a count against InvenTree's limit (500 for companies, 250 otherwise): `RecordDescription` shows a mapped record's InvenTree description read-only, over the limit or not, without blocking, and the description entered with a new location in Capture; manufacturer parts, supplier parts and proposed companies show a disabled field, because the app cannot store their descriptions yet (BI-015), and so does a mapped record whose settled read did not provide its description, saying why. A new Part's description is edited in `PartDescriptionField`, which counts the text as it will be saved and whose Save waits while that is over 250 characters. A proposed description that does not fit is listed under "Not supported yet" as a read-only field with its count. A step's value reads with its source kind and agreement in words (`operator/value-evidence.ts`), as Examine's readings and a lot's observations do. A type rail lists each type's new, existing and to-decide counts; the list shows a type's records; the detail shows each value with "Set by you", the step that proposed it, or "Estimated by Examine" for an AI lot's quantity estimate, which is accepted or replaced on the lot, and what an edit reaches ("Applies to …, used by N lots"), from the shared `recordScope`. Editors send `record` capture edits: companies and templates map batch-wide, and a Part's name, description, tags, category (mapping or dropping each parameter), parameters and sourcing edit in place. A Part without a spec starts a new one through the `part` edit. `records/model.ts` checks an edit with the shared `applyRecordChange` before sending it, so a refusal names the Part; the server checks again. Each editor keeps its draft until a save is accepted, reports it to the navigation guard, and blocks opening another record until it is saved or discarded. A refused save's "Load current values, keep this draft" reloads without touching drafts; the batch's "Discard local edits" drops them. A field a step proposed offers Ask (`AskControl`) when that step's session works on the record's Part (first) or one of its lots and can still read messages, on a batch that is not archived; it messages the session's inbox and shows "Asked <Step>" until the field's value changes. Unsent Tell Examine and Ask messages, with their idempotency keys, are kept in `processing/pending-messages.ts` across leaving the page, and count as unsaved work only while their form is shown; discarding a record, or the batch's "Discard local edits", drops its Ask messages too. Without sessions there is no Ask. A proposed new manufacturer or supplier from a catalogue proposal, on a Part being created that has no company in that role, is a company record per Part that needs a decision, labelled "<name> for <Part>"; `ProposedCompanyEditor` shows `CompanyDecision` (its likely match, if any) and another observed company in the role, either of which sets that role on that Part with its proposed number. Every other catalogue value that cannot enter a spec comes from BI-006's `assessCatalogue` rule (in contracts), each with why it is not supported yet: a proposed-new category is explained at the Part's category field when the Part lists it; a description that does not fit and values with no field of their own (such as a parameter the category cannot take, a company that is new on a Part not being created, a supplier with no SKU, a supplier price, or a reference no longer matching what was read) are listed under "Not supported yet", each with the agent's reason.

Records › Locations lists each stock location the batch's stock goes into, with its path, why it is used ("batch default", or "from N lot overrides" for a location other than the default, from `records/locations.ts`) and its stock count, one stock item per lot. A location's path is InvenTree's own, so while Locations lists a mapped location the existing-values read runs for the list too, and a failed or paused read says the path is unavailable rather than unknown. A new location drafted as the batch default shows its parent's InvenTree path and its name, or "Not known" when the parent is invalid or its path isn't read. Its detail (`LocationDetail.tsx`) shows the path, its use, a disabled Location type select (location types are not read from InvenTree yet, BI-015), the stock going there with each lot's quantity from its stock item record (an Examine estimate stays an estimate), and an Ask Inventory box when an Inventory session works on one of its lots. ## Retained read coordination

Pinned TanStack Query coordinates bootstrap, batch reads, manual workspace and activity. The generated AJV-validated client façades remain the transport boundary. `queries/client.ts` explicitly disables retries and focus/reconnect refetch; manual/activity observers poll every two seconds. Loopback reads attempt even when browser connectivity reports offline. Existing client deadlines still bound requests; cache cancellation does not claim physical cancellation of non-abortable ports.

`components/query/ServerStateProvider.tsx` owns an in-memory cache. App separates bootstrap from the private cache and keys its lifetime by origin, actor, target and target-context IDs. Scope replacement cancels and clears the previous private cache and drops that scope's waiting snapshot writes; the next scope deletes its stored snapshots (below). `useServerScope()` and `serverQueryKey(scope, ...resourceIds)` provide the shared seam for additional readers.

Cache data is an observation, never edit or command authority. Capture retains its accepted loaded snapshot until a confirmed save or explicit reload. React Hook Form drafts, dirty navigation, pinned preparation identity, review selection, last preview and payload-bound delivery intents remain outside the cache. Repeated reads cannot reset them. A cached manual preview stays disabled until the mounted observer verifies a read; failed or paused reads retain history while disabling freshness-sensitive commands. Confirmed commands and subsequent failed status reads have separate outcomes.

### Fresh reads

`queries/useFreshRead.ts` wraps a read and says how fresh it is: `empty`, `cached`, `refreshing`, `current` (verified, and the page's own `current` test holds) or `failed` (an error or a paused fetch). Every caller of a key goes through it: Processing, Manual Review, Records and the Review Map's `TellExamine` share the Processing key; Capture, the Map, Images, Review's lot evidence, Examine and `Batch`'s cache-keeping observer share the media key; the Agents page, Settings › Agents and Processing's overview share the agent sessions and settings keys. Records (and Inventory) read the batch's records, the batch list, Batch defaults and local setup go through it too. `keepPrevious` shows the previous key's data while a new key, such as Records at the next revision, is first read; that data never verifies the new key.

- **Verified:** `queries/fresh-reads.ts` keeps one registry per query client. Its query-function wrapper numbers each request, and the cache's `updated` event adopts a result only when it came from the newest request started. An observer is verified only while the adopted request started after it mounted. A manual `setQueryData` (even of equal data), any state change other than `cancelVerified`'s own revert, an error, a pause, a removed query and a new scope clear the proof; a restored snapshot never has one. An observer that joined a request already running gets one follow-up fetch per key, so it is verified without polling.
- **Cancelling:** `LiveUpdates` reconciles through `cancelVerified`, which marks the in-flight request so it can never verify and keeps the result already adopted. The other `cancelQueries` callers (Settings, the header's observations and the provider's teardown) cancel keys of their own.
- **Awaited reads:** a handler that awaits a read goes through `readReplacingCancels` (`queries/fresh-reads.ts`, around `awaitReadReplacingCancels` in `queries/replaced-reads.ts`): Batch's reload of saved values and its retries, Processing's and Manual Review's reads after a command, the media workspace's reads after a receipt, and `requestRead`'s `readAgain`. A read cancelled by reconciliation is not a failure: it waits, showing nothing, for the next settled result of the same query from a request started after the cancel, for at most 10 s from the first cancel, and starts that read itself when nothing has 100 ms after the cancel. It rejects with `ReadUnavailable` when the read pauses or the replacement fails or doesn't settle in time, and with `ReadAbandoned`, which callers ignore and which starts no read, when its caller's `AbortSignal` ends (a component's mount, `lifecycle/useMountSignal.ts`, or a delivery wait) or the query is removed or its scope changes, at any point of the wait. A replacement that runs out of time leaves the key unavailable and its shown read unverified, so commands wait until a newer read lands. The batch's reload after a save starts a read of its own rather than joining one from before the save. Other errors are the read's own and pass unchanged. It only waits: the cancelled generation still never verifies, and the replacement verifies through its own. Provider status (`useProviderStatus`) keeps its own loop, since only a read of its own fresh run answers it.
- **Unavailable since a read:** the registry records when a key's read failed or paused (a cancel isn't a failure) and the last network read it adopted, and `unavailableSinceRead` holds until a read started after the failure lands; a cache write never clears it. Batch shows `SavedValuesNotice` while its accepted batch's Capture read is unavailable this way: amber, "Couldn’t load the latest values. Showing what was loaded at 13:12. Trying again…", with the time Batch accepted the values shown, Try now, and a retry every 5 s. With unsaved changes it names those its editors can name, says they are kept and offers "Discard my changes", which calls each named change's own discard; a dirty report carries its `UnsavedChange`s (`navigation/unsaved-changes.ts`) through `useDirtySources` and `useReportDirty`. Review's lot editor names its fields ("Packet A · quantity") and Capture's settings panel names its drafts ("the batch settings") while nothing has been sent, dropping them with its own guarded discard; other drafts, and sent or unconfirmed saves, are dirty but unnamed, so they are kept and listed nowhere. A read that works is adopted only while nothing is unsaved and only when it brings another revision; otherwise drafts keep their revision and the workspaces keep their mount, and the notice clears all the same. With no batch accepted yet, the read's failure keeps its "Batch unavailable" error. After a confirmed command whose own read fails, Processing says "Saved. Showing the last status from 13:12 until it can be read again." instead of its "Processing status unavailable" banner, until a newer read lands; its commands stay disabled meanwhile. `processing/saved-status.ts` keeps it in `Batch` across the remount the batch's reload causes. While the notice shows, the batch's "Current operator review is unavailable or changed" banner waits behind it.
- **Commands:** commands with a revision need `commandsReady` and stay available through background refreshes; Review Map's edits and Records' record edits wait for it too. Commands with no revision (Pause and Resume, instruction delivery and the agent chat sends that name their session from the Processing read) need `settledAfterHint`: a verified read whose request started after the last live hint, with no newer read in flight, which `LiveUpdates` records when a frame arrives, before its 100 ms reconciliation delay. The Agents page's batch and global Pause and Resume and Settings › Agents' Pause all gate on the agent sessions read the same way. A Pause or Resume pressed before such a read is rendered does nothing and claims no failure. Records' Ask also needs this mount's own records read at the batch's revision, since it names its session from those records. Each is checked again when pressed, against the read the page showed: a newer read must be rendered first. Review acceptance keeps its stricter `current` test: settled at the batch's capture revision.
- **Receipt writers:** a command that writes its receipt with `setQueryData` clears the proof, so it reads the key again: Review Map's media link reads the media key again, so its next edit is available with polling off (the link that finishes a new lot needs an HTTP read of the media, not necessarily the one shown), and Capture's media commands already read after each receipt. Settings › Agents and Batch defaults write their confirmed settings the same way, but their forms open once per visit, so no command waits on a later proof.
- **Instruction delivery:** `processing/instruction-delivery.ts` lives in `Batch`, above Processing's remounts. Delivery, automatic after a save or Retry, holds a read request (`requestRead`), which reads Processing itself, so it needs no mounted page, and shows "Delivery pending" until a Processing read started after it was asked for, and after the last hint, is adopted; it checks that again just before sending, then sends once. A read that reconciliation cancels waits for the read that replaced it; a failed or unavailable read reports the delivery as failed, with Retry.
- **Showing the wait:** `ReadState` shows the page's skeleton until its first data, then the page with the same element tree in every phase, and the page's own failure banner when the read fails. It reports refreshing reads to `RefreshSignal` (mounted by `App`), which shows `RefreshLine` after 400 ms, a 2 px line in a zero-height layer under the masthead, still under reduced motion and announced as "Updating", and adds "Updating…" after 3 s. A command waiting only for its read uses `Button`'s `reasonDisplay="quiet"`: `aria-disabled`, still focusable, with "Updating…" as its description and a tooltip on hover or keyboard focus. Every page has a skeleton beside it (`*Skeleton.tsx`): Batches, each batch tab (`TabSkeleton`), Processing and its Images and session panel, Review, the Map, Records, Changes, the Agents page, the Settings sections and local setup; smaller reads inside a page (a lot's evidence, a mapped record's InvenTree values, a location's path, the full list of a preparation's records, the attachment choice, the phone activity pill) show a `Skeleton` block in place. Reads the operator opens on demand (session failure details, a delete dialog's impact) and the Dev mode menu's local setup wait with a `Spinner`. A form that opens only on this visit's read (Settings › Agents, Batch defaults) shows cached settings from an earlier visit inside `DisplayOnly` until it lands.

### Session snapshots

`queries/snapshots.ts` keeps display-only snapshots of four reads in the tab's `sessionStorage`, through the projections in `queries/snapshot-projections.ts`: Processing, the Review workspace, the batch (for the header and the tabs) and Records. Each projection is still a valid contract DTO and is validated on write and on read; it leaves out Capture's settings, reference drafts and context, agent session IDs, attempt and message IDs (replaced by a fixed placeholder), proposals that relied on a session inbox message, and Changes' preparations and runs. Nothing else is stored: no bootstrap or CSRF token, credentials, the Agents list, media, drafts or commands.

- **Writing:** after each verified read, at most once per resource per second. A projection over 1 MB is not stored; a full storage clears every snapshot and is reported only in the debug panel.
- **Reading:** a page reads its own snapshot once when it mounts, only for the scope bootstrap confirmed, and passes it to `useFreshRead` as `restored`. It is never put into the query cache, so it can't verify a command.
- **Lifetime:** entries expire after 12 hours or with another build (`build.ts`, from the Vite `define` of the commit and build time). `ServerStateProvider` deletes other scopes', expired and malformed entries when a scope starts, and drops that scope's waiting writes when it ends.
- **After a reload:** until Capture's fresh read lands, `Batch` shows the batch header and the open Processing, Review › Lots or Records tab from their snapshots inside `DisplayOnly`, an inert wrapper, with `displayOnly` set so every command and edit stays closed. The live workspace replaces it once Capture is read. On a return within the tab, Capture's cached read (never stored) shows any tab the same way, Capture, the Map and Changes included; with neither, the open tab's skeleton shows.
- **Operator review:** while `Batch`'s operator review read for the batch's revision is under way, Review fences its commands quietly ("Updating…") with no banner; "Current operator review is unavailable or changed" shows once that read fails, pauses or settles at another revision.

`ServerState.test.tsx` verifies scope isolation and late prior responses. App/manual component tests cover deduplication, periodic recovery, paused reads, accepted revisions, retained drafts, pinned preparation identity and lost acknowledgement.

## Live server updates

A save is built when it is sent, not when it was queued: the newest settings this page knows, with only the fields this form changed and never another field's draft, under the revision the edit was made over unless only this page's own saves have moved it on (`localSaves`). An edited form stays on the settings it started from, so a newer load never mixes into it, and an untouched form follows the shared read; a change to a form's own fields from elsewhere is refused as a conflict before anything is sent. Validation runs at dispatch too: a step naming a provider that is now off goes back to Default with the reset note, and the default provider moves to one that is on. An edit made while its own save is in flight saves again after it; only the draft actually sent is acknowledged. Each save carries a new `save_id` (`useSettingsSave`). A `revision_conflict` keeps the value and pauses the queue until Reload (which shows the saved settings and drops the unconfirmed non-text values, keeping text drafts) or Try again (which reads the settings and sends the change again over the new revision, validated again). A save with no answer pauses the queue and is resent with the same `save_id` after 1, 2 and 4 seconds, then on Try again; a resend of a save that had applied answers with its receipt, after which the settings are read rather than adopted. `save_outcome_unknown` is terminal: nothing is resent, and Reload drops that change and the subsection's later queued non-text edits. `useDirtyForms` holds the navigation guard while any form has an edit, a pending or unconfirmed save, and releases it when the section unmounts. It passes the guard a save-before-leaving step: `useNavigationGuard` sends pending debounces at once on a link or Back, waits for the queue, and continues only when nothing is left unsaved; otherwise it stays and the failed save shows its Try again. Reload and close keep the browser's leave prompt. The navigation guard lets the Agents sub-nav and Back move between subsections of the mounted page, keeping the drafts, and still holds leaving Settings › Agents. Providers and "Provider and model per step" are one form (`ProvidersAndSteps`, `provider-form.ts`), rendered around Sessions: a card per provider (`ProviderCard`: its sign-in status pill with Check again and its sign-in dialog button, the On switch, the sign-in segmented control and its default model), the default provider as a segmented control whose providers that are off can't be chosen, and each step's model (`StepModels`). A card's Default model lists only its provider's models and can be chosen before the provider is turned on. Every control here saves as it changes. Turning a provider off saves at once together with its steps reset to Default and the note, superseding queued choices for it; turning off the last provider on is refused at its switch ("At least one provider stays on") and nothing is sent, as is turning one on with no default model chosen. The other subsections save with no provider on. Sessions (`SessionsForm`) holds sessions at once with the slot meter and Pause all; Instructions (`InstructionsForm`), the Part description style (`DescriptionStyleRow`, 500 characters), Tag suggestions (`TagSuggestionsForm`) and Web research (`WebResearchForm`) save on their own. Web research reads readiness (`useReadiness`): when it reports `web: 'unavailable'`, both settings render disabled through `DisabledFeature` with the badge "Not for this profile" in place of "Coming later" (`SettingRow`'s `disabledBadge`), showing the saved values; until readiness answers, the form stays usable. Every on/off setting (each provider's On, Suggest tags, both Web research settings and the deferred description switches) is a `Switch`. The switches, segmented controls, pickers and the stepper report their edits themselves; text fields are read-only while their Save runs, and the non-text controls stay usable while their saves run. Agent settings requests and responses carry no keys or tokens, and API keys have no browser field.

Each provider card's status pill comes from the read-only provider status (`useProviderStatus`, `GET /api/v1/agents/provider-status` through `agentsClient.providerStatus()`), read when the section opens, with no key: Claude "Token saved" (with its save time where the VM recorded one) or "No token"; Codex "Signed in", "Signing in" or "Not signed in"; "Checking…" while a read runs or the VM has no result yet; or an unknown state naming its reason, such as "Can’t reach the agent VM", never signed out (`provider-status.ts`). A failed read shows "Status unavailable". Each provider reads its own answer, and the latest session's sign-in refusal shows on its own line, "Last session couldn’t sign in" with its time, apart from the pill. Codex's card also says quietly when the VM last checked it ("Checked 2 minutes ago", on the page's minute clock, and "just now" for a time ahead of it, as the VM's clock or a minute tick still due can make it); Claude is read on every request, so its card doesn't. Check again (`checkAgain`) and every sign-in change make a fresh read (`readAfresh`, `refresh: true`), which the server never answers from its reused read or a read in flight, and which asks the VM for a new Codex check; a read still running is cancelled rather than joined. The fresh read starts a run of reads, as does a first read that finds a check running: while the VM's Codex check runs (`unknown`/`checking`, or a known state with `refreshing`), the status is read again every second (`POLL_MS`), until the check lands, a read fails, or the first read asked for after 15 seconds on the monotonic clock (`POLL_LIMIT_MS`) answers. A polite status region on each card announces "Checking Codex sign-in…" and then the run's outcome: the pill, a failed read, or a check that didn't finish in time. Each fresh read gets a strictly larger number (`latestFresh`), which names its run. A fresh read that is cancelled (a live hint refreshing every read) or joins an older fresh read asks again, up to three times, unless a newer fresh read has taken over. A failed read also ends its run in the cache, so returning to the section starts a new run. Requests are bounded by the client's 10 s operation timeout. The changes are kept in the query cache beside the status read, so leaving Settings and coming back keeps them; their fresh reads run through the query client, so they finish after leaving too. A late answer to a dialog already closed restarts the wait but keeps a newer confirmed change.

Codex's dialog runs the device sign-in, polls while it is pending and closes itself once a poll confirms the account; a declined or expired sign-in, or a command whose answer was lost, has the card read the VM again. ## Capture grouped workspace

`MediaWorkspace` composes three evidence entry actions above named groups and ungrouped originals. `useEvidenceWorkspace` owns the accepted media projection, exact selected IDs/revision and one payload-bound retained command. Polling cannot replace dirty group/evidence editors or membership selections; confirmed receipts cannot be rolled back by an older read. Crop polling may update derived output while the original crop intent stays pinned.

`EvidenceDragContext` uses exactly pinned dnd-kit React/DOM adapters; pointer, keyboard and touch dispatch the same atomic `move_many` command as explicit selection controls. A conflict preserves selection until explicit reconciliation. Rename, evidence notes and group instruction editors keep loaded revisions and explicit save/discard. Review/viewer renders retained note provenance beside the same linked evidence identities. Grouping does not choose subject links or attachments.

Picking files uploads them at once; there is no separate retain step. `media/useUploadQueue.ts` owns each picked File with its own idempotency key and expected revision, outside form state, and `MediaWorkspace` provides its ports. Photo and PDF pickers accept several files and bind their intended group before the picker opens. The photos picker sets no `capture` attribute, so a phone may offer its own picker sheet rather than opening the camera directly. Files dropped on the evidence panel or one of its groups, or pasted anywhere on Capture outside text fields and dialogs (`browser/usePastedFiles.ts`), go through `useUploadQueue`'s `addMixed`, which types each file as a photo or a document and counts them as one run; the innermost drop target (`components/media/useFileDrop.ts`) takes them, so a drop on a group goes into that group only, and one elsewhere on `EvidencePanel` reaches `MediaWorkspace` through its `EvidenceFilesHandle` and goes to Ungrouped. Files over a portal inside a target, such as a modal viewer, can't be dropped at all. The batch notes that Batch settings portals into the panel are reached through native listeners (`useSlotFileDrop`), because React sends a portal's events up its owner's tree. Picking, dropping and pasting share one gate (`media/upload-gate.ts`), which names why files can't start: the batch archived, Capture otherwise busy, no current read, an evidence change being sent or unconfirmed, or another evidence draft open. A refused drop or paste shows that reason on the panel; without a media client, `EvidencePanel` still takes dropped and pasted files, so the browser doesn't open them, and says media storage is unavailable. The native picker's return is not gated, because focus coming back briefly re-reads the batch. The queue sends one file at a time, because each upload and each group move advances the media revision: it reads the current revision, uploads, then adopts the receipt through a fresh membership read and a separate move command. That move trusts the read it has just made, not an earlier failed poll the handler's render still shows. A file that read already shows in any group is not selected or moved.

Each picked file shows as an `UploadTile` in its target group's evidence grid, or the ungrouped grid when it has no group or its group has gone. `MediaUpload` keeps only the pickers. The group header shows "Uploading 2 of 3", counting every file picked together, including any already added or refused. Uploading is indeterminate because the fetch request reports no byte progress.

Each tile's status is a live region: "Not added" and "Upload not confirmed" are alerts, and the other states are polite status messages. Retry and Read again keep focus on their tile; they never touch the selection, so a selection held after a refused move does not disable them, and queued uploads do not disable clearing or reloading that selection. Dismiss moves focus to the next tile's enabled control, else the previous tile's, else the group region. A focused tile that leaves on its own, because its file was added or a read overtook its notice, hands focus to its group region. Unmounting the workspace stops new requests and follow-up reads; a request already sent finishes on its own.

Outcomes are handled per file:

- **Refused:** each of these shows "Not added" with the reason and Dismiss, and later files continue:
  - a file that fails the type check or the size and label checks shared with the contracts client (a label must be well-formed UTF-16, so URI encoding cannot fail);
  - a failed revision read before sending, so nothing was sent;
  - a 4xx response;
  - a second revision refusal.
- **Lost response:** "Upload not confirmed" keeps the exact request. Retry resends the same key, revision, label and bytes; a receipt is adopted, and a 412 proves the file was not kept, so it is sent once more with a new key at the current revision.
- **Move not saved:** the retained original stays selected in its confirmed ungrouped projection, and its tile in the target group says "Added to Ungrouped". While that move's intent or selection is held, later files are not moved: they stay in Ungrouped with the same notice and leave the selection unchanged. Refresh and later finishes drop the notice once a read shows the file in any group, and the tile is hidden as soon as the latest read does.
- **Failed read after a receipt:** reported separately and read again on request; it never authorizes another upload.

Files uploading or awaiting Retry or a read count as unsaved work. Media, settings and instruction drafts share navigation protection without allowing a clean sibling to clear it.

## Persistent header observations

The Masthead lives within the existing keyed server scope and LiveUpdates lifetime, above the application content. Ordinary batch-tab navigation preserves that header, the query subscriptions and dirty form nodes. `HeaderStatus` uses the generated public `headerClient` and scoped TanStack Query keys; response identity is checked against actor/target/context before publication. Connection reads poll every 30 seconds independently of healthy sockets; work reads keep the existing fallback cadence or a 30-second live safety poll. A local clock and foreground/visibility reconciliation enforce 60-second observation expiry. `browser/useNow` supplies that clock to the header and to Capture's `useApplicationAvailable`, `browser/useOnForeground` triggers the header's foreground reads, and `browser/useOnline` follows connectivity.

`LiveUpdates` provides read-only transport state/time/coverage through `UpdateHealthContext` (`#/context`); no second socket is created. Transport freshness also expires locally under the shared 30-second last-frame policy, so foreground rendering cannot wait for a background-throttled socket deadline to report stale/unknown health. API read success, live transport and target reachability remain independent. Fresh failed target probes are unavailable; stale/unobserved observations cannot display reachable. Only validated same-context HTTP(S) root navigation with no credentials/query/fragment becomes the isolated Open InvenTree link. Header navigation does not change the dirty guard or grant command authority.

The controlled Radix disclosures are mutually exclusive, portalled outside the decorative header and bounded/scrollable at narrow widths and native zoom. Workflow details prefer current-batch work, retain known steps with incomplete coverage, distinguish selected from reported model identity and show physical occupancy despite logical cancellation. The headline comes from `header/workSummary.ts`. Inside a batch it names the open batch's failed steps first, with their count of failed jobs ("Research failed · 1"), then steps waiting for the operator, with the failure's glyph; the line under it lists the rest and the agents still working. A truncated work list names those steps without counts, or says "Status incomplete". "‹Batch› · no agents working" needs a fresh read with complete work and session lists, the aggregate `lane_occupied` flag clear and no session holding a lane; a lane held by an unlisted session reads "Agent lane in use". Outside a batch the read leaves out other batches' settled failures, so the headline names only active and waiting work and never claims no failures or no agents. A stale read says "Updating…" and a failed one "Status unavailable"; nothing says "all done". The former global activity strip is retired; Processing, Changes and Agents navigation remains in the disclosure. Local setup diagnostics live in Settings › Developer and the Dev mode popover, and the page-level Debug panel shows in debug mode. The header's commands are Check connection now and Resume for a paused batch (`ResumeBatch`, through the existing pause route, unavailable while the work read is stale or failed, and waiting with "Updating…" until the header work read it shows has one that started after the last live hint, with none in flight (`queries/useReadAfterHint.ts`); `useHeaderObservations` and `useBatchAttention` number their reads through the fresh-read registry for this), and no inferred completion percentages are added. The workflow details are 520 px wide on desktop and, on a phone, a centred sheet across the window less the popover's edge gaps. Each Processing batch shows one stage bar and one row per stage (`ActivityPopover`), each row linking to its step page with its count ("12 lots formed · 2 questions" for Examine, "7 of 12 lots" after it), a `StatePill` and a status line: the newest line from that stage's current, uncancelled attempts in the bounded active-session list, else a plain reason. Every batch in the header's `paused_batches` gets a group with Resume, with or without work, and so does a batch whose work was cut from the bounded work list while its sessions were listed; its uncounted stages read their current sessions' states. Counts come from the open batch's attention read when its request started after the header work read's, or when the header doesn't count the batch, else from the header read's `batch_steps`; whether a batch is paused comes from the header read whenever it has the batch, since the attention read may be cached.

`header/workSegments.ts` derives each stage's `WorkState` (done, working, waiting for you, paused, queued, not started or failed) in one order: failed, then working (a turn already running finishes in a paused batch), paused, waiting for you (waiting jobs or open questions), queued, done (Examine's lead job ready; a lot stage once every live lot is ready there; never with no jobs) and not started. An uncounted stage reads its retained jobs' states. `ProgressSegments` draws each state with its own colour and its own pattern (`BAR_PATTERN`: solid, stripes, dots, hatching, an outline drawn over the fill, a dashed centreline or crossed lines), fills a counted lot stage to its `ready_lots` share of the batch's live lots and tints an uncounted one whole rather than inventing a share; only a working stage animates, never from a stale or failed read (`still`), from a header work or attention read that started before the last live hint, or under reduced motion; the Processing overview's bars are also still until its read started after the last live hint. The Processing overview's progress bar uses the same derivation from its own snapshot. Each stage row is its own component (`StageRow`), with a `StatePill` whose `label` puts a leading count in place of the state word ("2 working") and an `EventTime` on its status line.

## Native session replacement

Processing's session chat offers an explicit fresh-conversation action when a session cannot resume, failed, was interrupted or needs login, as well as after cancellation. It submits the exact job/attempt and capture/job revisions through the validated replacement API for both Examine lead and lot sessions. History and queued input stay on the same lineage. Opening the session or refreshing retained state never triggers replacement; unavailable reads, an outstanding send or a busy/unavailable runner disable the action. The server remains authoritative for revision, scope and physical-slot checks.
